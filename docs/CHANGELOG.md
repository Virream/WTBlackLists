## 跑图线路测试器(未发布 · 2026-10-27 第六块)

> 主题: **回放光标旁显示型号与速度**(用户 2026-10-27 要求), 设置里可关, **默认开**;
> 多条回放时标签**环绕排布 + 引导线**。

### 新增: 光标旁的「型号 + 速度」标签

播放线路时, 表示载具位置的那个小圆点旁边多一行 `us_m1a2_sep3_abrams  45 km/h`,
**跟着圆点一起移动**; 速度是那一帧插值出来的值(不是整条线的平均值)。

* **默认开启**; 菜单「设置 → 回放时显示型号与速度(跟随光标)」可以关掉, 选择会记住
  (关掉后与以前完全一样, 只剩圆点);
* 型号优先用 `vehicle_cls`(纯型号); 8111 录制的条目没有它就用 `vehicle`;
  两样都没有就只显示速度(不显示 uid);
* 外观与时间标签同一套: 深色底 + 该队颜色细边框 + 白字, 在明暗底图上都读得清。

### 改: 多条一起回放时的标签布局 —— **环绕 + 引导线**(用户 2026-10-27 第二轮要求)

第一版是把标签**垂直错开**排下来, 24 台车挤在一小片时(用户截图)后果很明显:
标签排成一长条列, 离自己的点几百像素、完全看不出谁是谁。

现在的规则(用户 2026-10-27 第三轮口述): **以点为圆心画个圆, 标签就在圆里,
一根线连回去**:

* **16 个方位 × 6 圈候选 + 贪心**: 依次给每个标签挑代价最小的位置
  * 最内圈是**沿该方位“框边离点正好 8px”**的位置(`_tight_radius`) —— 贴着点又不盖住点。
    ⚠ 不能统一用“框半对角线”: 那是**最短**方向上的贴边半径, 251×21 的标签
    往正上方摆就会离点 123px, 看着像飘走了;
  * 每往外一圈加 `1.05 × 标签高`(刚好不互相压住), 最多 5 圈 → 标签永远在自己点的圆里;
  * `代价 = 重叠比例 × 250 + 第几圈 × 圈距 + 被窗口夹住的 300 + 盖住自己的点(禁止)`;
  * 重叠用**比例**(长标签不吃亏);
* **引导线**: 标签被挤到 10px 之外就画一根 1.2px 细线连到点的最近边, 一眼看出归属;
* 布局每 **0.25 s** 重算一次(O(n²×96), 24 个标签实测 **6.6 ms**),
  引导线**每帧**跟着点画 —— 所以看不出标签是分档移动的。

**效果**(24 条线, 910×768 窗口):

| 场景 | 4 圈时重叠 | **现在(6 圈)** | 框心到点中位 | 有引导线 |
|---|---|---|---|---|
| 24 台挤在同一个点(±10px) | 24.4% | **6.9%** | 102 px | 20/24 |
| 24 台分散在 300×200 | 0.8% | **2.8%** | 67 px | 6/24 |
| 24 台贴着窗口左边 | 57.5% | **25.3%** | 102 px | 22/24 |
| 单条回放 | — | 0%, 紧贴右侧 **8px**, 无引导线(与最初一致) | | |
| 3 条叠在同一位置 | — | 0% | 67 px | 0/3 |

扫参过程: 12/16/20/24 方位 × 4/5/6 圈, 16×6 是重叠与耗时的平衡点
(24×6 同点 2.0%, 但 9.7 ms)。

### 修: 标签跑成“画面顶部一条横杠”(用户 2026-10-27 截图)

现象: 二十几个标签全挤在窗口最上面一条横线上、字变成方块、引导线从一个点扇形散开。

根因: **布局用的坐标系和夹边界用的坐标系不是同一个**。布局拿 `_to_px()` 的
“地图本地像素”(**放大 3.3 倍时点就是 (2566,1955)**), 却拿 `self.width()/height()`
去夹它 —— 于是所有框都被夹到同一个角上, 叠成一条。

修法: 布局统一在 **控件像素**里算(`map_pos()`, 含缩放与平移), 夹边界才是对的;
* 软件路径绘制时减回 `_map_rect()` 左上角(画笔本来就平移过);
* GPU 路径 `nx = (px - r.left())/dw`、`ny = 1 - (py - r.top())/dh`(与悬停浮层同一口径),
  引导线锚点改用 `map_pos()` 而不是 `cur.x * dw`;
* **点跑到窗口外就不再画它的标签**(否则十几个看不见的点会把标签全堆在边框上);
* GPU 端文字左边缘补上 `CURSOR_LABEL_PAD`(以前文字顶着框的左边线)。

**两条绘制路径都做了**(GPU 与软件回退), 数值口径一致:

| | 软件(QPainter) | GPU(pygfx) |
|---|---|---|
| 标签 | `_draw_cursor_label` 每帧现画 | 每个回放线路一对 Mesh+Line+Text 对象 |
| 改字时机 | 每帧(画字本来就免费) | **只有文字真的变了才 `set_text`** |
| 每帧开销(实测, 2 条线/每条 1000 点) | 与原来同一量级(多两行 `drawText`) | **0.025 ms** |

⚠ GPU 端**不每帧新建对象**: 实测新建 `gfx.Text` 要 **1.14 ms**(三条约 3.4 ms/帧),
而 `set_text` 只要 **0.164 ms**。所以对象建一次, 每帧只改文字/位置; 几何(底框/描边)
只在**文字宽度变化时**重算 —— 平移靠 `local.position`(改矩阵, 不碰顶点缓冲)。

开关标签会让**图标层**重建一次(它本来就跟重生点/机场同一层), 轨迹几何一动不动。

## 跑图线路测试器(未发布 · 2026-10-27 第五块)

> 主题: **右键删除的确认框可能点不动**(不展开全局条目时)。改动只有 3 处调用点 + 2 行日志。

### 修: 「会弹模态框」的菜单动作改成等菜单关掉再执行

用户 2026-10-27 报: **不展开全局条目直接右键删除, 确认窗口弹出来却点不动(像卡死)**;
展开过再删就正常。差别在于菜单动作的 `triggered` 是在 **`QMenu.exec()` 的嵌套事件循环**里
发出的, 那一刻菜单自己还握着鼠标/键盘 grab; 而展开过的条目惰性加载早就做完了, 弹框那一刻
的时序不一样, 所以看着"只有没展开时才坏"。

改法: 删除全局 / 删除线路 / 重命名地图 三个动作统一走 `_defer_modal()`
(`QTimer.singleShot(0, …)`), 等 `menu.exec()` 退出、菜单隐藏销毁之后再弹。
**文案、数据、后续逻辑一律没动**, 只改"什么时候弹"。

⚠ **诚实记录**: 这次**没能复现**——程序化 `trigger()`、`QTest` 真实鼠标点菜单、
软件绘制 + 点亮 107 条轨迹, 三种方式都没卡(离屏和真平台都试过)。所以这条修的是
**机制上确实不对的那一处时序**, 不是"复现后修掉的"。为此额外加了 2 行日志:

```
删除全局录制 <id>: 弹确认框(清单已加载=True/False)
删除全局录制 <id>: 确认框返回 16384
```

万一还卡, 看这两行的**时间差**就能判断卡在"弹出前"(菜单/事件循环) 还是"弹出后"(等输入)。

## 跑图线路测试器(未发布 · 2026-10-27 第二块)

> 主题: **回放解析的三处修正** —— 开始/结束时刻不再靠阈值猜, 而是用位置采样当硬事实。

### 修: 开局那 32 台「占位飞机」不再算成载具

每个玩家在开局都有一台占位实体(`aircraft+player_unit`, 块里有明文 `dummy_plane`,
没有型号也没有 uid, 8~10 s 出生)。以前靠「寿命 <5 s」间接筛掉; 现在按这个明文标记
**精确**跳过 —— ECS 档案从 164 条降到 152 条, 一条阈值都不用。

顺带修掉一个**隐性错标**: 这些占位实体的 uid 与玩家第一台车的 uid 相同(32 台里 29 台),
于是几台**会动的 AI 车**(uid176/184/192/280)被它们"带名", 看着像玩家开的。
现在这几条正确地变成无名线(将来接 AI 阵营色)。

### 修: 同一次出生被建成好几条实体时, 合成一条寿命

实测 `t1_player07_0` 的 `uid=306` 有 4 条创建记录(235.78 / 236.52 / 238.93 / 240.84 s),
型号 `cn_ztz_99a → cn_m1a2t → cn_ztz_99a → cn_vt_4b` 乱跳, 每条寿命 0.7~2 s。
以前它们被当成「下一台车」逐条截断, 凭空多出 3 条零点几秒的假线。

合并判据**不看时间, 看采样**: 前一条记录在自己的存活窗口里**一个位置采样都没有**
= 选车/换车时的临时实体。玩家快速重生(同一 uid 紧接着再出生)时两条都有采样, 不合并。

### 修: 飞机的 uid 偏移单独标定

飞机块的组件布局与地面不同, 用地面标出来的偏移会读出 `0` / `1` 这种垃圾值。
现在有空中位置流时按空中 uid 集合**再标定一次**: `ah_64e` / `mi_28nm` / `fa_18e_block_2` /
`rafale` / `su_30mkm` / `su_34` 等 8 条从「读不出 uid」变成真实 uid, 其中 5 条能对上轨迹。

## 跑图线路测试器 v1.3.1(2026-10-27)

> 主题: 战区图标压在线上看不见 + 把机场跑道画出来 + **修 1.3.0 起的卡顿**。

### 新增: 「设置 → 图形」—— 可以指定显卡了, 显卡用不了会弹窗告诉你(用户 2026-10-27)

**先定用户画像**(用户 2026-10-27 明确, 以后不用再讨论):

| 项 | 结论 |
|---|---|
| 操作系统 | **只支持 Windows 桌面**。macOS 不做 —— 用 macOS 的人不需要这个工具(本来也从未支持过) |
| 显卡 | 2012 年之后的卡(DX12 那一代); 再早的驱动早已停更, 不提供支持 |
| 远程桌面 / 云电脑 / 虚拟机 | **明确不支持**(反作弊本身就过不去) |
| 兜底 | **仍然保留**, 而且有两条: 软件绘制(QPainter) 与 WARP |

**关键发现: "支持率百分之几"这种数字给不出来, 也不该按年份判。**
程序里唯一可靠的判据是适配器支不支持 **`float32-filterable`** —— 那是 pygfx 在
import 时就写死的 `required_features`, 拿不到的适配器**根本建不出 device**。
所以老显卡不是"按年份拒绝", 而是"建 device 时失败 → 弹窗让用户更新驱动"。

**另一个关键发现: 没显卡时 wgpu 照样"成功"。** 本机实测枚举到 4 块适配器:

```
[1] NVIDIA GeForce RTX 3060 Laptop GPU (DiscreteGPU) via Vulkan     float32-filterable ✅
[2] NVIDIA GeForce RTX 3060 Laptop GPU (DiscreteGPU) via D3D12      float32-filterable ✅
[3] Microsoft Basic Render Driver (CPU) via D3D12                   float32-filterable ✅  ← WARP
[4] NVIDIA GeForce RTX 3060 Laptop GPU/PCIe/SSE2 via OpenGL         float32-filterable ✅
```

第 3 块是 Windows 的 **WARP**(D3D12 的 CPU 光栅化), 它**也满足** pygfx 的硬要求、
**也能跑起来** —— 只是比 QPainter 还慢。所以判"有没有显卡"必须看
`info["adapter_type"] == "CPU"`, 不能只看"拿到了适配器没有"。

**能不能"自由指定显卡"? 能, 已实测。** pygfx 的 device 是全局单例
(`Shared._instance` 里还有 `assert ... is None`), 但 wgpu 官方留了注入口:

```python
wgpu.preconfigure_default_device("wt81111g", adapter=选中的那块)
# 之后再 gfx.WgpuRenderer(canvas) → 用的就是它
```

实测(`tools/probe_pick_adapter.py`, 逐块验证):

| 目标 | `preconfigure_default_device` | pygfx 实际用的 | 渲染一帧并读回像素 |
|---|---|---|---|
| `Microsoft Basic Render Driver (CPU) via D3D12` | ✅ | ✅ 就是它 | ✅ ndarray |
| `NVIDIA RTX 3060 Laptop (DiscreteGPU) via D3D12` | ✅ | ✅ 就是它 | ✅ ndarray |

⚠ 三条硬约束(写在 `route_map_gl.py` 的注释里):

1. 只能在**第一次**建 renderer 之前调 —— device 建好后再调是 `RuntimeError`。
   所以"改设置"只能**存起来 + 提示重启**, 不能热切换(菜单里明写了这一条);
2. 不用 `PYGFX_WGPU_ADAPTER_NAME` 环境变量: 它找不到适配器时会让 pygfx
   **在 import 时就抛 ValueError**(整个模块炸), 一律走 API;
3. 判"有没有显卡"看 `adapter_type`(见上)。

**菜单长这样**:

```
设置 → 图形
    [✓] 自动选择(推荐)            ← 只认真显卡, 优先 D3D12 → Vulkan → OpenGL
        NVIDIA GeForce RTX 3060 Laptop GPU (D3D12)
        NVIDIA GeForce RTX 3060 Laptop GPU (Vulkan)
        Microsoft Basic Render Driver (D3D12)   ← 标"软件模拟, 很慢", 只在排查时选
    ─────────
    [ ] 强制软件绘制(不用 GPU, 最慢但最保险)
        当前用的渲染方式…
```

* **自动模式永远不选 WARP**(它比软件绘制还慢); 但**用户显式选它就照办** ——
  这是"我知道会很慢, 我要试试"的入口;
* 指定的卡如果已经不存在了(换驱动/拔了显卡/换机器) → 自动回退 + 一条提示,
  **不瘫**;
* 「当前用的渲染方式…」把**本次实际**用了哪块卡、本机枚举到哪些适配器全列出来 ——
  用户报"卡"时让他点这里, 一眼分出"走了 WARP / 走了软件绘制 / 显卡正常但卡在别处"。

**以前是静默回退软件渲染**, 用户只会觉得"为什么这么卡", 完全不知道原因。现在分类弹窗:

| 情形 | 弹窗标题 | 建议 |
|---|---|---|
| 枚举不到非 CPU 适配器 | 没有找到可用的显卡 | 更新显卡驱动 |
| 枚举时抛异常 | 无法访问显卡 | 更新显卡驱动(附技术细节) |
| 建 device 失败 | 显卡初始化失败 | 换一块显卡或更新驱动 |
| 建渲染窗口失败 | 显卡能识别, 但画不出来 | 多半驱动太旧 |
| 指定的卡没了 | 指定的显卡换了 | (只提示, 程序照常用 GPU) |
| GPU 组件加载失败 | GPU 加速组件缺失 | 打包漏了 wgpu DLL 时用 |

**崩溃回退(应对抓不住的 Rust panic)**: wgpu 配置 surface 失败会在 **Rust 层 panic**,
`try/except` 抓不住, 而打包版是 `--windowed`(无控制台) —— 用户看到的就是"闪退"。
现在启动时先留一个 `gfx_pending=1` 的标记并 `sync()` 落盘, 画布**活过 4 秒**才抹掉
(panic 常发生在渲染头几帧, 那一刻之前的代码都已经"成功返回"了);
下次启动发现标记还在 ⇒ 判上次崩了 ⇒ **自动改软件绘制 + 持久化 + 弹窗说明**。
用户修好驱动后到「设置 → 图形」取消「强制软件绘制」就能再试一次。

**顺手修了一个测试污染**: `RouteTesterWindow` 的 `QSettings` 以前写死
`QSettings("WTBlackList", "RouteTester")`, 于是**跑一遍测试就会改掉用户真实的
轮询间隔/显示开关**(而且新增的崩溃标记会让测试把用户的设置改成"强制软件绘制")。
现在 `QSettings` 可注入, `make_window()` 一律指向临时 ini —— `test_dead_style`
也从"读真实设置"改成读同一个临时文件。

**落地的代码**:

* `wt81111g/gfx_info.py`(新) —— **纯数据**, 不 import wgpu 所以谁都能顶层导入:
  `AdapterOption` / `GpuNotice` / `adapter_option()` / `enumerate_adapters()` /
  `gpu_usable()` / `PREF_AUTO` / `PREF_SOFTWARE` / `PYGFX_REQUIRED`;
* `wt81111g/route_map_gl.py` —— `create_map_view(parent, prefer=…, force_software=…)`,
  内部 `_pick_adapter()` 按设置挑卡并注入; 返回值上挂 `gpu_notice`(该弹的窗)与
  `gpu_adapter`(实际用的哪块);
* `wt81111g/route_window.py` —— 「设置 → 图形」菜单、`_on_pick_adapter()` /
  `_show_gfx_info()` / `_show_gpu_notice()` / `_clear_gfx_pending()`;
  设置项 `gfx_adapter` / `gfx_software` / `gfx_pending`;
* `wt81111g/help_text.py` —— 关于页新增「显卡与渲染(设置 → 图形)」一节,
  把支持范围、菜单用法、"启动时的显卡提示是什么意思"全写进去;
* 探针: `tools/probe_gpu_caps.py`(每块适配器支不支持 float32-filterable + 能否建
  device)、`tools/probe_pick_adapter.py`(指定适配器能不能真的生效)。

**注意「本次生效」与「下次生效」是两个值**: `_gfx_prefer/_gfx_software` 是**本次**
真正在用的(菜单勾选、崩溃标记都看它), `_gfx_prefer_saved/_gfx_software_saved` 才是
存进设置的值。混成一个的话, 用户改完设置还没重启时 `_clear_gfx_pending` 会以为
走的是软件渲染、不去抹崩溃标记, 下次启动就会被误判成"上次崩了"。

58 + 30 项测试全过, 新增 `test_gfx_settings`: 适配器折叠成选项(真显卡/WARP/老版
只给属性的 API)、**自动模式不选 WARP**、只有 WARP 时按"没有显卡"处理(抛
`LookupError`)、显式选了 WARP 就照办、指定的卡不存在时回退并返回说明、
`force_software` 时 `gpu_notice` 必须为空(是他自己选的, 别打扰)、

### 重构: 存储改成一局一个二进制会话文件(为 500~600 局准备, 用户 2026-10-26)

**先把账算清**。实测一局服务器回放约 **80 万点、217 条线**, 于是 500 局 = **4 亿点**:

| | 以前的单文件 `routes.json` |
|---|---|
| 体积 | **5~6 GB 一个文件** |
| 改一个地图名 | **要重写整个文件**(1.9 s/局 × 500 ≈ 十几分钟) |
| 内存 | 全量常驻 ≈ **32 GB** |

所以旧的"一个文件装完 + 全量内存"两条路在 500 局这个量级上是**算不出来**, 不是慢。
现在改成:

```
data/routes.json                      ← 只剩**地图级小数据**(几十 KB, 普通 JSON)
data/routes.sessions/<id>.wts         ← 一局一个(头部 JSON + 每条线一个 zstd 点块)
```

* **一局一文件** → 改地图名只写几 KB 的 meta, 导入一局只写那 3~5 MB, **其余几百局一个字节都不动**;
* **点用列式 `float32` 二进制 + 每条线一个 zstd 帧**(带内容校验和) —— 不用 JSON 数字,
  `frombuffer` 是纯 C; 精度对数据本身(`round(x, 5)` = 2 cm)绰绰有余;
* **文件分两段**: 第一段是**会话级**元数据(几百字节), 第二段是**每条线路**的清单。
  启动只读第一段 —— 侧栏最上面三层(地图 → 模式 → 局)根本用不到线路清单;
* **点用到哪局才读哪局**(`LazyPoints`, 继承 `list` 所以 100 多处调用一行都不用改);
* 侧栏/悬停要的"点数 / 首末时刻 / 最高速"跟着元数据走, **不会为了显示它们去读点**;
* **侧栏也改成展开才建子项**: 一局 200 多条线, 500 局是 10 万行 —— 启动时全建出来
  要一两秒、还要吃掉上百 MB。现在只需要建"地图/模式/局"三层;
* 旧的单文件(明文或 gzip)在第一次启动时**自动迁移**成会话文件, 原文件改名
  `.v1.bak` 留档不删。

**实测**(探针 `tools/probe_store_v2.py` / `tools/probe_tree_scale.py`):

| 指标 | 旧 | 新 |
|---|---|---|
| 启动(500 局 / 10.8 万条线) | 不可行 | **存储层 66 ms + 建侧栏 78 ms** |
| 改地图名/隐藏/关联/校准 | 重写全部 | **8 ms**(只写 meta) |
| 保存一局(80 万点) | 1.9 s(还要重写别人) | **305 ms**(只写这一局) |
| 删除一局 | 重写全部 | **10 ms** |
| 磁盘 | 5~6 GB 单文件 | **4.4 GB**(500 局) |
| 展开一局(建 251 行) | — | **6.7 ms** |

真实数据迁移核对(`data/routes.json`, 3.66 MB / 18 个会话): 迁移 137 ms,
**逐点与旧文件比对 0 处不一致**, 之后启动 **7 ms**。

**为什么不上数据库**: 数据是"几千行、每行一个几 MB 的二进制块", 查询全在内存里做,
索引能力用不上; 反而要多管 schema 迁移、WAL 和"索引 vs 文件两份真相"。
"一局一文件 + 原子替换"把一致性限定在单个文件内, 坏文件跳过即可自愈。

⚠ **下一步**: 批量导入多局时按局并行。已经做了, 见下面「批量导入多局按局并行」一节。
单局内部**不拆**(`DeltaHistory` 跨包且跨分片共享, 拆开必错)。

52 + 30 项测试全过。新增的存储用例把这几条都钉住了: 格式、往返、惰性 + 元数据、
只写变过的、坏文件自愈、删记录连文件一起删、旧格式迁移。

⚠ **同一个改动带出来的 bug(用户 2026-10-26 当天报到)**: “全局路线条目无法进一步展开了”。
Qt 里**没有子项的条目根本不画展开三角**, 而“惰性填充”要等 `itemExpanded` 才建子项 ——
没有箭头就点不开, 于是永远等不到 `itemExpanded`, 死锁。现在折叠着的条目会挂一个
不可选的占位行「（展开载入 N 条线路）」, 箭头因此存在; 一展开先清掉占位行再建真子项。
代价是 500 局重建侧栏 54 → **78 ms**(多出来的就是那 500 个占位行), 仍远小于 1 s。

### 新增: 批量导入多局按局并行(用户 2026-10-26)

用户: “实际用起来估计软件要存 5、600 局录像, 存取系统需要高性能支持……
简单的能拆分的就拆分, 复杂性过高容易出错的就别拆”。

**为什么按局拆**: 一局服务器回放要解 **20~35 秒**的位流, 全是纯 Python 计算 ——
GIL 把线程挡死了, 所以只有**多进程**才是真并行; 而按局又是最安全的粒度:
每局自己读自己的文件、自己建自己的记录, **进程之间不共享任何状态**。

**为什么单局内部不拆**: `wrpl_reader` 的 32 槽 delta 历史跨包、跨分片共享,
按分片拆开必然算错 —— 这正是“复杂性过高”那一类, 不拆。

**关键设计: 子进程自己把结果写成 `.wts`, 主进程只接管文件。**

```
子进程: load_replay() → build_record() → _pack_global() → 写临时 .wts
        ↓ 只回传几十字节的元数据(线路数/玩家数/耗时)
主进程: RouteStore.adopt_session()  → os.replace 进 routes.sessions\ , 读头部建记录
```

要是把 `GlobalRecord` pickle 回主进程, 一局就是几百 MB 的搬运(几十万个点对象),
比解析本身还慢; 而“一局一文件”碰巧让这件事变得**完全多余** —— 文件已经是最终形态,
主进程连打包都省了。

其他细节:

* **两局以上才走并行**: 单局仍走原来的串行路径 —— 它能报「分片 3/24」这种细进度,
  而且不必为一次导入 spawn 一个解释器; `WTRT_NO_PARALLEL=1` 可强制串行(排查用);
* **并行度** = `min(局数, CPU 数÷2, 4)`: 一局光解出来的对象就占几百 MB, 不敢按核数开;
* **条目 id 由主进程发号**: 并行时两局可能落在同一毫秒, 各自取时间戳会撞;
* **取消** = 不再等后面那些局; **已经解析完的照样入库**(不让白跑的活浪费掉),
  并且 `shutdown(wait=False)` —— 等还在跑的那几局会让界面像死了一样(一局几十秒);
* **子进程必须自己配日志**: spawn 出来的解释器是干净的(主进程的 handler 带不过去),
  而打包版是 `--windowed`、`sys.stderr` 是 `None` —— logging 保底的 stderr 输出器
  会自己抛异常, 把“只是有点警告”的解析变成失败。现在配 `FileHandler`(同一日志文件,
  带进程号), 拿不到路径就配 `NullHandler`;
* **打包版硬要求 `multiprocessing.freeze_support()`**: 已加在 `route_tester.py` 的
  `__main__` 第一行 —— 没它的话每个子进程都会把 `main()` 重跑一遍(开一堆窗口)。

验证: `tests/route_tester_test.py` **54 项**, 新增两条:

* `test_adopt_and_import_pool` —— 接管子进程写好的会话文件 / 临时文件被**挪走**
  (不是复制) / 坏文件返回 `None` 不炸 / 地图名与已知地图登记上 / 重启后还在 /
  并行度 / 发号 / 校准表按关卡代号也能展开;
* `test_import_wiring` —— 两局以上**真的走并行分支**、单局仍走串行、`expect_server`
  透传、失败照常汇总(把 `import_many` 换成假的测接线 —— 那段代码平时没机会被执行到)。
真正的加速比要拿真回放量: `python tools\probe_import_parallel.py <路径…>`
—— 它会先串行跑一遍、再并行跑一遍, 对比总耗时并校验两条路径的产物完全一致。
⚠ 探针**要求你在命令行上手写路径**, 不会去扫游戏目录(那是禁止的)。

**实测**(真回放, 用户 2026-10-26 提供的 `回放文件\`): 

| 输入 | 串行 | 并行 | 加速比 | 产物 |
|---|---|---|---|---|
| 4 个本地回放(每局约 6 s) | 24.9 s | **9.5 s** | **2.61×** | 287,582 点, 逐局一致 |
| 3 个服务器分片文件夹(每局约 19 s) | 56.7 s | **27.9 s** | **2.03×** | 1,050,679 点, 逐局一致 |

没跑满 3~4 倍是正常的: 一局解出来的对象有几百 MB, 同时跑 3 个进程时内存分配与
解压带宽先到瓶颈。**2× 意味着「十局」从 5 分钟降到 2 分半**, 这已经够用了。

⚠ **踩到的坑(用户当天报到, 三局全废)**: 用户 Shift 选 3 个分片文件夹 →
“软件卡住, 一会后报错: 共 3 个输入, 成功 0, 失败 3 / 会话文件写出来了但读不回来”。

日志把原因写得很清楚: `[WinError 17] 系统无法将文件移到不同的磁盘驱动器` ——
半成品原来写在 `tempfile.mkdtemp()`(默认 **C 盘**), 而数据在 **D 盘**,
**`os.replace` 不能跨盘**。所以“解析成功、打包成功、就是接不进来”, 三局全丢。

改法:

* **半成品直接写在 `routes.sessions\` 里**(后缀 `.wts.part`): 与最终文件同目录,
  `os.replace` 是原子改名, 不可能跨盘; `.wts.part` 不以 `.wts` 结尾,
  `scan_dir` 不会把它当会话(测试钉住了这条); 每次导入开始前 + 收尾都清残留;
* `adopt_session()` 另加一层兜底: `os.replace` 失败就退化成“复制 + 删源”,
  免得将来别的调用方传了别处的路径又栽一次;
* 顺带改好了**“看着像卡死”**: 以前进度条要等第一局跑完才动(并行时拿不到单局
  细分进度), 现在一开局就报“正在并行解析 3 局(同时 3 局, 每局约半分钟)…”。
  用户描述的“卡住一会”其实就是这半分钟。

### 性能: 点改成**列数组**常驻, 不再逐点造对象(P3, 用户 2026-10-26)

**先量再改**(探针 `tools/probe_points_speed.py`, 拿真实会话文件, 一局 126 条线 / **43.99 万点**):

| 阶段 | 耗时 |
|---|---|
| `read_block`(读文件 + zstd 解压) | **21 ms** |
| 列展开 `array.frombytes` | 0.4 ms |
| **逐点造 `TrackPoint`**(旧实现) | **213 ms** |
| `np.frombuffer` + reshape | **0.2 ms** |

也就是说「打开一局」的耗时**九成是在造 Python 对象**, 而不是在解压或读盘 ——
213 ms / 43.99 万点 = 每点 0.48 µs, 全是 `TrackPoint(...)` 的函数调用开销。

**改法**: 从会话文件读出来的点**保持列数组**(`(列, n)` 的 `float32` 二维视图),
用到哪个点才现造哪个(`_Cols.at`)。

* `LazyPoints` 因此有了两种模式: **列模式**(文件读来的)与**对象模式**(录制/新建的);
  `columns()` 给热点路径拿列数组(`(fmt, arr)`);
* **遍历一律物化**(`__iter__` 先 `_flat()`): 全项目有大量
  `for p in points: p.x = ...`(换校准重算坐标), 若给的是临时对象, **改了不生效
  且没有任何报错** —— 那是最难查的一类 bug, 所以宁可牺牲"遍历不造对象"这点收益;
* 走快路径的正好是"打开一局/每次重画"要用的那几样, 它们**都不物化**:
  `_vmax`(第 4 行最大值)、`_times`(`arr[0].tolist()`)、`_bbox`(min/max)、
  `_px_line`(直接查表造 `QPointF`)、`build_speed_segments`(numpy `argsort` 一次算完
  24 个速度桶的索引, 不再逐点调 `bucket_index`)、保存时的 `pack_points`(直接 `tobytes`);
* 单点访问仍是老样子: `points[i]` 现造一个对象(`float()` 包了一层 ——
  `np.float32` **不能**被 `json.dumps` 序列化, 将来谁拿点去写 JSON 会直接抛错)。

**实测(同一局, 含解压)**:

| 路径 | 第一次画出来 |
|---|---|
| 先物化成点对象(P3 之前) | **1307 ms** |
| 列存储(现在) | **776 ms** |

**1.68×**。剩下的 776 ms 里, 几乎全是 **132 万个 `QPointF` 构造**
(分桶折线 88 万 + 灰色底衬折线 44 万) —— 那是 Qt 那边的硬成本, 想再降一个数量级
只能做 **LOD 抽稀**(44 万点画在 1200 px 宽的窗口里, 每像素 366 个点, 本来就严重过采样)。
这一块要动缩放/缓存策略, 留到下一轮(P3-B), 本轮不碰。

55 + 30 项测试全过, 新增 `test_column_points`: 列存储下
「点数/列数组/单点访问都不物化」+「分桶几何与老路径**逐桶逐点一致**」+
「物化后改点能真的存进文件」。第二条是关键 —— 快路径算出来的颜色桶必须和原来一样,
否则线的颜色会跳。

### 性能: LOD 抽稀 + 回放前缀不再造对象(P3-B, 用户 2026-10-26)

用户先问了一句关键的话: **“抽稀会不会损失鼠标悬浮时可读取的点数细节?”**
—— **不会**, 而且这条现在是测试钉住的断言:

* `_hit_test` 用的是 `rec.points` 的**全部原始点**(numpy 全量算距离), 与"画出来的
  折线"是两套东西; 抽稀只作用在**给 QPainter 的几何**上;
* 抽稀**强制保留** 首末点 / **速度桶变化点**(否则颜色分段的位置会漂, 线的颜色会跳) /
  静止段点;
* 放大后 `w/h` 变大 → 同样的 1 px 阈值对应更细的归一化步长 → **自动用回原始精度**,
  缓存键里带了 `_geom_key()`(含 zoom 与窗口尺寸)。

做法(两个独立改善):

**① 回放前缀不再切片造对象。** `_play_prefix_geom` 原来是 `geom.feed(pts[:k], vmax)`
—— 列存储下 `pts[:k]` 会为**整条已播放前缀**造一遍点对象, 而这是回放**每帧**都要调的
东西。现在 `_LiveGeom.feed(points, vmax, limit=k)` 直接在列数组上读前 k 个,
`QPointF` 只为真正画出来的段构造。**这才是"播放界面卡"的主因**。

**② LOD 抽稀。** `lod_mask(arr, w, h, vmax)`: 同一屏幕像素内的连续点合并成一段,
屏幕上本来就是一条直线。

**实测**(探针 `tools/probe_points_speed.py`, 一局 126 条线 / 43.99 万点,
窗口 1200×800 + 2048² 底图, 含解压):

| 路径 | 第一次画出来 | 分项(px_line / segments) |
|---|---|---|
| 先物化成点对象(P3 之前) | **1364 ms** | 318 / 995 ms |
| 列数组(P3-A) | 776 ms | — |
| **列数组 + LOD(P3-B)** | **505 ms** | 186 / 280 ms |

比 P3 之前 **2.7×**; `vmax`/`times`/`bbox` 三项已经降到 **2 / 6 / 1 ms**(原来 19 / 13 / 75)。

⚠ **一个诚实的数据**: 这批真实数据 LOD 只抽掉 **43.99 万 → 22.5 万(51%)**,
把阈值从 1 px 放到 2 px 也只到 49% —— 说明这些点**本来就平均 1~2 像素一个**,
没有多少水份可挤。想再快只能牺牲信息(20 px 阈值那种), 不做。

⚠ 最后 500 ms 里几乎全是 `QPointF` 构造(约 0.8 µs/个 × 45 万)。
PyQt6 没有"从 numpy 批量造 QPolygonF"的 API, 这是硬成本; 真要继续只能改渲染后端
(把点直接喂给 OpenGL 顶点缓冲), 那是另一个量级的事, 不在本轮范围。

56 + 30 项测试全过, 新增 `test_lod_decimation`:
1.2 万点的斜线 → 抽稀后点数明显变少、首末点不变、**每个速度桶边界两侧都保留**;
2. **被抽稀掉的点, 鼠标悬浮仍能精确命中**(断言命中的正是那个原始点的 t, 不是附近保留点)。

踩到的坑: 用 PowerShell 的 `Set-Content -Encoding UTF8` 改文件会**写入 BOM**
(变成 `EF BB BF`), 之后用 `ReadAllText` + `UTF8Encoding($false)` 写回才干净。

### 新增: 悬停时 **Shift+滚轮** 逐个采样点前后翻(用户 2026-10-26)

用户: “当鼠标悬浮在路线上的时候按住 shift+上下滚轮控制读取上一个和下一个点的数据,
因为有时候想精确读取某一个点的数据鼠标指针要动的很细微有点难控制,
**但是注意还没显示出来的别读**”。

**为什么要它**: 相邻两个采样点在屏幕上常常只差**一两个像素** —— 想读第 51 个点而不是
第 50 个, 靠鼠标挪等于在跟手抖较劲。滚轮一格走一个点正好替代那种微操。

做法:

* `_hit_test` 顺带把**点在这条线里的下标**带回来(以前只回 `RoutePoint`, 而相邻点坐标
  可能只差 0.5 px, 反查不可靠), 悬停状态因此多一个 `_hover_idx`;
* `wheelEvent` 里: **按住 Shift 且正悬停在某条线上** → 不缩放, 调 `_step_hover(±1)`
  (上滚 = 前一个点, 下滚 = 后一个点); 没有悬停目标时 Shift+滚轮**仍然是缩放**,
  不抢原来的手势;
* 浮层文本第三行末尾补「第 N/M 点」—— M 是**整条线的总点数**(不是"现在能读到的点数"),
  这样回放播到一半时能看出「后面还有没走的」; 光标不动也能知道跳到哪了;
* **只翻到已经画出来的点**: `_hover_point_limit()` 在回放时取
  `_played_prefix(rec, playhead)[0]` —— 与 `_hit_test` 完全同一个判据,
  所以滚轮**不能偷看**玩家还没走到的位置; 滚到边界就停住(不越界、不报错);
* 鼠标一移开就恢复“跟着鼠标重新命中”; 离开控件时下标一起清掉。

57 + 30 项测试全过, 新增 `test_hover_wheel_step`: 命中第 50 点 → 下滚到 51、上滚回 49
(时间/速度都跟着换成那个点的) → 滚到两端停住 → **回放到第 60 点时怎么滚都停在 61**
→ 无悬停时 Shift+滚轮仍然放大 → 鼠标离开清空。关于页也补了一节说明。

### 修: 保存 / 启动 / 退出卡顿(用户 2026-10-26: "从 1.3.0 这个版本开始的")

**不是代码退步, 是数据量。** 1.3.0 起线路来自回放文件, 一局就是 **80 万点**。
实测那次 `save()` 一次 **3.8 秒**、`load()` **1.8 秒** —— 而这些都在 UI 线程上执行:
点 F6 保存要等它写完叠加层才消失、提示音才响; 开始录制、选关卡代号、关窗口同理。

| 环节 | 原 | 现 |
|---|---|---|
| `save()` | 3.8 s(阻塞界面) | **1.9 s, 且已挪到后台线程** |
| `load()`(启动) | 1.79 s | 1.52 s |
| 界面调 `save()` 的代价 | 3.8 s | **0.04 ms**(只置个标志) |
| 关窗口 | 3.8 s | 没改动就**瞬时**, 有改动 2.1 s |

怎么做到的:

1. **点写成数组, 不用 `asdict`**: 以前每个点是
   `{"t":..,"x":..,"y":..,"speed":..,"dx":..,"dy":..}`, 光键名就 40 个字符。
   改成 `[t, x, y, speed, dx, dy]`(`_pack_route_point`)后 JSON 从 3300 万
   降到 ~2900 万字符, 而 `asdict`(80 万次递归深拷贝)整个去掉了。
2. **保存时不再 `round`**: 80 万点 × 4 次 `round` 要 **1.08 秒**(实测), 而数据在
   **采样时就已经 round 过**(`replay_import` / `global_record` 的构造点)。现在
   只 round `t` —— 它是逐帧累加的, 会带出 `0.30000000000000004` 这种尾巴。
3. **gzip level 6 → 1**: 0.46 → 0.09 秒; 体积 8.3 → 11.6 MB(自己的数据, 体积不是瓶颈)。
4. **写盘挪到后台线程** + 80 ms 合并窗口: `save()` 变成"请求", 立即返回; 连续操作
   (标记 + 结束录制)只写一次。关窗口时 `flush()` 等它写完 —— 但**没有新改动时直接
   返回**(`_dirty` 判定), 所以大多数时候关窗口是瞬时的。
5. **解包走位置参数 + 长度快路径**: 0.82 → 0.52 秒(80 万次调用, 关键字参数与多余
   的 `float()` 在这里很贵)。

⚠ 测试/探针里大量“写完立刻重读”的断言, 所以新增 `route_store.SYNC_SAVE = True`
开关(两个测试文件开头都打开), 不用每处手动叫 `save_now()`。

### 改: 启动时的「同图不同分辨率」合并判得更严了(用户 2026-10-26)

8111 同一个关卡会以 1024²/2048²/4096² 不同分辨率发底图(实测), 按字节哈希当地图身份
就会把同一张图算成两张。这个归并有两处入口, 原来**两处的严格程度不一样**:

| 入口 | 时机 | 原来的闸 |
|---|---|---|
| `MapCache.save()` → `similar_key()` | 8111 每次发新图 | 灰度差 + 结构哈希 + **最近邻余量** |
| `MapCache.duplicate_groups()` → `_pair_same()` | 程序启动, 清历史重复 | 只有前两道(**少了余量**) |

而启动那套会**删掉多余的图片文件**、还会改 `routes.json`(留 `.bak`), 出错的代价
比运行时大得多。收紧成跟运行时同一套、并且在两处再各加一道:

**① 补上最近邻余量。** `second` 取“该键与**全局第二近**那张”的灰度差,
必须 ≥ `SAME_IMAGE_TOL × SAME_IMAGE_MARGIN`(= 1.2 × 2 = 2.4)。于是“两张都很像”时
两边都不认。

**② 双向。** 新增纯函数:

```python
def group_same(distance, ham, second_a, second_b) -> bool:
    """批量/启动时分组用的同图判定 —— 比 looks_same 更严: **双向**都要认。"""
    return (looks_same(distance, ham, second_a)
            and looks_same(distance, ham, second_b))
```

`second` 是“自己做主角时次近的那张”, 所以 A 侧和 B 侧看到的余量可能不同 ——
A 只有 B 这一张像它(`second=None`, 直接放行), 而 B 那边另有一张更像的(不认)。
单看 A 就会误合。

**③ 全员。** 加入一个组要求与组内**每一个**成员互相都认, 不再“和第一个像就行” ——
否则 A~B、B~C 但 A≁C 时会链式误合并。

顺带把 O(n²) 次 `phash` 降到 n 次(先算好 `_fingerprints()`), 每对比较只剩
一次 `gray_distance`, 启动反而更快。

**验证**: `tests/route_tester_test.py` 新增 `test_map_duplicate_strict`(47 项)。
纯函数用实测数字直接钉住语义, 不需要造图 —— 同图 灰度 ≤0.60 / 汉明 ≤372,
不同图 ≥11.97, 同一张图的不同区域 2.91 / 1776:

```
group_same(0.4, 241, None, None)   → True    缓存里只有这两张
looks_same(0.4, 241, None)         → True    ← 单看 A 侧会误合(这正是要堵的)
group_same(0.4, 241, None, 1.0)    → False   B 那边另有更像的 → 不合并
group_same(0.4, 241, 2.4, 3.1)     → True    两边都有明确次近
group_same(0.8, 1700, None, None)  → False   灰度像、纹理不像(同图不同区域)
```

再加上三张图的实际分组: `{256 版, 128 版}` 归成一组, 颜色不同的那张不并进来。

### 修: 看不到双方机场(缩放下限卡在 1.0 + 平移出不了图框)(用户 2026-10-26)

**两个根因都在 `route_map_view.py` 的视图约束里**:

| 约束 | 原来 | 问题 |
|---|---|---|
| `MIN_ZOOM` | **1.0** | 1.0 就是"整张图刚好铺满窗口", 再缩不了 |
| `_clamp_pan()` | `(图幅 + 窗口)/2 - 40` | 只能在"图片矩形 + 窗口"那一圈里拖 |

### 修: 「▶ 回放」一直是灰的 + 侧栏层级(地图名 / 模式名)不对(用户 2026-10-26)

**① 播放按钮灰着不能点。** 启动时 `store` 是空的 ⇒ `_update_buttons()` 算出
`has_track=False` ⇒ 按钮被禁用;**导入完成后没有任何地方再算一次**, 于是
「删掉 `data` → 重新导入」之后按钮一直是灰的(我上一版只修了“点了没反应”，

* 修法: `_reload_tree()` 末尾补一次 `_update_buttons()` —— 导入 / 删除 / 重命名
  都会走它;
* 另外补了兜底 `_fallback_tracks()`: 侧栏里**没选中、也没点亮眼睛**时, 播
  「当前底图下最新那一局」的全部线路(眼睛点亮状态不落盘, 重开程序后全是关的)。

**② 模式层显示 `finland_Dom`。** 以前直接把回放头的 `battle_type` 当模式名,
而它其实是「地图名 + 模式缩写」拼起来的内部串。8111 的规则是
**战区数量 → 模式**(3=战区控制 / 2=战区攻陷 / 1=战区争夺), 回放里虽然拿不到
战区坐标, 但 `cz_circle_0N` 的**个数**能数出来(实测两份回放都是 3 个)。

### 地图校准(世界米 → 底图像素): 回放线路终于能对齐底图了

**要解决的问题**: 回放导入的路线以前用「本局观测到的 min/max」归一化, 那和地图
图片覆盖的矩形**不是同一个**, 所以路线相对底图会偏、会缩。

**答案**: 8111 的 `/map_info.json` 里 `map_min` / `map_max` 就是**图片覆盖的世界
矩形**(米), `/map_obj.json` 的 `x` / `y` 是该矩形内的 0~1。于是

```
px = (x - min_x) / (max_x - min_x) * 图片宽
py = (max_z - z) / (max_z - min_z) * 图片高      (北在上)
```

**实测确认**(finland 三点图, 2026-10-25 20:15 抓取):

```
map_min [0,0]   map_max [2048,2048]   grid_size [1700,1700]
map.jpg 2048×2048 像素  →  1 像素 = 1 米（px = x，py = 2048 - z）
mission.json: "占领并守住战区 ╸,╹,╺" → 3 个战区
战区 A (597.6, 1039.6) / B (1007.1, 1089.8) / C (1590.1, 1096.2)
   → 打回图片分别是「左村 / 中路 / 右村」, 与底图完全吻合
坦克重生点 40 个(20 蓝 + 20 红), 两队各一簇
fighter/ucav 重生点在**图框外 7~10 倍** —— 正常, 画的时候要允许出界
```

**回放里拿不到的**: 战区中心(`cz_circle_*` 的平移是占位值, 两张不同地图都是
`(1832, 5, 2456)`, 换算成像素在图外)、坦克/各机型重生点坐标(只有名字)。
这两样交给 8111, **一张图抓一次**即可。

**闭环已通(怎么用)**:

1. 进一局这张图, 跑 `python tools\wrpl\capture_8111.py` 抓一次 8111 数据;
2. 菜单「地图管理」选中那张地图(回放导入的地图会以 `无底图` 行列出, 选中它);
3. 点「导入 8111 校准…」选刚才那个文件夹 → 外框与底图一起装进去,
   **已导入的旧记录会自动重算坐标**(`renormalize_map_records`, 不用重新导入回放);
4. 以后同一张图的回放直接就是准的。

**实测效果**(芬兰单点模式, 117 条地面线路): 97 条完全落在 2048 m 底图内;
20 条在框外的是 `t2_airfield_aaa_*` **机场防空**(固定在几公里外的机场, 单点),
不是回归 —— 以前是把它硬挤进画面。

**落地的代码**:

* `wt81111g/map_calib.py` —— `MapCalib`(世界矩形 + 图片尺寸 + 战区/重生点)、
  `load_from_capture()`、`load_bundled()`(读 `assets/map_calib/<关卡>.json`);
* `RouteStore.map_calib` —— 按地图键存校准(`calib_of` / `set_calib` / `clear_calib`),
  `merge_map_keys` 时跟着迁移;
* `MapCache.put()` —— 按**指定地图键**装底图(回放导入的图没有 8111 图片);
* `replay_import.build_record(data, src, calib=...)` —— 有校准就用校准矩形,
  没有退回观测范围估算; `ImportStats.calibrated` / `calib_note` 写进导入报告;
* 地图管理器: 新增「回放校准」列 + 「导入 8111 校准…」/「清除校准」按钮,
  并且**只有轨迹/没有底图的地图也会列出来**(否则回放地图根本选不中);
* `GlobalRecord.norm_rect` —— 记住归一化用的矩形, 换校准后能原地重算。

预置校准时把 `assets/map_calib/<关卡名>.json` 打包进去即可(打包脚本已支持)。

### 修: 残骸被当成"多出来的一条线"(用户 2026-10-25: A26_2)

**现象**: 一位玩家名下的 `ussr_t_72b3_2011` 有两条 —— `A26_1` 正常, `A26_2` 从死亡
那一刻一直拖到对局结束, 4837 个点**全在同一个坐标**, 而且永远不显示阵亡
(玩家本人 670s 已经换了铠甲-S1)。

**原因**: 车被击毁后位置流**继续上报残骸**, 坐标一动不动(实测某 uid 击毁于 147.7s,
之后 12,641 个点都在 (981,1070), 直到 1012s)。整局地面采样里**约 73% 是残骸**,
且 67/67 个被击毁的 uid 都会这样。

**先找过"残骸标记", 结论是回放里没有**(负结果, 记下来免得再找一遍):

| 找过的地方 | 结果 |
|---|---|
| 位置包 14 个标志位(`b1 / 4bit / v2 / v3 / b2 / dir / turrets / full / pnd / npn / size / point4 / turretPos / sensor`) | 逐点记录某 uid 死亡前后 **1 万+ 个包, 全部标志位完全不变** |
| ECS 创建包模板名(30 种) | 无 wreck / debris / corpse 类模板(`destructed_model` 全局限 1 个, 不是通例) |
| 击杀包 | 只有 `killer_uid / killer_pid / victim_uid / victim_pid`, 没有"尸体 eid" |

**所以只能靠"存活窗口"裁**, 窗口外的采样直接丢。窗口 = `[ECS 创建, min(ECS 销毁,
被击毁那一刻)]` —— **击杀列表的时间**是关键的一环:

* `0x26` 销毁包对**残骸常常根本不发**(残骸就留在场上), 这时 `died_t` 只能兜底成
  对局结束。只看它就会把冻结的残骸整条留在线上 —— 实测 6 个 uid 在 **79~194 秒**
  被击毁, 之后 **1.9~2.2 万个采样全在同一个坐标**(跨度 0~5 m), 一直报到 1005 秒,
  于是 6 条幽灵线拖了整局(`Brikmen XM` / `Adolf Nickler` / `GHOST40044` 等)。
* 击杀包的 `VictimUid + 时间戳` 正好补上: **被打死的那一刻就是这辆车的终点**,
  之后的位置流全是残骸。取窗口内**第一次**击杀(之后的属于 uid 复用)。
* 起点仍然用 ECS 创建包的 tick —— 就是「这辆车什么时候出生」。

**不做任何"有没有位移"的启发式** —— 残骸被撞会滑动, 实测 6 个被撞残骸滑了 **5~22 m**,
用位移判定必然误判。中途试过的 `strip_corpses()`(位移 > 20 m 当新车)已删除。

击杀端点只给 **0.5 秒**窗口容差(其余 2 秒): 击杀时刻同时是切段点, 给 2 秒会多出一截
几十个点的碎屑段(`A26_2` 那种 `_2` 小尾巴)。空中的坠机残骸同理, 太短又几乎没动的段
直接丢。

判死窗口仍保留到击杀后 **20 s**(用于标"阵亡"红叉), 否则阵亡标记会消失。

效果(三点图 107 条 / 本地 116 条): 全 31 位玩家**时间重叠 0 处**; 末尾「原地不动
≥ 120 秒」的线**只剩 20 台机场 AI 防空 + 2 台真蹲坑的防空车**(以前有 6 条残骸长线
拖满整局); `A26_2` 消失, `目击而道存矣` 干净的 5 条, `WineLover` 3 条。

**战果核对(用户 2026-10-26 提供当事实)**: 那局结局是**敌方只剩 ZTZ99、ADATS、
苏-24M 这三台在移动**, 另一队(我方)**6 位存活**。导入结果逐条对上了:

| 阵营 | 导入结果里 `dead=False` 且线尾在末尾的玩家单位 | 末尾 60 s 位移 |
|---|---|---|
| B 队 | `cn_ztz_99` / `us_adats_bradley` / `su_24m_china_killstreak` | 464 / 49 / 1818 m |
| A 队 | `uk_challenger_2_megatron` / `ussr_bmpt_72` / `tiger_uht` / `ussr_t_80u` / `ussr_t_72b3_arena` / `ussr_t_90a` | 146 / 122 / 1166 / 83 / 293 / 389 m |

**误杀校验**: 反过来查「击杀之后、本车 ECS 窗口结束之前还在移动 > 100 m」的档案

### 修: 一位玩家名下挂了 4 条线、其中一条从**敌方重生点**开始(用户 2026-10-25)

**根因(两个, 都不在 ECS)**: 

**① 击杀包的 `victim_pid` 根本不是玩家槽位。** 用 ECS 的出生组名(已验证 66/66)
当裁判逐条核对 88 个击杀包:

| 字段 | 对得上 | 对不上 |
|---|---|---|
| `killer_pid`(配 `killer_uid`) | **65/65** | 0 |
| `victim_pid`(配 `victim_uid`) | 1 | **56** |
| 伤害包 `pid` | 0 | **2** |

88 条击杀里 **53 条的 `victim_pid` 都是 14** —— 那不是槽位, 我们解错字段了。
而 `uid_pid[victim_uid] = victim_pid` 这条映射把所有**受害者**的 uid 全算到了
同一个玩家头上: 实测 26 个 uid 只靠它才有主人, 且全是错的 —— 于是别人(甚至敌人)
的车都挂到了他名下, 从他的名字看就是"4 条线", 其中一条从敌方重生点起步。

> ✅ **修正后仍然不采信它**: `uid_pid` 只从 `killer_pid` 取; 受害者/被击伤者的
> 主人交给 ECS 的出生组名(`_fill_uid_pid_from_ecs`, 只在该 uid 上所有档案
> **同一个槽位**时才采用, 避免 uid 复用的歧义)。

**② 少数创建包的 uid 读取偏移差 1 个字节。** 之前认为"ECS 的 uid 有 42/142 不可信"
是**错的** —— 那 42 台里绝大多数是机场防空/工事/`*_support_*` 这类 **AI**, 它们本来
就不在位置流里。真正的玩家载具是 83 台, 其中 **18 台**读不出合法 uid, 而且全都落在
几个固定假值上(880 / 1392 / 1136 / 112)。

把这几块的组件值区域摊开看: `00 80 00 00 … 38 70 [uid] 00` —— 它们比主流**多 1 个
字节**, uid 在 `rel+1`。办法不是猜, 而是**把这批挑出来再标定一次**(同一条“命中
已知 uid + 互异性”规则), 实测在子集上得到 `rel2 = rel+1`, 18/18 命中、17 个互异;
而常量字段(如 `+27` 恒为 56)会被互异性门槛挡掉。

**效果**: 玩家载具 uid 合法率 **65/83 → 83/83**;
WineLover 名下 **4 条 → 3 条**(正好是他那 3 台豹2A6/豹2A6/梅卡瓦3);
全 31 位玩家「同一时刻两台车」的**时间重叠 0 处**(三份回放都是 0)。

**顺带修**: 每条线的最后一个采样往往落在**击杀那一刻**, 而 ECS 的销毁时刻还要再晚
~10 秒 —— 判死窗口从 5 秒放到 20 秒, 否则所有阵亡标记都会消失。

### 修(2026-10-25 反馈: 点服务器录像后卡死 + 内存一直涨)

- **原因**: 老实现 `_list_parts()` 只是 `sorted(listdir())`, 把所选文件夹里**所有**
  `.wrpl` 都当成同一局的分片, 而且每一份都**整份读进内存再整份解压**。
  误选一个放着好几局录像的大目录时, 内存就是按“文件总大小 + 解压后大小”堆上去的。
- **现在**:
  * 只读**文件头**(`read_header_file`, 默认 8 KB)扫描分片, 不整份加载;
  * 逐分片处理完即时 `del`(单份服务器回放可能几百 MB);
  * 分片数 > 400 或总大小 > 3 GB **直接拒绝**并提示“把同一局单独放一个文件夹”;
  * 解析期间弹**进度框**(`[k/N] 分片 x/y · 包 a/b`), 随时可点「取消」。
- **目录不再猜“里面有几局”**: 用户自己会把同一局的分片放在一起, 所以
  一个文件夹 = 一局; 本地回放则是一个文件 = 一局。
- 分片按**自然排序**(`part2` 在 `part10` 前), 纯字符串排序会把顺序弄反、
  解出来的 delta 全错。

### 新增: 严重伤害事件(`0xF157`)—— 把「载具↔玩家」覆盖率再撑一点(2026-10-25)

严重伤害包与击杀包同构(1=载具 uid / 2=玩家槽位 / 3=型号 / 4=玩家 uid / 5=unk),
同样用 `IdFieldSerializer32` 解。**被打过但没死**的车也会被打上标记。

实测那局只有 10 个 `0xF157`(这局几乎没打成重伤), 覆盖率 69 → **71/94**, 
有名字的线路 74% → **78%**。

### ECS 实体档案(`wt81111g/wrpl_entities.py`)——「这辆车是谁的」解决(2026-10-25)

之前判断「必须搞一份组件哈希表」是**错的**。真正需要的信息全都躺在**明文**里,
只需要把 `ptype=6` 的**实体创建包**(`0x24` / `0x25`)解到「组件值起点」为止 ——
组件值一个都不用解析, 所以**完全不需要 `ecshashes.json`**。

四件事全部拿到(服务器回放 avg_finland 实测):

| 需求 | 来源 | 实测 |
|---|---|---|
| 什么时候出现 | 创建包的 tick | 1,325 个实体 |
| 什么时候消失 | 销毁包 `0x26` 的 `ReadEID` | 926 个 eid, **与创建包 100% 对得上** |
| 什么型号 | 块内明文 `tankModels/…` | 66/66 命中, 42 种 |
| **谁的 / 哪一队** | 块内明文出生组名 `tN_playerMM_K` | 66/66 绑定 |

关键点:

- **模板名是明文**(`tank+player_unit` / `fortification` / `rocket` …), 模板名本身
  就决定实体类别, 这是绕开哈希表的第一步;
- **`0x25` 是 LZ4 压缩的创建包**(233 个), 而 `lz4` 这个 PyPI 包没有 cp314 的
  wheel —— 自己写了 40 行 block 格式解压(纯 Python, 不引依赖);
- **出生组名 `t1_player(NN)_0`**: `t1` → `slot = NN-1`,
  `t2` → `slot = NN-1+K`, K = 每组人数(16v16 时 16, 8v8 时 8, **现场拟合**)。
  注意 `t1`/`t2` 前缀**不是阵营**(两队是交叉的, 32 个名字正好对应 32 个槽位);
- 验证方式纯回放内部: 「击杀者 uid → 击杀者槽位」是确定事实,
  与公式 **32/32 完全一致**(一开始把"被杀者"也算进 uid 归属会得到 57% 的假结果
  —— 受害者当然属于对面玩家);
- **uid 偏移不写死**: 用「与 MPI 已知 uid 集合的交集 + 互异性」现场标定
  (实测 +28; 常量字段会 100% 命中已知集合, 必须用互异性排除)。

### 修: 机场防空全归 A 队 / 核弹机不见踪影

两件事其实是同一个根: **AI 单位与特殊飞行器没有出生组名**, 只能靠别的信号定边。

**① 机场防空**: 它们是 AI 工事, 名字形如 `t1_airfield_aaa_small_01`。这些名字以前
**根本没被读成型号** —— `include_air=True` 之后一条 `ground = not include_air` 的
全局开关让地面模板也去走「机型词」分支, 于是任务对象名被当型号写了进去, 又因为它
不是 `tankModels/` 格式而在别的路径上丢失。现在改成**按模板**判断, 并单独识别
「任务对象名」。

关键发现: **`tN_` 前缀与队伍编号是反的**(`t1_` 属 team 2)。两条独立验证:

```
机场出生的飞机: 已知 team1 的 12 架, 首点全部靠近 t2_ 那侧机群
地面载具出生点: team1 的坦克 29/29 靠 t2_, team2 的 35/36 靠 t1_
```

(注意这与玩家出生组名 `tN_playerMM_K` 完全不同, 那套的 tN 不是阵营。)

**② 核弹机**: 用户 2026-10-25 反馈 —— `______dma` 这局没死就打够了 2500 分起核弹机,
被对面 F-15E 拦截后又回坦克继续打。回放里能对上:

```
dma(uid=31) 的击杀在 608.5s 之后空了 254 秒, 直到 862.2s
742.2s  159(pid 8, f_15e) -> 169(pid 0)   us_aim_120c_5_default
770.5s  玩家 eclipsa- 在聊天里问 "what happened to the nuke"
```

`uid=169` 就是 `tornado_ids_de_assta1_britain_killstreak`(英国 killstreak 核弹机)。
它不显示的原因: 击杀包里它的 `victim_pid` 是 **0**(服务器不归属), 而 `0` 恰好是真实
玩家槽位, 我们不敢采信 —— 于是它没有阵营, 被当作「解不出来的空中单位」丢弃了。

现在加了一条兜底: **用起飞位置定边** —— 首点离哪个机场群近就算哪队, 但只信「真的很近」
(< 3 km 且明显更近)的情况。`uid=169` 的首点离机场只有 **468 m**、离对面 28 km,
判定明确。巡逻/攻击机常 10 km 外进场, 这种就不猜。

结果: 核弹机线路出现在 A 队(`A51  10:48  tornado_ids_de_assta1_britain_killstreak`)。



UCAV 的构造块里**没有**出生组名 `tN_playerMM_K`, 所以槽位公式用不上。但它**能被击落**,
而击杀包的 `victim_pid` 就是**受害者**的玩家槽位 —— 正好是放飞它的那个人;
反过来它自己击杀别人时 `killer_pid` 同理。

- 新增绑定步骤: 对「没有出生组名」的实体, 用 `killer_uid / victim_uid == 该 uid`
  的击杀事件定主人, 且**要求事件时刻落在存活窗口内** —— uid 会复用, 时间不对就会
  张冠李戴(实测 `uid=120` 的伤害事件给 pid 9、击杀事件给 pid 10, 就是不同时刻的两位主人);
- 实测这局 7 架 UCAV 里, 4 架有交战证据(2 架 A 队 + 2 架 B 队), 3 架全程没交战;
- **解不出阵营的空中单位直接忽略**(用户口径: 宁可不要这条线, 也不要硬塞进某一队);
- 顺带修: 「玩家同一时刻只能开一台车」的链式截断**只对有出生组名的实体生效**。
  UCAV 与玩家的坦克**并行存在**, 算进链条会把坦克截成零点几秒
  (实测 `GHOST40044` 的 `ussr_t_90m_arena_m` 被自己的 UCAV 顶掉)。



飞机/直升机走的是 `ptype=2`(FlightModel), 之前一律硬编码 `side="A"` —— 因为曾判断
它的 uid 是「独立空间」。实测**不成立**: ptype=2 的 uid 与地面共用同一套 11 位编号
(同一时刻不会重复), 所以可以用 ECS 的 `aircraft+player_unit` 档案把空中航迹绑到玩家。

- 现在 `load_replay` 会把飞机档案也解出来, 单独存进 `ReplayData.air_vehicles`
  (地面仍走 `vehicles`, 两条线各自的存活窗口不混);
- uid 偏移**只在**地面模板上标定 —— `aircraft+player_unit` 里有一大批是开局出生的
  占位实体(`dummy_plane`, 没有型号也没有 uid), 混进来会把标定带歪;
- 空中航迹也做**越窗裁剪 + 按销毁时刻切段**(同地面, 击杀时刻不参与), 并标 `dead`;
- 实测 avg_finland: **14/16 的飞机 uid 能绑到玩家**, 侧栏里 `su_25t` / `jaguar_is` /
  `hunter_f58_switzerland` / `tiger_uht` 都挂到了各自玩家名下;
- 剩下没有出生组名的是无人侦察机(`ucav_recon_micro_flir`), 仍兜底在 A 队。



用户 2026-10-25 反馈: 一位玩家名下出现 **4 条 `cn_ztz_96b`**, 但游戏里除以色列 M51 外
一局只能出击 **2 次** —— 说明有车被错误地切成了两条。

原因: 车被击毁后**残骸还会被上报约 10 秒**, 而击杀时刻和 ECS 销毁时刻并不相同:

```
uid=61  ECS 窗口 born 18.7 -> 373.7   cn_ztz_96b
        击杀包 victim 时刻: 363.3          ← 比 ECS 销毁早 10.4 秒
```

我们在**击杀时刻**切了一刀, 剩下的 10 秒残骸就成了第二条线路
(实测 `B33_2` 正好 `00:10`、`B41_2` 正好 `00:12`)。

现在: **被 ECS 存活窗口覆盖的击杀时刻不再当切段点**, ECS 的 `died_t` 才是权威边界;
没有 ECS 档案的载具(AI)仍然用击杀时刻切。

连带修正: 「阵亡」数之前被**重复计一次**(正片一次 + 残骸尾巴一次), 现在一辆车只算一次
(实测 `做帝江号…` 5 台 / 阵亡 10 → **5 台 / 阵亡 5`)。



- **同一 uid 的先后两辆车被合并成「1 台」**(用户 2026-10-25 提问: 「第一辆车被击毁后
  第二次又出了相同型号的车会不会有 bug」—— 会)。回放的 uid 是**场上槽位**而不是唯一
  实体, 实测这局有 21 个 uid 对应 2~5 辆车。基号原来按 `(uid, 队)` 分配, 所以
  `uid=61` 那两辆 `cn_ztz_96b` 会共用一个编号、侧栏只算 1 台, 而且型号标签会张冠李戴
  (实测 `B47_3` 显示成 adats 的车, 实际是 `us_m18_hellcat`)。现在基号按**这一辆车的
  ECS 档案条目**分配, 同型号同玩家的两台车也会分成 `B33` / `B41`。
- **`died_t` 比 `born_t` 还早**: eid 同样会被复用, 而销毁表原来只记「第一次」销毁,
  后创建的实体拿到的是前一个实体的销毁时刻(实测 `uid=114` 一辆车 `born 210.9 -> died 14.0`)。
  现在销毁表按 eid 记**全部**时刻, 匹配时取「不早于创建时刻的第一个」。
- 段号 `_N` 改成**按车辆**重新计数(一辆车 `_1/_2`, 下一辆仍从 `_1` 开始),
  不再是整个 uid 的全局序号。



### 修: 同一辆车被数成多辆、寿命重叠

- **基号**: 一辆车因为「隔太久没上报 / 一步瞬移」会被切成多段, 以前每段都重新取

  序号, 变成 `A25_1 / A26_2 / A27_3` —— 侧栏把一辆车数成三辆、时长还重复累加。
  现在同一个 uid 的多段**共用一个基号**(`A25_1 / A25_2 / A25_3`);
- **台数/在场时长**: 「台数」去掉 `_N` 段号后去重; 「存活」改成各段区间的**并集**
  (直接求和会把重叠时间算两遍);
- **越窗裁剪**: ECS 给了每辆车的存活窗口 `[born, died]`, 窗口之外的采样点一定属于
  别的东西(uid 被复用给微型侦察无人机 / 别的实体)。不裁的话会出现「同一玩家同一
  时刻开着两台车」(实测 `A25_3` 从 01:39 一直画到 16:30, 而这位玩家 01:42 已经
  换车了)。裁完线路 213 → 170 条, 每辆车的生命周期完全连贯、无重叠。



### ECS 补充: 当初为什么误判「必须搞哈希表」

早期只看了 `0x20 ENTITY_MSG`(组件增量) 和 `0x22 ENTITY_REPLICATION`,
这两类包里**组件名确实是 hash**, 明文里 `unit__*` 一个都没有, 于是以为无解。
漏掉的是 `0x24 / 0x25`(**实体创建**): 它自带**模板定义表 + 模板名字符串**,
而模板名本身就把「这台实体是什么」说清楚了, 型号和身份又都是块内的明文串。

- `ptype=6` 实际分布(服务器回放): `0x20` 12,430 / `0x22` 1,260 / `0x26` 758 /
  `0x24` 531 / `0x25` 233 / `0x21` 38 / `0x23` 1;
- `ptype=7`(快照) **服务器回放里 0 个**;
- 仍然解不出来的: 组件**值**的语义(血量/弹药/装填进度等)。那确实需要哈希表,
  但本项目不需要 —— 路线测试器只要「谁 / 哪队 / 什么车 / 什么时候出现消失」。

### 新增: 飞机 / 直升机轨迹(ptype=2 FlightModel, 2026-10-25)

`ptype=2` 是**独立于地面通道**的另一个 uid 空间(数值会重叠, 不能混), 实测 4 Hz。
包体本身是一串 entry, 每条一个 uid:

```
HasUID:1 → uid = compressed() & 0x7FF(没有则 uid += 1); uid == 0x7FF 就是包尾
noData:1 → 本帧无数据
Unk0/Unk1 都是 1 → 本条到此为止
Unk2:1 Unk3:u32 Unk4:1 Unk5(可选位集) Unk10/Unk11(zigzag 变长表)
PosX/PosY/PosZ: f32          ← 位置
EulerBytes:u32 Unk12:u32 对齐 Unk13:7B
engines / sensors / countermeasures / targets / 尾部两组可选
```

⚠ **尾部必须全部走完**: 只解到位置时每包只能拿到 1 架飞机(包里其实有 40+ 个 uid 条目);
补全尾部后 6 架 → **16 架 / 13,683 个位置**。

⚠ **错位检测**: 尾部字段读错一位后位置就变垃圾(实测出现 **-1137 m 的高度**), 而且不会
自愈 —— 所以一旦位置不合理就丢弃本包剩余部分(丢掉 2.3%)。

集成:
- `ReplayData.air_units`(与 `units` 分开存);
- 归一化范围**仍用地面的** —— 飞机常飞到 20 km 外的机场, 算进去会把战场压成一小块;
  超出的部分画到画布外;
- 侧栏显示 `✈ uidN`, 速度按相邻点位移算(不设上限, 超音速正常)。

实测(avg_finland): 95 条地面 + **16 条飞机 = 111 条线路**; 解析 32.7 → 35.0 s。

### 新增: 玩家身份 + 真实分队 + 击杀(2026-10-25)

位置包只给 `uid`（0..2047 的**载具槽位**），没有任何身份字段。但另外两种包能把身份补齐，
**而且都不需要 ECS 组件哈希表**:

| 包 | 签名 | 内容 |
|---|---|---|
| **Slot** | `0xF02D`(ptype=4) | 玩家槽位 0..255 → `player_id`(u64) + 名字(65 B) / 军团 / 称号 / **队伍**(u8) |
| **Kill** | `0xF058`(ptype=4) | `KillerPid` / `PlayerVehicle` / `VictimUid` / `KillerUid` / `PlayerWeapon` / `VictimPid` / `DestroyedWeapon` |

实现: `wt81111g/wrpl_events.py`（含 `IdFieldSerializer255/32` 的字段表解码、`ReadSize`）。

- `KillerPid`/`VictimPid` 是**玩家槽位号**，`KillerUid`/`VictimUid` 是**载具 uid** →
  凡参与过击杀/被击毁的车，uid ↔ 玩家 的映射直接得到;
- 载具型号也从 `PlayerVehicle` 白拿;
- 算上击杀事件，**服务器回放实测能覆盖 73%（69/94）的载具**；
- `build_record()` 现在按 **team 真实分 A/B**（team=1→A, team=2→B），
  `UnitLife.icon` 改成「玩家名 · 载具型号」，侧栏直接可读。

实测（avg_finland，24 分片）: **32 位玩家 / 88 次击杀 / A 队 49 条 + B 队 46 条**,
74% 的线路带玩家名。解析耗时 30.3 → 32.7 s（slot 包 14,016 个，多 2.4 s）。

### 性能(2026-10-25: 服务器录像 34 MB 从 230 秒 → 30 秒, 7.6 倍)

解析耗时 99.6% 都在**解包后的位流解码**, 逐项改下来:

| 改动 | 效果 |
|---|---|
| `BitReader.bits()` 从**逐位 Python 循环**改成按字节批量取(`int.from_bytes(...,"big")` 正好是 MSB 优先 + 大端拼接) | 230 → 90 s |
| `bytes_n()` 不对齐时也一次性取位窗口; `u16/u32/f32` 对齐时直接切片 | |
| `rle0ki_decode()` 从逐 2 位写 bytearray 改成**预计算块表** + 低位先拼 + 一次甩出 8 字节 | 90 → 45 s |
| RLE 的 if/elif 状态机换成**转移表**(状态 = `code`/`sup` 各 4~6 种, 输入 = 一个 4 位组) | 45 → 39 s |
| 去掉每步的 `len(out)` 调用、改用计数器 | 39 → 30 s |

本地回放(11 MB / 141,786 包): 也会快同量级, 现在约 6 秒。

> ⚠ 中途踩过一个坑: 以为「`code==4` 字面量模式会持续」，想整字节 memcpy —— 实际
> `code` 每组都复位成 `-1`，改完样本数从 151,611 掉到 103,648。现在用新旧实现
> 对拍 3,000 例随机输入做保证(`rle0ki_decode` / `xor_patch` 全等)。

### 修(2026-10-25: 线路贴着地图边框走成直线)

- **归一化范围从 1%/99% 分位改成 0.1%/99.9% + 两侧留 5% 余量**, 并且**不再把坐标夹到
  0~1**。原来 1%/99% 分位下实测有 **2,848 个点(1.88%)落在框外**, 被 `min(1.0,max(0.0,x))`
  夹到边框上 → 玩家自己绕到重生点后方那一段就变成一条贴边的假直线(A22/A49)。
  改完两种回放都是**框外 0 点**。
- **丢弃“只出现一瞬间”的段**: 以前只验点数 ≥ 3, 于是只被看见 1.4~3 秒的车在图上
  就是一个孤立小点(A1/A11)。现在还要过一道 `时长 ≥ 3s 或 位移 ≥ 50m`。

### 修(2026-10-25: 线路中一段莫名跳变 / A67)

- **uid 是“场上槽位”, 不是唯一实体**: 玩家在车里操作微型侦察无人机、或者死后重生,
  同一个 uid 前后就是两台不同的东西, 而时间上是连续的 —— 原来只在“间隔 > 45 秒”
  才切段, 这种串号就拉出一条瞬移直线。
- 实测证据(avg_finland 服务器回放): `uid=142` 在 t=404.6s 一步跳了
  **370.9 m / 3.52 s = 105 m/s(380 km/h)**, 地面车最快也就 150 km/h。
- 现在多了道闸: **一步 > 200 m 且折算速度 > 60 m/s(216 km/h) → 切段**。
  那局线路数 94 → 95, 单步最大位移速度从 0.0046 降到 0.0013(归一化/秒)。
- 另查过: 本地回放里“隔了 5 秒以上”的相邻采样,**距离 p50 = 0 m** —— 那是停着的车,
  不是串号, 不需要切。

### 实测(avg_finland / finland_Dom, 全程 985.8 秒)

## 跑图线路测试器 v1.2.0(2026-10-24)

> 主题: 数据准确性。这一版基本都是在修“录下来的东西不对”——
> 速度、死亡时刻、坐标、战区、线尾, 以及 hudmsg 漏采。
> 另有几项使用体验改动(三档轮询率、地图隐藏、按钮文字)。

### 新增

- **地图管理加「隐藏」列**: 空战等场合 8111 也会发地图图片, 那些地图永远用不到却在左侧
  列表里占一行。现在「地图管理」每行有一个「隐藏」勾选框, 勾上就不再在左侧列表显示;
  轨迹、名称、缓存图片都保留(不是删除), 取消勾选立刻恢复。
- **回放中“阵亡的线突然消失”(修)**: 两个原因——
  ① 不勾“被击毁后路线变暗”时, 代码把整条线**直接清除**(而不是“不变暗”), 播到
  阵亡那一刻整条就没了; 现在不勾 = **照常按速度配色显示**;
  ② 勾了变暗时, 灰色太淡(`alpha=100`、线宽 2.0)。一条只有几十米长的轨迹(比如
  原地待机的防空车)在深色底图上几乎看不见 —— 现在 alpha → 165、线宽跟正常段一致。
  实测触发场景: 西奈半岛那局一辆待机 209 秒只移动 61 米的 SAM。
- **全局路线的速度被放大了 2~4 倍(修)**: 上一版的“静止段折叠成 `hold`”把
  “每帧位移小于 0.8 m 的**慢速行驶**”也当成了静止, `hold` 一路累加到当前帧 ——
  下次存点时算速度的 `dt` 被压成一帧(40 ms), 速度就变成真实值的
  `真实间隔/40ms` 倍。实测西奈半岛那局: 图上人人 80~110 km/h, 而按点反算
  只有 20~40 km/h。现在只有**坐标一模一样**才算“没动”(8111 对停着的车每帧报同一个数),
  慢速行驶不再污染 `hold`。⚠ 旧录像里的速度不会自动变, 要重录。
- **"没车就自动停录"改成"只认回车库"(修)**: 以前"全场没有可录单位超过 3 秒"就判
  "已回车库"并停录 —— 但**没车不等于结束, 只要有重生点随时能再出一辆**。
  西奈半岛那局就是: A 队地面车在 16:17 之后陆续打光(每秒只剩 1~2 条线), 最后一辆
  16:18:30 结束后 3 秒整局就被停掉(只录到 392 s), 而对局还在打。
  现在**只认三条回车库信号**: ① **8111 断开**(从战局回车库时 8111 会断一下, 最可靠);
  ② 地图变成占位 "?" 图; ③ 连续拿不到地图图片。场上没车时只写一行日志提醒,
  录制继续等你重生。
- **三档轮询率拆开**(菜单「设置 → 轮询间隔」): **单条录制** / **全局录制** / **hudmsg**
  各自独立可调(默认 40 ms / 100 ms / 2000 ms, 见下面“默认轮询率调整”)。主循环频率**跟着当前在录的那种走**
  (全局录制时就是全局那个值 —— 叠加层/状态栏显示的就是它, 设 10 Hz 就是真的 10 Hz);
  两者互斥, 不互相干扰。
  信息区右侧只留一个极小的灰色只读文字, 显示**实际轮询频率**(如 `轮询 24 Hz`)。
  录制/回放期间这些菜单项同样被禁用。
- **hudmsg 改按 8111 网页自己的节奏抓(修 “怎么都修不好的漏采”)**: 以前 15 秒读一次
  增量, 结果西奈半岛那局一局只采到 11 条击毁、全挤在最后 75 秒 —— `/hudmsg` 的
  `damage` 是**滚动窗口**, 交火期每秒好几条(击毁 + 引燃 + 嘉奖 + 坠毁), 15 秒的量
  早就被挤掉了。现在**照抄 8111 首页内联脚本的行为**:
  `setInterval(updateSlow, 500)` → 每 **0.5 秒**一次, 参数是
  `/hudmsg?lastEvt=<lastEvtMsgId>&lastDmg=<lastDmgMsgId>`, 回来后把两个游标各自推到
  “最后一条的 id”。黑名单程序的同类轮询也从 3 秒改回每 tick 一次。
- **全局录制的采样与存储重做**: “从 8111 拉多少数据就存多少数据, 静止的只存坐标 + 时长”。
  - 移动段**逐帧全存**(跟随轮询间隔, 默认 40 ms), 不再 5 Hz 抽稀 —— 转弯的细节不再丢;
  - 静止段折叠成 **一个点 + `hold`(静止持续时长)**: 一棵不动的高炮蹲 20 分钟也只占
    1 个点(以前是每 15 秒一个心跳点), 而线尾时刻更准;
  - 落盘格式 `[t, x, y, speed]`, 静止点才会多第五个数 `hold` → **旧数据完全兼容**;
  - 回放取点尊重静止段(`point_at`), 阵亡叉/变暗、偏移拟合、“这一段里有几次阵亡”
    全部改用有效结束时刻(末点 + hold)。
- **默认轮询率调整**: **全局录制 → 100 ms(10 Hz)**(整场走位够用, 请求量减半),
  **hudmsg → 2000 ms**; 单条录制仍是 40 ms。⚠ hudmsg 放到 2 秒有风险 ——
  8111 网页自己用 500 ms, `damage` 是滚动窗口, 交火密集时会丢击毁记录;
  需要准确阵亡时间时请调回 500 ms。设置增加了版本号(`SETTINGS_VERSION = 2`),
  升级后旧存档里的两个间隔会被清掉一次, 避免旧值盖住新默认。
- **播放控制栏换成文字图标**: `▶ 回放` / `‖ 暂停` / `» 到下一标记暂停`,
  与旁边的“结束播放”风格统一(以前是 emoji 图标)。
- **空中视角(直升机/无人机/固定翼)下不再误判“已回车库”**: 8111 在空中的坐标系与地面
  **不是同一套** —— 实测图框范围是 ±65536(131072 m)而不是地面的 4096, 归一化坐标会
  跑到 0~1 之外, 以前的“坐标越界 = 不在图里 = 回库”规则会误判。现在录制器带
  `air_view` 标记 + `_frame_fit()` 换算(逆向拟合出 `scale=32, origin=(-16,-15)`),
  越界不再当成回库。
- **A/B 队录制标记不再持久化**: 它只是“下次点录制录到哪一条”的临时指向,
  关掉软件就该忘掉(以前会写进 `routes.json`, 第二天点录制会莫名其妙录到旧条目上)。
  旧文件里的标记读入时一律忽略。
- **静止的车, 线尾比真实消失早最多 15 秒**(修): 采样只在移动时存点、静止时每 15 秒
  补一个心跳点, 收尾时又只在“位置变了”才补终点 —— 于是一直停着的车(防空车、
  部署好的发射车)线尾停在最后一次心跳上。实测西奈半岛那局两台**同时**被毁的发射车
  分别结束在 307.5s 和 316.6s, 差 9 秒就是这么来的。现在由上面的 `hold` 收尾到
  “最后一帧见到它的时刻”, 需要补点时(它最后还在动)才补。
- **hudmsg 采集的诊断日志**: 有新增时才记一行(几条消息 / 其中阵亡几条 / 游标推进到哪),
  发现 id 跳跃(>60)时告警“滚动窗口已滚过, 中间的阵亡会丢”。
  死亡时刻修正里“这一段没有他的阵亡”也会带上“本局共采到 N 条击毁消息”, 便于判断
  是数据没采全还是他真的没死。
- **侧栏与悬停显示线路编号(A2 / B13)**: 全局录制里一辆车一局可能有几条命, 侧栏原来的
  `15:32:10  型号` 看不出“这条是第几次出击”。现在每条命有一个稳定短编号
  (队号 + 序号, 如 `A27`), 侧栏、悬停提示、播放时的队伍信息都用它;
  放在这一级是因为“跨局复盘时靠编号互相引用线路”比靠时间更好用。
- **线路编号 + 回放总长按 `hold` 算**: 见上条与下面“静止的车线尾”那条 ——
  静止段的 `hold` 现在参与回放总时长、阵亡判定与偏移拟合。
- **分体防空(雷达车 + 发射车)**: 8111 会把同一玩家的每台车各上报一份(`Player` / `Radar` /
  `SAM`, 颜色都是“自己黄”), 所以三条线**各自录制、各自判死、各画一个叉**(实测 2026-10-23:
  雷达车被 AGM-88A 打掉时, 两台发射车在同一帧一起消失)。
  - 侧栏名字改用**第一个非 `Player` 的类别**(否则三条线全叫 “Player”, 分不清雷达车);
  - 死亡时刻修正只针对**最外层那条**(摄像机挂着的那台, 它阵亡后不消失、线会拖到录制结束);
    被它包住的发射车那几条本来就死得准, 不再当成“额外的命”(否则会算成“阵亡 3 次”)。
- **A/B 两队的战区颜色统一了**: 8111 的颜色是“站在观战者视角”的, A、B 是两次观战、
  视角相反 —— 以前两段快照混在一条时间轴上, 回放时同一个战区的颜色一会儿蓝一会儿红。
  现在时间轴每条都记下**是哪一次观战录的**(`side`), 回放取同一次观战的那批, 再按
  “两队各自重生点的颜色”重映射(`zones.decode_capture` 反解出
  `(端点, 端点, 进度)` 后用新调色板重算, 进度比例不变)。旧数据没有 `side` → 不动颜色。
- **战区占领动画改对了**: 8111 给战区的 `color` 不是“三种归属色”, 而是游戏自己算好的
  **占领进度混色**(中立白 → 蓝 / 白 → 红, 中途如 `#587EFD`、`#fc7E76`)。以前先归成
  蓝/红/白三档再上固定色, 进度全丢, 而且中途混色会被判成“中立”, 颜色会乱跳。
  现在**直接用 8111 的原色**, 于是“争夺时进度回落”“易手时先清空旧进度再涨新进度”
  “防守方在场时不动”这些规则自动就对了(游戏已经把结果算进颜色里)。
  另外 `zone_states` 的变化判据加了量化颜色, 回放也能看到进度在动。
- **放大到最大时满屏方块**: 底图只有一个分辨率, 双线性放大到 6~20 倍时, JPEG 里逐像素的
  噪点(草地最明显)被放大成一个个方块。现在按“每个源像素放大成几个屏幕像素”分档:
  < 2.5 倍用原图, 2.5~14 倍用降采样 2 倍的版本, ≥ 14 倍用降采样 3 倍的版本(盒式低通,
  噪点被平均掉)。档位图在换图时一次性建好, 稳态帧时间反而从 3.4 ms 降到 1.7~2.3 ms。
  对比工具: `tools/probe_map_quality.py`、`tools/probe_map_upscale.py`。
  (起初用的是“6 倍以上降 4 倍”, 实机看下来太糊 —— 2048² 地图 + 1264×720 窗口时满格
  实际只有 7 倍, 清晰度掉近一半; 已改成上面这组阈值。)
- **GPU 画布上“已阵亡”没算 `hold`(修)**: 线消失的时刻取的是**最后一个点的 `t`**,
  而静止段被折叠成“一个点 + 时长”, 于是那一段被整个漏掉 —— 实测 A19 那条线的
  阵亡叉**提前 12.4 秒**出现, 播放到那里线就整条消失。现在与软件渲染共用
  `_dead_now(rec, head)`(末点 + `hold` 才是有效结束时刻)。
- **最后一辆车被打死时漏标被击毁(`dead=0`)(修)**: `alive` 数的是**坐标换算后**仍在
  图框内的单位, 而空中/越界的 AI 防空会被 `_align` 过滤掉 —— 一局收尾时若只剩几台
  越界防空, `alive` 就成了 0, 于是“全场清空”被当成“视角切换”, 死亡标记不写。
  现在改用**换算前**的单位数(`reported`)。
- **切换坐标系后战区/重生点没跟着换算(修)**: 用户反馈“正播放着路线, 战区长腿跑了”——
  轨迹点已按 `_frame_fit()` 换算到录制开始时的地面坐标系, 而战区/重生点还是原始坐标,
  一遇空中视角就整体偏移。现在三者走同一套换算。

## 跑图线路测试器 v1.1.1(2026-10-22)

### 修复

- **回放中“所有路线卡一下”**: 战区状态混在轨迹层的内容指纹里, 于是每次占领/易手都
  把全部线路的几何重算一遍 —— 实测 67 条线 **239 ms/次**, 一局发生 9 次(用户报
  “播放中偶尔整片线路卡一下, 像是某条线的玩家阵亡要隐藏导致的”)。
  实测排除“死亡隐藏线路”(那一步只多 0.3~2 ms); 真正的原因是战区快照每帧都变。
  现在指纹拆成 **轨迹 / 图标 / 战区** 三级, 战区变化只换那几面菱形旗(亚毫秒):
  整层重建 9 次 → **0 次**, 单帧最慢 239 ms → **7.75 ms**, 平均 3.76 → 2.80 ms。
  核对工具: `tools/probe_playback_stutter.py`(逐帧把同步与提交分开计时)。

- **阵亡时刻修正**: 用 `/hudmsg` 的击毁记录把“摄像机挂着那位玩家”的真实阵亡时刻补回来
  (其余玩家 icon 正常消失, 判死本来就准)。一条命一条线, 一局死几次就修几条;
  候选名单里 ★ = 每一条命都对上, ✔ = 能修其中几段, 灰 = 对不上。

  (A/B 两次观战颜色是反的, 不能再写死 A 蓝 B 红)。
- **录制叠加层**: 录制时显示实际采样率、轮询频率、点数、标记数(菜单「设置 → 叠加层」)。
- **`/hudmsg` 边录边取**: 每 15 秒取一次增量, 避免环形缓冲区把前几分钟的击杀挤掉;
  同时识别两种阵亡文本(`击毁了` / `已被摧毁` = 弃车、淹死、坠毁)。
- **转弯半径**改为整数米 + `±x%` 一致度; **全局线路存储**改紧凑 JSON + gzip(716 KB → 100 KB 级)。
- **性能与内存**: 修复缩放/换图时场景对象累积(重生方块叠成一堆同心方框);
  重建图标只换图标层; 悬停命中改 numpy 批量; 缓存按“画面上还存在的线路”剪枝。

### 修复

- **全局线路的速度配色与单条轨迹不一致**: 原先全局线路固定以 120 km/h 为基准
  (看起来偏藍), 现改成与单条轨迹完全同一套规则(基准 = 这条线自己的最高速),
  同样的速度就是同样的颜色。
- **眼睛开关可能“一点就全灭”**: 重录/删除后 `_visible_lives` 里可能残留已不存在的
  线路 id, 导致“这一层当前亮不亮”的判断全错。现在每次刷新都会剪掉失效 id,
  开关只认真实存在的线路, 状态栏还会写明到底切换了哪一层(如“已隐藏「A 队」 15 条…”)。
- **全局录制时刷新率掉到 8Hz / 滚轮缩放卡顿**: "边录边画"最初每帧都把全部线路重画一遍
  (240 ms/帧)→ 改成**累加层**(每帧只补新段, 3.5 ms/帧); 缩放时先把旧图层按比例贴上去
  (270 ms → 5 ms), 停手 200ms 后再重建。
- **录制结束时反复报错弹窗**: `AttributeError: 'UnitLife' object has no attribute
  'zone_signature'` —— 选战区布局时没跳过全局线路, 每帧都抛一次。已用 `getattr` 兜住。
- **回放全局线路会崩**: 回放光标要读点的朝向, 而全局点没有 `dx/dy`,
  `point_at()` 已兼容。
- **不播放时滚轮缩放也卡**: 轨迹层的内容指纹里含了几何指纹, 于是**每滚一格**都要把
  全部轨迹重新栅格化(1920×1040 / 20 条线要 25~37ms, 连滚 6 格 245ms)。现在把内容与
  几何拆开 —— 缩放/改窗口时先把旧层**按比例贴上去**(1~2ms), 停手 200ms 后再重建一次;
  余量的容忍范围按缩放比放大(否则放大中途锚点一漂就重建), 离屏图回收复用。
  实测单格 6~10ms, 连滚 6 格 105ms。
  顺带修正了按比例贴图的偏移(`p.scale()` 会多出 `(余量+锚点)×(scale-1)`,
  放大 2 倍能偏两百多像素)与“改窗口后余量算错”的问题。
- **全局录制中途“线路突然断开、换个地方继续画”**: 观战中的玩家上了固定翼时, 8111 会把
  地图切成空战图, 同一批地面单位的坐标**整体被缩放 1/16 并平移** —— 帧间最近邻全部
  脱靶, 正在录的线就断了。现在用**静态地物(重生点/战区)当锚点**每帧反解相似变换,
  把坐标换算回录制开始时的地面坐标系(实测反解精确到 1e-5:
  `空战 = (陆战 + (8,7)) / 16`); 换算期间速度仍按地面图的边长算;
  换视角后的 5 秒内不判“被击毁”(那几秒消失更可能是看不见了)。
  坐标系一变还会写一行**交叉校验日志**, 把拟合尺度与 `/map_info.json` 的图框比对照
  (实测 `图框 65536/4096 = 16.0000× → 与拟合一致(差 0.00%)`)。
  核对工具: `tools/probe_frame_align.py`。
- **回放中途缩放后, 着色段画到一半就不再增长**(只有再缩放一下才显示):
  “几何变了就先按比例贴旧层”这套做法里, `_note_geom_change()` 被每帧调用
  (重建之前“当前几何 != 建层几何”每帧都成立), 而它会刷新“最后一次几何变化”的
  时间戳 —— 于是 `_geom_settle()` 永远以为“刚刚还在缩放”, 无限推迟重建, 画面就
  永远停在按比例贴的旧图上。现在只在几何**再一次真的变了**时才刷新时间戳。

### 新增

- **回放新增两个“被击毁”显示选项(默认勾选)**:
