# 赛道检查点(计时门) —— 可行性与设计草案

> **状态: 想法, 未实现**(用户 2026-11-10 提出, 先记录, 暂不写代码)。
> **结论: 可行** —— 不需要任何新的数据来源, 现有 `RoutePoint` 序列就够; 难点全在
> 判定口径与编辑界面, 不在数据。

## 1. 想解决什么

在同一张图上定义一条"赛道"(= 一串有序的检查点), 然后**自动**算出每辆车:

- 每个检查点的通过时刻;
- 每段的耗时与区间平均速度;
- 整条赛道总时间。

用途: 比较不同载具的机动性 —— 直线加速、过弯、越障、绕圈, 都能给出一组可直接排序的数字。

**现状的差距**: 只能用 `F7` 手动打标记。人没法在游戏里精确地"压着某个位置"按一下, 两次
录制之间标记点会差好几米, 于是同一段路的耗时没法直接比较。

## 2. 数据够不够 —— 够

| 来源 | 有什么 | 采样 |
|---|---|---|
| 单条录制 | 归一化 `0~1` 坐标 + `t` + `speed` + 朝向 | 默认 25 Hz(40 ms); 40 km/h 时点距 ≈0.44 m |
| 回放导入 | `UnitLife.points`, 同一套归一化坐标 + `t` | 服务器回放 24 Hz; 本地回放对未被看见的单位 ≈2 Hz |

判定用**线段与区域求交**, 不是"点落在区域里就算" —— 只要相邻两点跨过边界就能算出穿过时刻,
用线段做**线性插值**。所以：

- **不漏判**: 门再窄也不会被跳过(点和点之间的距离再大, 线段一定穿过门);
- **精度与点距有关但不是决定性的**: 24 Hz 时插值误差 ≈ 半个点距(40 km/h → ~0.2 m);
  2 Hz 的本地回放相邻点可能差 15 m, 这时误差明显 —— 结果表里要标注来源与采样率。

## 3. 形状

两种就够(再加一个可选的"方向"约束):

### 3.1 圆

- 存: 圆心(归一化 `0~1`) + **半径(米)**
- 判定: 线段 `A→B` 与圆求交, 取最早的进入时刻; 特殊处理"两点都在圆内"(停在圈里再动)
  → 只算进入那一次
- 典型用法: 路口、某个点位(半径 15~30 m)

### 3.2 矩形

- 存: 中心(归一化) + 宽/高(米) + 旋转角, 或直接 4 个角
- 判定: 线段与 4 条边求交, 取最早进入点; 要处理"起点已经在矩形内"
- 典型用法: 起跑线(细长条)、越障区、一段区域

### 3.3 可选: 方向约束

门可以带"允许通过方向 ± 容差角", 防止车在门口来回蹭被重复计次。不带方向时取**第一次**通过。

### 3.4 一个门只算一次

计时赛语义: 每个门只取首次通过。要多圈就复制一条赛道(或以后加"圈数")。

## 4. 计时口径(最容易出分歧的地方)

- **0 点必须由赛道自己定**: 现在单条录制的 `t=0` 是"按 F5"或"速度从零变化"
  (`以速度从零变化时刻作为起始时间点`), 两次录制不可能对齐 → 赛道模式要有**起点门**,
  以"首次穿过起点门"为 0 点;
- 输出: 每门时刻 → 每段耗时 → 累计耗时; 区间平均速度用**门的间距 / 段耗时**;
  最高速度取该段的 `speed` 序列最大值;
- 缺门(没穿过)记为 `—`; 只有**全部门都通过**的线路才进排名表(可以另设"允许缺 1 门")。

## 5. 在现有代码里的落点

| 部分 | 放在哪 | 说明 |
|---|---|---|
| 判定算法 | 新模块 `wt81111g/route_track.py` | `Checkpoint` / `Track` / `pass_times(points)`; 纯几何, 好写单测 |
| 存储 | 跟"地图 + 模式"一起存 | 和战区/重生点同一层(`RouteStore` 加 `tracks`), 或在会话文件里加新 `kind` |
| 画门 | `wt81111g/route_map_view.py` 加一层 | 圆/矩形 + 序号; 编辑态给拖拽/缩放手柄(注意要先破 GPU 那套批量绘制, 门只有几个, 走即时绘制最省事) |
| 编辑界面 | 菜单「工具 → 赛道检查点…」 | 列表(排序、改半径、删除) + "在地图上新画一个" + 保存为命名赛道 |
| 结果表 | 侧栏选中多条线路 + 选一条赛道 → 弹表格 | 行 = 线路(载具/来源), 列 = 门; 可导出 CSV |

## 6. 工作量与建议顺序

1. **只读版先跑通**(推荐): 手写一个 JSON 门列表(先不做编辑界面), 把"判定 + 结果表"做出来,
   拿现有录制验证数字合不合理 —— 约 150 行;
2. 再做地图上画门/拖动 —— 约 300 行(这块最费时间, 与 GPU 绘制层打交道);
3. 最后做导出 CSV / 排名 —— 约 150 行。

## 7. 坑

- **车辆尺寸**: 只用**中心点**判定, 不把车宽算进去; 想"压线即过"就把门做粗一点;
- **半径用米, 不用像素**: 归一化坐标要靠 `map_calib`(`map_min`/`map_max`)换算成米,
  否则"10 像素的门"在不同分辨率/不同地图上含义完全不同;
- **坐标系必须与线路一致**: 回放导入的点已经过校准(`FrameAligner` / `map_calib`),
  门要存在同一套坐标下, 换图/换分辨率不能错位;
- **低采样率的诚实标注**: 2 Hz 的本地回放算出来的段耗时要标"低精度", 不要和 24 Hz 的混在一起排名;
- **录制期间不能编辑**(沿用现有"录制中锁定界面"的规矩)。

## 8. 与已有功能的关系

- 手动标记(`F7`)保留: 临时测一个点仍然比画门快;
- 赛道的"门"和现有的「战区/重生点」绘制是**同一类地图标注**, 可以共用图层与显示开关;
- 如果以后真的能拿到回放里的地形(见 `录像解析调研.md` §2.8), 赛道还能顺便标出坡度 ——
  但那是另一件事, 不影响本设想的可行性。
