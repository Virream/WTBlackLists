# 跑图线路测试器 —— 功能与实现文档

> 独立程序, 入口 `route_tester.py`, 与黑名单助手(WBBlackList 主程序)相互独立, 可单独运行。
> 依赖: PyQt6(项目既有依赖), **无需任何额外第三方库**。

---

## 1. 用途

记录"**重生后到达某些位置花了多少时间**": 在地图上绘制起点、实时轨迹、途经标记与终点,
并直接标注每段用时(如 `00:30` / `01:37`), 用于跑图线路的计时与对比。

---

## 2. 界面布局(左 / 右 / 下 三部分)

```
┌──────────────────────────────────────────────┐
│  菜单栏: 地图(地图管理/缓存目录)   帮助        │
├──────────┬───────────────────────────────────┤
│          │                                   │
│  侧栏    │           地图显示区              │
│ (与窗口  │   (右上角向下、向左延伸,          │
│  同高)   │    左边框贴侧栏, 下边框贴信息区)   │
│          │                                   │
│  两级    ├───────────────────────────────────┤
│  树形    │           信息显示区              │
└──────────┴───────────────────────────────────┘
```

- **侧栏**(全高): 列 = **展开/收起 / 地图·线路 / 信息**。层级 = 地图名 → **模式** → **版本** → 线路记录
  (模式由 8111 的战区数量推出, 版本就是**战区位置**; 见 §6.5)。
  - 线路条目文本 = `创建时间  载具名`(用时在“信息”列里);
  - **外观**(见 `wt81111g/tree_view.py`): **不用交替行底色**(条纹与层级无关, 四层看起来就是一片灰白相间),
    改成**统一背景 + 每层一条竖直引导线**(像 VS Code 侧栏), 层级一眼能看出;
  - **表头第 0 列写“展开/收起”**: 分组行那里是展开箭头, 线路行那里是眼睛图标;
    第 2 列写“信息”: 分组行 = 该组有几条, 线路行 = 用时, 只有缓存图片的地图 = “仅缓存”;
  - **启动时默认全部折叠**(只列出一排地图名), 想看哪张再自己展开;
  - **之后就按你的操作来**: 侧栏重建("地图管理"关掉、录完一条轨迹、改名、删除、
    新增地图/版本)后, 你展开过的保持展开、折起来的保持折叠; 新出现的分组默认展开,
    **刚录完的那条会自动展开到它**(不然它藏在折叠的分组里看不到)。
    以前每次重建都硬编码全展开 —— 折好的层级会被打乱;
  - 眼睛列宽 = 缩进×4 + 图标 + 间距: 缩进会占用第 0 列, 列宽不够时 Qt 会把图标
    裁掉或压到名称列的文字上(见 `EYE_COLUMN_WIDTH` 注释与回归测试);
  - **眼睛图标 = 地图上是否显示该轨迹**: 点一下显示、再点一下隐藏
    (点亮=显示中, 淡化带斜杠=已隐藏); 可同时点亮多条用于对比跑法, 但**只能同一版本
    (同一张图 + 同一战区布局)** —— 不同交战区域的线路本来不可比, 点亮其它版本的
    轨迹时, 之前点亮的会自动隐掉(见 §6.5);
    地图/模式行右键有“显示本图全部轨迹 / 隐藏全部轨迹”(实际只显示其中最新那个版本),
    版本行右键有“显示/隐藏本版本全部轨迹”, 线路条目右键有“在地图上显示 / 从地图上隐藏”;
  - **选中(Shift/Ctrl 多选) = 回放播哪几条**(见下文): 选中一条就播一条, 选中多条就播多条。
    **选中只影响回放, 不会把轨迹显示到地图上** —— 显示始终只由眼睛决定;
  - **双击某条线路 = 把它所在的版本定为“基准” + 把它显示到地图上 + 把底图切到它的地图**:
    之后 Ctrl/Shift 多选**锁死在该版本内**, 点到其它版本会被弹回(状态栏会提示);
    双击其它版本的线路就换成新基准; **基准版本那一行前面会有一个图钉图标**(提示基准在哪),
    信息区回放那一栏显示 `基准 地图 · 模式 · 版本 | 待回放 N 条`;
  - 刚打开软件/还没定过基准时: **第一个点到的线路就把它的版本定为基准**
    (清空选中不会取消基准, 图钉还在, 方便接着多选);
  - 线路条目右键可删除; 新增条目不在此侧栏操作 —— 由"结束录制"自动写入。
- **地图区**: 显示地图图片(游戏里实时取, 关掉游戏后来自本地缓存),
  并绘制玩家位置、轨迹、标记与时间。切换显示的轨迹/回放时**地图会自动切成那张图**。
- **信息区**(固定高 172px, **顶部为轨迹回放, 用分割线隔开**):

| 行 | 内容 |
|---|---|
| 0 | **轨迹回放**: 回放/暂停、到下一标记暂停、倍速、回放进度 |
| 1 | ──────── **分割线** ──────── |
| 2 | 连接状态 + 采样间隔设置 |
| 3 | 载具型号 / 速度 / 计时器 / 已标记数 |
| 4 | 三个录制按钮(带**绿圈 / 红圈 / 黄圈**图标, 与地图上的起点/终点/标记圈同色同比例) + **“以速度从零变化时刻作为起始时间点”选项** |

> **界面上不放常驻提示文字**(早期在侧栏底部与信息区右侧写过“点眼睛显示/隐藏”“快捷键是…”,
> 用过一次就是纯粹的占地方) —— 这些说明全部收进菜单 **「帮助 → 关于 / 功能说明…」**
> (正文在 `wt81111g/help_text.py`, 快捷键、界面用法、录制/回放规则、地图与战区、数据位置都在那里)。

## 3. 使用流程

1. 启动游戏, **进入对局或试车场**(机库中无地图与玩家坐标);
2. 运行 `python route_tester.py`;
3. `F5` **开始录制轨迹** → 播放提示音, 地图上在玩家当前位置画**绿色起点圈**, 开始计时;
4. 驾驶载具跑图 → 地图**实时绘制轨迹**(按速度着色: 慢=蓝, 快=红), 信息区实时显示速度;
5. 途中按 `F7` **标记当前位置** → 画**黄色圈**并在旁边标注时间(如 `00:30`, 可多次标记);
6. 到达终点后按 `F6` **结束录制轨迹** → 在当前位置画**红色终点圈** + 总用时(如 `01:37`);
   (默认键只是默认值, 菜单 **「快捷键」** 里随便改, 见 §4)
7. 该次录制自动保存到侧栏对应地图下, 且**自动点亮它的眼睛**(仍显示在地图上);
   没选中任何条目时它就是“高亮层”(用速度配色画), 之后可随时点击回放按钮回放
   (回放对象见下文“轨迹回放”)。

**录制期间其余功能被锁定**: 侧栏(含眼睛/选中/右键菜单)、回放按钮与倍速、采样间隔、
“等移动再定起点”选项、菜单里的「地图管理」「用缓存底图重新显示当前轨迹」全部禁用,
防止录制时误触预览 —— 主界面和录制功能会“打架”(看着这张图、录的是另一张)。
若开始录制时你正在预览**另一张地图/另一个版本**的轨迹, 程序会:

1. 把主界面**切回游戏当前地图**(实时图 / 本地缓存图);
2. 清掉之前预览点亮的所有轨迹(录制期间只显示正在录的这条);
3. 状态栏补一行“已切回游戏当前地图并暂停预览(录制期间其余功能已锁定)”。

### 可选: 以速度从零变化时刻作为起始时间点

“开始录制轨迹”右侧有一个复选框。**这是非默认开启的功能**: 每次启动都是未勾选状态
(选项只对本次运行有效, 不写入配置), 需要时手动勾上。勾选后,**不再按“按下按钮的时刻”计时**:

```
按下开始录制 ──── 还在静止, 不计时 ────┐
                                      ↓ 速度首次不为 0
                         回溯: 找最近一次速度为 0 的时刻 ← 这就是计时起点
```

适合这种用法: **用界面按钮开始录制 → 切回游戏窗口 → 再起步**。
切窗口、动画、按键反应这一段时间不会被算进成绩, 计时起点≈实际起步的那一帧。

细则:

| 情况 | 行为 |
|---|---|
| 按下后速度一直为 0 | 状态栏显示**“准备录制… 等待载具移动”**, 不计时; 起点圈也还没画 |
| 速度首次不为 0 | 在**最近 1.5 秒**的采样里从后往前找最近一次速度为 0 的时刻 → 该时刻的**位置**作为起点、该时刻作为 `t=0` |
| 起点之后的位移帧 | **补录进轨迹**(最多回溯窗口内的几帧), 不会丢掉起步那一下的线条 |
| 按下时车已在行驶(窗口内没有速度为 0) | 退化为“按按下时刻计时”, 并提示“回溯窗口内没有速度为 0 的时刻” |
| 等待期间按“标记当前位置” | 不可用(还没定下起点, 标记无意义) |
| 等待期间按“结束录制” | 视为**取消**: 该次录制作废, **不写入侧栏、不落盘** |

为什么回溯窗口取 **1.5 秒**: 只需覆盖“按下按钮”与“车真正起步”之间的几十毫秒~几秒延迟;
窗口太长会把起点拉到很久以前(比如点击时已在行驶, 会把几秒前的静止误当起点)。

实现位置: `wt81111g/route_recorder.py`
(`request_start(start_on_move=…)` → `_do_start` → `_arm_check` → `_begin_recording`),
选项开关通过命令队列传给轮询线程, 不共享可变状态。

### 地图缓存(关掉游戏也能看回放)与「地图管理」

8111 的 `/map.img` **只有游戏在运行时才拿得到**, 所以程序会把地图图片缓到本地:

- 每次发现**新地图**就写一份到 `<data>/maps/<哈希>.<ext>`;
- **同一张图只存一次**(键相同直接跳过, 不重复写盘);
- 战局外那个 `"?"` 占位图**不入缓存**(它不是地图);
- 显示/回放某条轨迹时, **地图自动切成这条轨迹所属的那张图**:
  - 游戏在跑 → 直接就是 8111 的实时图;
  - 游戏关了/不在战局 → 从缓存读;缓存也没有则提示“进一次该地图就会自动缓存”。

#### 地图身份: 为什么不能只看“图片哈希”(2026-10-09 修的 bug)

用户反馈“同一张地图同一模式录了几次, 侧栏里出现了两张一样的地图”: 缓存里
`372ce29b0767.jpg`(2048×2048) 与 `0fc34e933121.jpg`(1024×1024) 其实是**同一张图**。

原因: 8111 **会把同一张地图以不同分辨率发过来**(实测见到过 1024²/2048²/4096²)。
而且**客户端没法指定分辨率**(逐项实测: 在 `/map.img` 上加 `?size=`/`?w=`/`?zoom=`/`?type=`
全都返回同一张图; 官方页面的 `?gen=<地图代数>` 只是个防缓存参数, 它自己的放大缩小纯粹是
canvas 端的 `map_scale`) ⇒ 分辨率由**游戏侧的缩略图纹理代数**决定。
早期地图身份 = **图片字节的 sha1**, 分辨率一变字节就变、哈希就变 → 同一张图被当成两张,
侧栏/缓存/战区布局/名字全部分开; 中途换分辨率还会被当成“换图”而清理预览。

现在的判定(与分辨率无关), **三道闸全过才算同一张地图**:

| 闸 | 指标 | 阈值 | 实测“同图”侧 | 实测“不同图”侧 |
|---|---|---|---|---|
| ① 灰度 | 缩到 **64×64 灰度**后的平均差 | ≤ **1.2** | ≤ **0.60** | ≥ **2.91 / 11.97** |
| ② **结构**(主力) | 同尺度 dHash 的汉明距离(共 4032 位) | ≤ **800** | ≤ **372** | ≥ **1776** |
| ③ 最近邻余量 | 次近的那张的距离 ≥ 2×阈值(=2.4) | — | — | 两张都很像时一律不认 |

实测样本(`tools/map_similarity.py` 可随时重跑, 样本随你见过的地图自动变大):

| 对比 | 份数/对数 | 灰度 | 汉明 |
|---|---|---|---|
| **同图**: 0.25/0.5/0.75/1.0 倍率 × JPEG q60~95 | 135 份 | 最大 **0.60** | 最大 **372** |
| **不同图**: 9 张真实地图两两对比 | 36 对 | 最小 **11.97** | 最小 **1813** |
| **最坏情况**: 同一张 4096² 大地图的 12 个不同区域裁切 | 66 对 | 最小 **2.91** ✗ | 最小 **1776** |

为什么必须有 ② 结构哈希: 第三个场景(同一张大地图的不同局部, 也就是“小地图/大地图”那种)
灰度上可以非常接近(2.91 已经贴上闸门), **但纹理位置完全不同** → 汉明距离 1776 稳稳拦住。
只靠灰度会被它骗过 —— 这也是把灰度阈值从最初的 4.0 收到 1.2、并加 dHash 的原因。
反过来, 同图即使被压到 1/4 分辨率 + q60 重压, 汉明也只有 372, 仍有 2.2 倍余量。

> 两道闸在实测样本里**各自都能把两个群体分开**(各约 2 倍余量), 而且要误判必须**两个指标
> 同时**越界 —— 因此“把两张不同地图认成一张”的风险很低; 万一真发生, 后果也很轻:
> 它们只合成一条地图(轨迹仍按“战区指纹”分版本), 且合并前 `routes.json` 已备份成 `.bak`。

#### 历史重复条目的自动合并

老版本已经写下的“同图两键”不会被新逻辑自动消掉, 因此**启动时会跑一次合并**:

1. 给缓存目录里没有指纹的图片补算指纹(写进 `maps/index.json`, **只算一次**);
2. 按上面的三道闸分组, 组内多于一个键时**合并**;
3. 保留哪个键: 优先**有轨迹记录的**, 其次**用户起过名字的**, 再其次**分辨率高的**,
   最后取先缓存的(所以“货运港口(3 条, 有名字)”会赢过“地图 10(1 条, 无名)”);
4. 合并内容: 轨迹的 `map_key`、`known_maps`、`map_names`、`map_zones`(按战区指纹去重)、
   `layout_names`, 并把多余那张图片删掉(分辨率更高的一方留在保留的键上);
5. **动手前先把 `routes.json` 备份成 `routes.json.bak`**; 侧栏会提示合并了哪张地图。

演练结果(用真实数据副本): `0fc34e933121 → 372ce29b0767`, 货运港口 3 条 → **4 条**,
地图条目 10 → 9, 缓存目录里 1024² 的那份被删掉、2048² 保留, 备份文件生成, 再跑一次无重复。

> 副产品: **地图分辨率变化不再算“换图”** —— 以前中途拿到另一分辨率的图, 底图会重载并
> 触发一次“换图清理”(清回放/清不相关轨迹); 现在键不变, 只是把底图换成新到的那张。
>
> 另一个副产品: **界面优先显示最清晰的那份**。8111 有时只发 1024²(而缓存里有 2048²),
> 以前会直接把模糊的那份画上去, 放大看细节时很明显; 现在 `MapCache.sharpest()` 会把
> 缓存里更清晰的那份拿出来用(只读图片头比像素数, 开销极小, 日志会写一行)。

**地图名**: 8111 **不提供地图名**(已逐端点实测: `map_info`/`mission`/官方页面都没有,
客户端日志与 Saves 里也搜不到, 详见 `docs/8111使用经验.md` §3.6), 因此:

- 默认显示为 `地图 1 / 地图 2 …`(按首次见到的顺序编号, 只缓存过图片的地图也占号);
- 菜单 **「地图」→「地图管理…」** 可以:预览缩略图、看到图片大小/轨迹数/首次缓存时间、
  在顶部**固定的「地图名称」输入框**里改名(回车即存, 表格本身不可就地编辑 ——
  以前双击单元格会弹出输入框并藏在缩略图下面)、删除选中的缓存图片、打开缓存文件夹;
- 名字存在 `routes.json` 的 `map_names` 里, 侧栏与已录制记录会同步显示新名字。

### 眼睛图标(显示 / 隐藏轨迹)

侧栏每一条线路前面都有一个**眼睛**图标:

| 图标 | 含义 |
|---|---|
| 亮色**眼睛** | 该轨迹**正在地图上显示** |
| 淡色**眼睛加斜杠** | 已隐藏 |

- 点一下显示 / 再点一下隐藏, 与条目本身的“选中”无关(因此不需要 Shift/Ctrl 多选);
- 点亮多条 → 多条轨迹同时画在地图上, 便于对比跑法;
- 侧栏重建(结束录制、重命名地图、删记录)后**眼睛状态保持不变**;
- 换地图 / 退出战局时, 不属于当前地图的轨迹会自动隐掉;
- **跨版本不能共显**: 点亮另一版本的轨迹时, 原版本的点亮自动熄灭 ——
  同一张图的不同交战区域(大地图/小地图)线路叠在一起看没有意义;
- 地图/模式行右键提供“显示本图全部轨迹 / 隐藏全部轨迹”。

图标素材来自开源图标库 **Lucide**(ISC 许可, 见 `assets/icons/LICENSE-lucide.txt`),
由 `tools/make_icons.py` 从官方 SVG 光栅化为黑描边 + 透明底的 PNG(`assets/icons/eye*.png`),
运行时用 `CompositionMode_SourceIn` **按当前调色板着色** —— 所以浅色/深色主题下都看得清。
只用 Qt 内建的 PNG 解码, 不依赖会被 `tools/trim_qt.py` 精简掉的 `qsvg` 插件;
资源缺失时会自动退化为 `QPainter` 现画的简笔眼睛(见 `wt81111g/icons.py`)。

## 4. 全局快捷键

| 功能 | 默认快捷键 |
|---|---|
| 开始录制轨迹 | `F5` |
| 结束录制轨迹 | `F6` |
| 标记当前位置 | `F7` |

默认值改过两次, 现在是 **F5 / F6 / F7 单键**:

1. 最早是 `Ctrl+Alt+…` 这类组合 —— 组合键在游戏里容易和游戏本身/输入法打架;
2. 后来改成 `右Shift + 小键盘 1/2/3` —— 用户实测**在游戏里按了没反应**(疑似键盘多键冲突:
   前进要一直按着 `W`, 再加修饰键 + 小键盘, 廉价键盘会丢键);
3. 现在默认 **F5 / F6 / F7**: 不带修饰键(不存在和 `W` 抢键盘矩阵的问题),
   且 **F5~F7 在游戏里默认没有功能**, 不会误触发游戏动作。

菜单 **「快捷键(&K)」** 里可以自由改:

| 菜单项 | 作用 |
|---|---|
| 快捷键设置… | 弹对话框, 每个动作一行(**修饰键下拉** + **按键下拉**), 改完立刻生效并存盘 |
| 同时使用按键轮询(可区分左右 Shift) | 勾选项, 控制下面那条**兜底通道**是否开启(默认开, 见下文“两条通道”) |
| 恢复默认快捷键(F5 / F6 / F7) | 一键改回默认 |

对话框里每行后面会显示当前绑定与状态: 绿色 `✓` = 系统热键注册成功;
橙色 `⚠ + 原因` = 这个键**被别的程序占用了**(比如某个软件已经注册了 `F5`), 此时只能靠轮询通道。

### 两条通道(任意一条命中即触发)

| 通道 | API | 特点 |
|---|---|---|
| **系统热键**(主) | `RegisterHotKey` + 隐藏消息窗(`WM_HOTKEY`) | 不靠定时器、不读按键状态, 由 Windows 直接通知; 游戏把主线程挤到几百毫秒一轮也不影响 |
| **按键轮询**(兜底) | `GetAsyncKeyState` 定时查询(20ms) | 能区分**左右 Shift** 这种精确组合(系统热键做不到); 可在菜单里关掉 |

两条通道可能同时命中同一个按键, 因此**同一动作 0.3 秒内会去重**, 不会触发两次。

轮询通道的实现要点(`wt81111g/global_hotkey.py`):

- 使用 Windows `user32.GetAsyncKeyState` 定时轮询(20ms), **零第三方依赖**;
- **可区分左右修饰键**(如"右 Shift");
- **不看"是否正好同时按住", 而看 `GetAsyncKeyState` 的最低位** ("自上次查询以来按过"):
  游戏把主线程/定时器挤得几百毫秒跑一次时, 这一位也不会丢, 所以不会"按了没反应"
  (旧写法只判"当前是否按住", 慢一次轮询就漏掉了 —— 这是 2026-10-07 修的问题);
- **按住不放只触发一次**, 松开(或再按一次)后才会再触发;
- **NumLock 兼容**: 小键盘键在 NumLock 关时退化为 `End/Down/PageDown` 等, 两种虚拟键码同时监听;
- 窗口无需保持焦点, 游戏全屏时也能触发; **不拦截按键**(游戏仍然收得到这个键)。

### 会不会影响反作弊?

不会踩到反作弊通常盯的那几类行为。本程序只用两条**官方的、只接收通知**的通道:
`RegisterHotKey`(系统热键) 与 `GetAsyncKeyState`(按键状态查询, 且可在菜单里关掉)。

| 本程序**不会**做的事 | 为什么重要 |
|---|---|
| `SetWindowsHookEx` 全局键盘钩子 | 这是“读你所有按键”的行为, 最容易被盯上 |
| `SendInput` / `keybd_event` 注入按键 | 模拟输入 = 外挂脚本的典型特征 |
| 打开/读写游戏进程内存、注入 DLL | 真·外挂行为 |
| 读写任何游戏文件/日志/存档 | 本项目的硬性约定(见 `copilot-instructions.md`) |

也就是说: 我们**不是游戏进程的一部分**, 只是“坐在旁边听那几个键”, 且**不拦截**。
唯一需要用户自己权衡的是: 因为不拦截, 绑的键在游戏里**会同时生效** ——
所以最好选游戏里没绑功能的键(默认 F5/F6/F7 就是), 或者把游戏里对应的绑定解掉。
另外可以在菜单里关掉「同时使用按键轮询」, 关掉后程序**完全不查询按键状态**, 只留系统热键。

### 其它

- **每次触发都会写进日志**(`data/route_tester.log` 里的"全局快捷键触发(系统热键|轮询): …"),
  万一还有按了没反应的情况, 先看日志即可区分"没收到按键"还是"收到了但动作被拒"。

每次触发都会播放**提示音**以便在游戏中凭听觉确认(`wt81111g/sound.py`):
开始 = `Speech On.wav`、结束 = `Speech Off.wav`、标记 = `Windows Balloon.wav`
(都是 Windows 自带音效, 在 `%SystemRoot%\Media`), 错误提示 = `Windows Critical Stop.wav`。
菜单「音效」可一键开关、调音量(0~100%)、给四个动作分别换本地 .wav(带试听)、恢复默认;
**音量是把样本按比例重采样后播放, 不改系统音量**(waveaudio 驱动不支持 MCI 设音量)。

## 5. 地图绘制规则(`wt81111g/route_map_view.py`)

| 元素 | 呈现 |
|---|---|
| 起点 | 绿色圆圈 + 圆心点(开始计时位置); **实时与已显示的轨迹都画** |
| 轨迹 | 折线, **按速度着色**(蓝→红), 悬停显示“哪条线 + 时间 + 速度” |
| 标记 | 黄色圆圈 + 旁边时间标签 `MM:SS` |
| 终点 | 红色圆圈 + 旁边总用时标签 `MM:SS` |
| 选中的历史轨迹 | **不透明**灰蓝折线(可同时显示多条, 便于对比多次跑图) || 回放未播放段 | **半透明**淡灰蓝(唯一使用半透明的地方) |
| 玩家当前位置 | 浅蓝色圆点 + 外圈 |

**透明度规则**: 轨迹一律**不透明** —— 半透明只用来表示回放中"**还没播放到**"的那一段。
多条选中轨迹叠在一起时也能看清各自的位置。
注意: 同时选中 **≥ 2 条**时不画时间标签(多条轨迹的同一标记位置标签会完全重叠、无法阅读),
只看单条时才显示标记/终点的时间。

坐标系: 8111 `map_obj.json` 的 `x/y` 为 **0~1 归一化值**, 控件把地图图片按原始宽高比等比
缩放居中(letterbox)后再映射为像素, 因此任意窗口尺寸下位置都准确。

### 地图交互(缩放 / 平移)

| 操作 | 效果 |
|---|---|
| **滚轮上/下** | 以鼠标位置为锚点 **放大 / 缩小**(1× ~ 20×; 1× = 适配窗口) |
| **按住鼠标中键拖拽** | **平移**地图(限制至少保留 40px 可见, 不会把地图拖丢) |
| **双击左键** | **复位**为适配窗口 |
| 鼠标悬停轨迹点 | 左下角浮层显示**是哪条线路**(录制时刻 + 车型 + 用时)与该点的**时间/速度** |

**悬停提示**(左下角浮层)细则:

- 命中范围: 鼠标到轨迹点的像素距离 **< 18px**; 在**所有当前显示中的轨迹**里取最近的那个点；
  “显示中的”= 回放时正在回放的那几条, 否则 = 眼睛点亮的 + 高亮层 + 正在录的那条;
  (早期只查“实时轨迹 / 第一条可见轨迹” —— 于是只剩刚录完那条有提示, 2026-10-07 修)
- 两行文本: 第一行 = 录制时刻 | **车型** | 用时(与侧栏条目一一对应),
  第二行 = 该点的 时间(毫秒) | 速度;
- 同时在命中点画**白环** —— 多条线路叠在一起时能确认读的是哪一条;
- 被悬停的那条被隐藏/删除/换图后, 提示立刻消失(不会留着别的线路的数据);
- 鼠标移出地图则提示消失。

实现要点:

- 视图以"**适配窗口**"为基准(`zoom=1` 时与未启用缩放时的行为完全一致);
- 缩放/平移只改变地图显示矩形, 轨迹、标记、玩家位置**共用同一套坐标映射**,
  因此缩放后位置依然准确;
- **底图缩放用平滑(双线性)滤波**: `QPainter.SmoothPixmapTransform` —— 放大后边缘不会
  再有台阶/马赛克。实测**开销可忽略**(整帧 1.72 → 1.49 ms; zoom 3/8/20 完全一样),
  因为被缩放的目标只有可见区域那一小块;
- **优先用最清晰的那份底图**: 8111 会按“地图代数”发 1024/2048/4096 三种分辨率,
  手上若有同一张地图更清晰的缓存, 就显示那一份(只读图片头比尺寸, 开销极小)。
  实测同一张图放大 8 倍看细节: 1024² 底图清晰度指标 2.69、2048² 为 3.73(+39%),
  肉眼差别明显(建筑轮廓/屋顶纹理);
- 滚轮缩放以鼠标位置为锚点(鼠标下的地图点保持不动), 便于对准细节;
- **切换地图时自动复位视图**(旧缩放对新地图无意义)。

### 绘制性能(多条线路同时显示时为什么不卡)

地图每帧都要重画, 而**重绘频率 = 采样间隔**(默认 40ms/25Hz)。
2026-10-08 用户反馈“选中 2 条还算流畅, 选 5 条卡得不得了”。实测(5 条真实线路共 3766 个点):
一次重绘 **41ms**(预算只有 40ms), 其中

1. 在 Python 里给每条轨迹重建"按速度分桶"的几何 ≈ **30ms**;
2. 逐段 `drawLines` 栅格化 ≈ 10ms;
3. 128 个重生方块逐个 `drawRect` ≈ 3ms。

拖动观察时更糟(**53ms/帧**): 平移以前算进"几何指纹", 每挪一下都要重算上面第 1 项。

#### 现在的机制

| 机制 | 内容 | 失效条件 |
|---|---|---|
| **归一化几何** | 分桶几何 / 灰色折线都以 **0~1 归一化坐标**缓存(按 `route_id + 点数`); 画的时候 `p.scale(地图边长)` + 线宽 `宽度/边长` | 只跟点数有关 → **缩放、平移、改窗口都不用重算** |
| **平移只动画笔** | `_to_px` 给"地图本地坐标"(不含平移), 绘制时 `p.translate(地图左上角)` | (永远有效) |
| **离屏层 + 余量偏移贴图** | 轨迹层(重生方块 + 轨迹 + 标记)渲进一张**比窗口大 35% 余量**的 `QImage`; 平移在余量内就直接 `drawImage` 偏移贴图 | 内容变 / 缩放 / 拖出余量 / 换图 |
| **回放累加层** | 未播放底衬 + 已播放的着色段画进一张图, 每帧**只补新播放到的段** | 往回拖拽 / 缩放 / 拖出余量 / 换回放对象 |
| **方块批绘 + 路径缓存** | 128 个重生方块按归属色合成 `QPainterPath`, 并按几何指纹缓存 | 缩放 / 改窗口 / 方块内容变 |
| **底图每帧直贴** | 地图图片不再单独缓存(缩放贴图本身只要零点几毫秒) | (永远有效) |

用 **`QImage` 而不是 `QPixmap`** 存缓存层: 同样是 ARGB32_Premultiplied, 但往 QPixmap 上
画在本机要慢一倍(实测 5 条线 21ms vs 12ms)。缓存层的缩放比取**画笔设备**的 DPR,
这样贴图是 1:1、不会被重采样。

战区**不进缓存层**(占领中要闪烁), 每帧现画 —— 只有几个菱形, 便宜;
玩家位置、悬停浮层同样每帧现画。

#### 实测(1000×700 窗口, 5 条真实线路, 含底图 / 128 个重生方块)

| 场景 | 改前 | 改后 |
|---|---|---|
| 预览(选中 5 条, 每个采样周期重绘) | 41 ms/帧 | **1.2 ms/帧** |
| **拖动观察**(每步平移几个像素) | 53 ms/帧 | **1.2 ms/帧** |
| 滚轮缩放(每一步都变 zoom) | 39 ms/帧 | **12~25 ms/帧**(2026-10-21 进一步降到 3~9 ms, 见下节) |
| 回放 1 条 | 8.3 ms/帧 | **2.2 ms/帧** |
| 回放 5 条同时 | 41 ms/帧 | **5.4 ms/帧** |
| 录制中(实时轨迹每帧增长) | ~10 ms/帧 | ~9 ms/帧 |

剩下的大头只有"重建缓存层"(12~25ms), 它只在缩放、轨迹集合变化、录制增长时发生;
拖动与静止都是 1ms 量级。

#### 缩放卡顿的最后一轮修(2026-10-21, 用户报"不播放时缩放也卡")

当时的实现里 `_tracks_key()` **含几何指纹**, 于是**每滚一格**都要把全部轨迹重新栅格化:

| 场景(1920×1040) | 改前 | 改后 |
|---|---|---|
| 滚轮缩放一档(10 条线) | 19~25 ms | **7~10 ms** |
| 滚轮缩放一档(20 条线, 1.7 万点) | 25~37 ms | **6~9 ms** |
| 连滚 6 格(20 条线) | 245 ms | **105 ms** |
| 缩放一档时**重建**轨迹层(一次性) | 20~50 ms | 20~50 ms(只在停手后发生) |

四个改法(都很小, 但每一个都有实测依据):

1. **几何变了不重建, 先按比例贴旧层**: 内容指纹与几何指绞拆开; 缩放/改窗口时把
   旧层按 `当前尺寸/建层尺寸` 贴上去(1~2ms), 停手 `GEOM_SETTLE_MS`(200ms) 后
   再重建一次变清晰。过渡帧略糊, 但位置分毫不差(见下一条)。
   ⚠ 这里有个坑: `_note_geom_change()` 是“当前几何 != 建层几何”就调进来的, 而重建
   之前这个条件**每帧都成立** —— 所以它只能在几何**再一次真的变了**时才刷新时间戳,
   否则 `_geom_settle()` 会永远以为“刚刚还在缩放”, 无限推迟重建, 画面就永久卡在
   按比例贴的旧图上(实际症状: 回放全局线路时着色段画到一半不再增长, 再缩放一下
   才又出现)。回归用例: `test_playback_zoom_resumes`。
2. **按比例贴图的偏移必须自己算**: 以前是 `p.scale()` 后再贴, 会多出
   `(余量+锚点)×(scale-1)` 的偏移(1920 宽 / 余量 0.35 时放大 2 倍能偏两百多像素)。
   现在直接算目标矩形 `(-余量-锚点)×scale`; 余量还得用**建层时**那份
   (它 = 控件尺寸×0.35, 改窗口后就变了)。回归用例: `test_zoom_scaled_blit_offset`。
3. **余量按缩放比放大**: 按比例贴图时覆盖范围也跟着变大, 所以锚点偏移的容忍量
   要乘 `scale` —— 否则放大过程中锚点一漂就重建, 滚轮又变成一顿一顿的
   (这一条把上面的尖峰从 20~58ms/格 降到 6~10ms/格)。
4. **离屏图回收复用 + 视野裁剪**: 一张 1920×1040 的层图 = 23MB,
   每次重建都新分配 + 清空要 ~5ms, 改成回收上一张((`_recycle`/`_take_spare`));
   额外地, 看不见的轨迹按包围盒直接跳过 `drawPolyline`(高倍放大时有用)。

实测数据: 重建一次 22~47ms, 与放大倍率**几乎无关**(zoom 1x 和 8x 一样慢) ——
说明 `QPainter` 的 clip 不会提前拒绝视野外的线段, 靠自己用包围盒裁。
另外试过把归一化坐标预映射成像素后画(恒等变换): 20.4 → 22.0 ms, **没有变快**;
关掉抗锯齿也只从 20.4 降到 18.4 ms。也就是说 20ms 这个量级是 2.2 万条线段的
**栅格代价下限**, 不是变换开销 —— 所以只能"少重建", 不能"重建更快"。

#### 全局录制"边录边画"的三次踩坑(2026-10-21)

一次几十条线、每条几千个点, 直接套用上面的"轨迹层"会炸:

| 做法 | 实测 | 后果 |
|---|---|---|
| 塞进静态轨迹层 | 层指纹每帧都在变 → **每帧全量重画** | 25Hz 轮询被拖到 **8Hz**, 滚轮缩放卡成幻灯片 |
| 每帧现画全部线路(分桶几何缓存) | **240 ms/帧**(4.8 万个抗锯齿线段) | 同样卡死 |
| **累加层**: 每帧只补新段 + 贴一次图 | **3.5 ms/帧** | 正常 |

细节:

* `_LiveGeom` 按 route_id 做**增量分桶**(只处理新加的几段), 每个桶的 `QPolygonF`
  只在"这帧加过点"时重建;
* 速度基准 = **这条线自己的最高速**, 与单条轨迹**完全同一套规则**(同样的速度 → 同样的颜色);
  基准上涨超过 4% 时这条线整条重算、整个图层重建(否则桶索引/颜色全是旧的);
* 累加层(`_layer_live`)与回放层(`_layer_playback`)同一个思路;
* **缩放**会让几何全变, 重建一次要 270ms(40 条线 × 1200 点) → 缩放过程中先把旧层
  **按比例贴上去**(立即有反馈), 停手 200ms 后再重建;
* 静态轨迹层/回放层后来也改成了同一套做法(见上一节“缩放卡顿的最后一轮修”)。

| 场景(1000×800, 40 条线 × 1200 点) | 耗时 |
|---|---|
| 稳态(每帧补几个点) | **3.5 ms/帧** |
| 滚轮缩放一档 | **5~6 ms**(270 → 5) |
| 停手后的重建(一次性) | ~200 ms |


#### 为什么不用显卡?

* 本程序是 **Qt Widgets + `QPainter` 自绘**, 走的是 Qt 的**软件光栅**(raster)引擎 —— 纯 CPU;
* Qt 6 **没有 GPU 版的 QPainter 后端**(Qt 5 的 OpenGL paint engine 已移除)。把控件
  换成 `QOpenGLWidget` 也**不会**让 `QPainter` 的绘制变成 GPU 绘制: 几何还是 CPU 栅格化,
  只是最后多一次上传/合成;
* 要让这 3766 条线段真跑在 GPU 上, 得把地图控件改成**原生 OpenGL/Vulkan 渲染**
  (自己写着色器画线段、菱形、方块、文字)。收益不成比例: 现在静止/拖动已经在
  **1ms 量级**(60fps 下占用不到 2%), 而代价是新增 `QtOpenGL` 等模块
  (会被 `tools/trim_qt.py` 精简掉, 也会让安装包变大)和整块渲染代码的维护风险;
* 所以这里的选择是: **把 CPU 的工作做成缓存 + 少做无用功**, 而不是换渲染后端。

#### GPU 化评估(2026-10-21, 用户再次提出“性能仍不满意”时重做的量化)

先看钱花在哪(离屏实测, 本机, 回放一条全局条目 = 64 条线路):

| 场景 | 整帧 | 底图平滑缩放 | 图层贴图 | 光标/叉/标记 | 其余(fill+起步+玩家/悬停) |
|---|---:|---:|---:|---:|---:|
| 回放稳态 1920×1040 | **7.22 ms** | 2.79 | 1.04 | 1.51 | ~1.9 |
| 显示轨迹(28 条) | 3.63 ms | 2.09 | 0.86 | 0 | ~0.7 |
| 录制预览(边录边画) | 5.50 ms | 2.56 | 1.91 | 0 | ~1.0 |
| 空地图(只有底图) | 3.79 ms | 2.18 | 0.87 | 0 | ~0.7 |
| 回放 2560×1440 | 9.74 ms | 4.10 | 1.72 | 1.37 | ~2.5 |
| 回放 3840×2160 | 21.41 ms | 9.22 | 4.16 | 1.55 | ~6.5 |
| **每帧强制重建** 1920×1040 | **86.4 ms** | — | — | — | `make_layer` = **79 ms** |

⇒ 1920 下的稳态**不是矢量栅格化, 而是像素写带宽**(底图重采样 + 大图贴图 + 整窗填充
≈ 4.5 ms); 真正的矢量开销只在“重建”那一刻(79 ms)。GPU 恰好擅长这两件事:

| 成本项 | GPU 后预期 | 现在 |
|---|---|---|
| 底图重采样 / 图层贴图 / 整窗填充 | ~0.1 ms(两张纹理各画一个四边形) | ~4.5 ms |
| 2.2 万段抗锯齿折线 | ~0.2 ms(顶点缓冲一次画完) | 79 ms(一次性) |
| 时间标签文字、悬停浮层 | 不变(仍走 QPainter/文字图集) | <1 ms |

三条路线的复杂度(含两条**硬约束**):

| 路线 | 收益 | 工作量 | 硬约束 / 风险 |
|---|---|---|---|
| A. `QOpenGLWidget` + 照旧用 `QPainter` | **接近 0 或更慢** | 0.5 天 | QPainter 描边仍是 CPU 三角化后再上传; 且 Qt 文档明说**一加 QOpenGLWidget, 整个顶层窗口的合成都会切到 GL**, 其它控件仍软件绘制 —— 组合/透明/远程桌面都会变脆 |
| B. `QOpenGLWidget` + 自写 GL 画线 | 稳态 7→~2 ms, 重建 79→<1 ms | **3~5 天** | 要自己写: 着色器、归一化→NDC 矩阵(含 zoom/pan/DPR)、**线宽扩边成四边形**(core profile 的 `glLineWidth` 多数驱动限 1.0)、圆头/接头、AA(MSAA 或边缘着色)、底图/图层改纹理; 文字与图元仍要 `beginNativePainting()` 混用; `tools/trim_qt.py` 要保留 `QtOpenGLWidgets`; 老显卡/远程桌面 GL 上下文可能创建失败 → 必须留软件回退(两套渲染代码并存); 跟像素有关的用例也要放宽 |
| C. Qt Quick(GPU 场景图) | 同上 | 换栈级别 | PyQt6/PySide6 都**不暴露自定义 QSG 节点**(要写 C++ 扩展); `Canvas`/`Shape` 画 2 万段线更慢 |

**结论(2026-10-21)**: 先做 CPU 侧剩下的三个小项(都不动架构):

1. **底图预缩放缓存**: 缩放/改窗口后重建一次缩好的图, 之后 1:1 贴 —— 实测
   1.76 → 0.64 ms(1920); 4K 下 4.98 → 3.90 ms(1:1 贴本身就贵);
2. **只填需要填的地方**: 整窗 `fillRect` 在底图覆盖大部分画面时是白费(≈1 ms);
3. **重建分帧**: 79 ms 拆成“先粗后细”(先按 1/4 抽稀画一遍, 随后几帧补细节)让尖峰变平滑;
   顺带可以按**段**(而不是整条线包围盒)裁剪视野外的线段。

只有当“同时显示 200+ 条线 / 拖动时也要 4K 满帧”成为真实需求时才走 B 路线; A 和 C 不建议。

#### vispy 实测(spike, 2026-10-22) —— 结论: 不值得重写

用户提出“查一下有没有什么合适的库可以直接用”。候选里 **vispy**(MIT, 纯 Python,
唯一硬依赖 numpy, Qt 后端标为 Stable, `LineVisual` 支持 `width` / `antialias` /
`method='agg'` 片元抗锯齿)最合适, 于是用**真实数据**做了 spike:
`dist\WTRouteTester\data` 里的一条全局录制 = **64 条线路 / 29630 段**, 底图
`maps\<key>.jpg`, 独立 venv(Python 3.12 + vispy 0.17.0 + numpy 2.5.4 + PyQt6 6.11),
GL 4.6 / NVIDIA。测法: 每帧改相机 rect 后 `canvas.update() + app.process_events()`,
取 80~300 帧平均与最差值。

| 测法 | 帧时间 | 备注 |
|---|---:|---|
| 空画布(只剩 GL 交换) | **6.0 ms** | 165 Hz 垂直同步底噪 |
| 底图 `ImageVisual(method='subdivide')` | 6.0 | 底图基本不要钱 |
| 64 × `LineVisual`, `method='gl'`(1px 无 AA) | **18.7** | 12.7 ms 全是 Python 侧开销 |
| 64 × `LineVisual`, `method='agg'`(2.4px 抗锯齿) | **49.5** | 每帧每个 visual 都重新 bake 三角带 |
| 8 × `LineVisual`, gl | 6.3 | 可见是**按 visual 个数**付钱 |
| 2.96 万段**合成 1 个** visual(`connect='segments'`, gl) | **6.0** | GPU 本身毫无压力 |
| 合并后每帧重传颜色数组(59k 顶点 ≈ 950 KB) | 9.3 | 回放推进的代价 |

三点硬结论:

1. **GPU 不是瓶颈, vispy 的调度才是**。同样的 2.96 万段, 拆 64 个 visual 是 18.7~49.5 ms,
   合成 1 个就是 6.0 ms(= 什么都不画的价)。agg 方法还会每帧重算三角带
   (profile 里 `_agg_bake` 60 帧 × 64 visual = 3840 次), 且**只支持 `connect='strip'`**,
   逐段配色要用"逐顶点配色 + 相邻段插值"绕。
2. **beat 不过现有的软件渲染**: 现有稳态 **4.26 ms**(拖动平均) / **7.22 ms**(回放),
   而 GPU 版最好情况 6.0 ms、回放更新 9.3 ms。GPU 唯一的好处是**没有 79 ms 的重建尖峰**。
3. 代价却是全都要重写: `gl` 方法线宽只有 1px(和现在的 2.4px 圆头比是另一个观感)、
   文字标签/悬停浮层/命中测试/战区闪烁/重生方块全要改成 visual 攒(cjk 字体还没有保障)、
   `tools/trim_qt.py` 要留 `QtOpenGLWidgets`、远程桌面/老显卡要留软件回退。

⇒ **判为不值得**: 用户感受到的"拖动卡"来自**重建尖峰**(拖出定位余量就整层重画, 64 条线 = 79 ms),
不是来自稳态。下一步应该**消尖峰**, 不是换渲染栈:

* **图层滚动平移代替重建**(首选): 拖出余量时开一张同样大小的新图, 把旧层按偏移
  `drawImage` 过去(实测贴图 1.0 ms/张), 然后只重画新露出来的那条边(用 `setClipRect`
  限制), 预计 79 ms → 6~10 ms, 且**不影响任何绘制效果**;
* 顺带可选: 重建分帧(先抽稀画粗再补细)、按段视野裁剪。

附注(踩过的坑): Python 3.14 上 **numpy 有 cp314 轮子, 但清华镜像还没同步**
(`pip install numpy` 报 `No matching distribution found`), 要装得显式指官方源
`-i https://pypi.org/simple`; spike 因此用的是本机 `D:\Python312`。

#### 拖动尖峰的根因: 描边端帽(2026-10-21 晚)

spike 之后先把放大尺寸的那笔账量清楚了 —— 64 条线路 / 29630 段, 只画“已播放的
着色段”, 同一张 3264×1768 的层图:

| 画法 | 耗时 |
|---|---:|
| 每段一对点 `drawLines` + **圆头端帽**(原实现) | **216.6 ms** |
| 每段一对点 + **平头端帽** | **61.2 ms**(3.5×) |
| 把“同桶连续段”合并成折线(实测 29630 段只连成 16252 条, 每 1.8 段就断) | 80~(平头) / 128 ms(圆头) |
| 整条 64 根折线单色 `drawPolyline`(下限参照) | 24.1 ms |

两个反直觉的结论:

1. **`setClipRect` 完全不省时间**: 只露出 280 px 宽的边来重画是 171 ms, 整层重画
   170 ms —— 因为 Qt 的描边(SDF 光栅化)**逐段独立进行**, docstring 里写“已裁掉”的
   线段它照样要处理。所以“搬图层 + 只补窄边”这种 tile 式优化在 Qt 上无效;
2. **端帽是真凶**: 每段两端各一个半圆端帽, 代价是平头的 3.5 倍。线宽只有 2.4~2.6 px,
   平头在拐弯处留的缺口**不到一个像素**(圆/平同屏 2× 放大对比肉眼分不出, 抽样
   24 万点里 0.55% 有差异且都在拐角), 因此逐段绘制一律改成平头
   (`SEG_CAP`, 见 `route_map_view.py`)。

顺带落地的两项:

* **回放前缀几何缓存** `_play_seg`: 以前每次重建/搬图层都把所有已播放段重新分桶
  (纯 Python 过 2.9 万段); 现在复用 `_LiveGeom` 增量缓存, 重画只做 `drawLines`;
* **拖动时搬图层而不是重建** `_shift_layer`(轨迹/回放/实时三种层): 贴旧内容
  (fill 2.0 ms + 整层拷贝 1.0 ms) 再补新露出来的那条边。**注意它并不比直接重建快**
  (原因见上: clip 不省描边), 保留它的价值在于: ① 实时层以前根本不看锚点, 录制中
  拖动会让已录线路**错位**(真 bug, 已修); ② 为将来上“分块几何 + 按块裁剪”留好
  接口。锚点必须挪到“偏移 0”, 挪到余量边界会让 40 px 一步的拖动**每帧搬一次图**。

#### pygfx(wgpu/WebGPU)实测(spike, 2026-10-21 深夜) —— 这条路能用

独立 venv(Python 3.12 + pygfx 0.17.0 + wgpu-py 0.32.0 + rendercanvas 2.7.2 + PyQt6),
真实数据(64 条线路 / 29630 段 + 真实底图), GL/Vulkan 走 NVIDIA:

| 写法 | 拖动 300 帧 | 缩放 20 档 | 逐帧改颜色 |
|---|---:|---:|---:|
| 合并成 **1 个** `Line`(`LineSegmentMaterial`, 段对) | **1.75~1.91 ms** | 1.70~1.82 | 1.01~1.11 |
| 64 条 `Line`(`LineMaterial` = strip, 带接头) | **2.58~2.80** | 2.58~2.86 | 1.79~1.83 |
| 64 个 `Line`(`LineSegmentMaterial`, 段对) | 3.63~4.02 | 3.65~3.73 | 2.70~2.99 |

(以上是**离屏**画布, 只算渲染; 对比现有的软件渲染: 稳态 4.26 / 7.22 ms, 重建 61~70 ms。)

三个必须记住的坑:

1. **Qt 下的 present 是真正的瓶颈, 而且默认是最慢的那种**。`rendercanvas` 的 Qt 后端
   默认 `present_method="bitmap"`(`WgpuContextToBitmap`: 渲到纹理 → **读回** →
   `QPainter.drawImage` 贴到控件)。实测空场景 **9.8 ms/帧**、带场景 **11.9~89 ms/帧**
   —— 比现在的软件渲染还慢, 直接淘汰。
   **必须显式 `RenderCanvas(..., present_method="screen")`**(→ `WgpuContextToScreen`,
   `WA_PaintOnScreen` 原生 surface): 同一场景拖动 **1.17 ms/帧**。代价是绕过 Qt 合成,
   远程桌面/多屏/某些驱动上有黑屏风险 → 要留“失败就回退软件渲染”的开关。
2. **线段比线宽短会画成虚线(串珠)**。pygfx 的厚线着色器为接头会缩短每段, 段长
   < 厚度(2.6 px)时几乎每段都被吃掉 → 整条线看着像虚线。实测按 `[::2]`/`[::4]` 抽稀后
   完全连续 ⇒ **上 GPU 必须配按缩放的 LOD 抽稀**(Douglas-Peucker 或按最小段长抽稀,
   目标段长 ≥ 1.5× 线宽), 顺带把顶点数降下来。
3. **中文文字要显式注册系统字体**: `pygfx` 自带的字体管理器在 Windows 上扫不到
   `msyh.ttc/simhei.ttf` 这些(431 个系统字体里没有 CJK), 直接 `gfx.Text("时间")`
   会报 `Cannot render chars '时间'`。加上
   `from pygfx.utils.text import font_manager as fm; fm.add_font_file(r"C:\Windows\Fonts\msyh.ttc")`
   之后 SDF 文字可以正常出中文(已渲染验证)。

结论: **vispy 淘汰, pygfx + `present_method="screen"` 可用**(渲染 1~3 ms, 无重建尖峰,
中文可解, BSD-2 许可)。真正落地时要处理的: LOD 抽稀、命中测试(可继续用现有 Python
侧 `_hit_test`, 数据结构不变)、标记/战区/叉/光标改用 `Mesh`/`Line` 图元、打包带
`wgpu-native` DLL、以及“screen present 失败自动回退软件渲染”。



代价是几张比窗口略大的离屏图(每张 3~6 MB), 以及"内容一变就重建"的逻辑复杂度 ——
因此缓存层的失效条件都写成了明确的指纹(几何 + 内容 + 定位余量), 并有回归测试
(`test_map_draw_cache` / `test_playback_draw_cache`)盯着"什么该重建、什么不该重建"。
渲染等价性也验证过: 与改前逐像素对比, 地图区域仅 ±1~3/255 的重新采样噪声(肉眼无差别),
轨迹类像素数量相差 0.03%。

#### 回放时“所有路线卡一下”的真凶: 战区状态混进了轨迹层指纹(2026-10-22)

用户报: **播放中有时候所有路线会卡顿一下, 像是某条线路对应的玩家被击毁、线路要隐藏导致的**。

猜测先用数据验: `tools/probe_playback_stutter.py` 拿真实回放(`c513b76710d5`, 67 条线,
0~416.5 s)按 0.2 s 步长逐帧推进 playhead, 把 `_sync_objects()`(同步)与
`renderer.render()`(提交)分开计时。

第一轮(只推 playhead)结论就一条: 尖峰全在**渲染提交**段(同步仅 0.4~0.9 ms),
而且**和阵亡时刻对不上** —— 各线末点 t=34.49/41.66/43.63/48.25 处只多 0.3~2 ms,
所以“死亡隐藏线路”不是元凶(那一步只是 `colors` 清零 + `update_full()`, 代价很小)。

第二轮补上真实回放**每帧都会做**的那一步(`view.set_zones(g.zone_state_at(t))`)后立刻现形:

| 指标 | 改前 | 改后 |
|---|---|---|
| 整层重建(`_rebuild_objects`)次数 | **9 次**(每次占领/易手) | **0 次** |
| 单帧最慢 | **239.13 ms**(同步 113 + 提交 126) | **7.75 ms** |
| 平均帧 | 3.76 ms | 2.80 ms |

根因: `_content_key()`(决定要不要重建 GPU 对象的指纹)里含 **战区快照**, 而回放每帧
都会把战区推进到当时的占领状态 —— 于是每次占领/易手都判定“内容变了”, 把 **全部 67 条
线路的几何重算一遍**(约 110 ms)+ 重建全部图标, 再提交一次全场景(约 120 ms)。
一局里 22 次战区快照变化里有 9 次真的触发了重建, 观感就是“放着放着整片线卡一下”。

改法: 把指纹拆成三级, 各自只重建自己那一层。

| 指纹 | 内容 | 变化时的动作 | 实测 |
|---|---|---|---|
| `_content_key` | 可见/高亮/录制中/回放中的路线 id 集合 + 底图指纹 | `_rebuild_objects()`(最贵) | 只在开始/结束回放时发生 |
| `_icon_key` | 重生点版本 / 占位文字状态 | `_rebuild_icons()`(不碰线路几何) | ~5 ms 同步 + 6 ms 提交 |
| `_zone_key` | 战区 label/side/坐标 | **`_rebuild_zones()` 只换那 4×N 个对象** | 已掉出 top15(亚毫秒) |

顺带记一条: 战区的 4 类对象(填充 `Mesh`/深色描边/白色描边/字母)必须自己记一份
`_gl_zone_objs` —— `_gl_zones` 里只存了 `(z, fill, color, text)` 四元组, 拿不到那两条
描边 `Line`, 单换战区时就会漏删旧对象(表现: 每次占领多叠一层描边)。
`_clear_icons()` 里也要把它清空, 否则换地图后会去删已经不在场景里的对象。

#### 那换成现成的绘图库呢(QCustomPlot / SciQLopPlots / pyqtgraph)?

结论: **不合适, 这条路不走**。四个理由(按否决力排序):

| 理由 | 说明 |
|---|---|
| **许可证** | `SciQLopPlots` 是 **GPL-3.0**; 本项目自己的代码是 Apache-2.0, 一旦链进去, 再分发的整包就必须按 GPL-3.0 发布。真要上 GPU, 用 `QOpenGLWidget` / `pyqtgraph`(MIT) 就没有这个问题 |
| **Qt 绑定冲突** | `SciQLopPlots` 是 Shiboken6 绑定, 只认 **PySide6** 且 `pip` 安装会**把 PySide6 锁到某个精确版本**; 本项目全量是 **PyQt6**。一个进程里混用两套绑定是已知的灾难, 所以等于把整个程序迁到 PySide6 |
| **不是同类工具** | 它是**时间序列/频谱**绘图库(`x = 时间`), 一条曲线 = 一个画笔; 而这里要的是"地图底图 + 每段独立颜色的折线(24 档速度) + 一堆自绘图元(起点/终点圆环、重生方块、闪烁战区菱形、带朝向的玩家箭头与回放光标、悬停浮层、命中测试)"。折线要拆成 24×N 条 graph, 图元也只能落回 `QCPLayer` 自绘 —— 又回到 `QPainter`, 白换 |
| **收益已经没了** | 它的强项是"后台重采样 + GPU 画百万点时间序列"。而这里 2 万段的稳态是 **4~10 ms/帧**、缩放一档 **6~10 ms**(见上节), 真正的剩余成本只有"停手后重建一次"的 20~50 ms |

真到了"线段数量再涨十倍"那一天, 优先级是: ①按段视野裁剪 ②按像素间距抽稀(LOD)
③把地图控件改成 `QOpenGLWidget` 自己画 `GL_LINES`(PyQt6 自带 `QtOpenGL`, 不换绑定、
没有 GPL 传染、只在需要时开启)。

### 地图切换 → 自动清除旧轨迹

8111 不提供地图名, 因此用**地图图片的 SHA1 指纹**作为地图身份(即记录里的 `map_key`)。
地图图片一变, 就认定为**换图**, 此时:

| 情况 | 处理 |
|---|---|
| 旧地图的实时/历史/回放轨迹 | **清除**(否则会画在新地图上, 产生误导) |
| 挂在旧地图上的"上次录制" | 清除(回放按钮随之置灰) |
| 属性仍属于当前地图的轨迹 | 保留(同一张图反复进出不会被清) |
| **正在录制时换图** | **保留实时轨迹**(否则轨迹会在录制中途直接消失), 仅提示; 本次录制仍归属开始时的地图 |
| 退出战局(见下文占位图) | 同上办理: 旧地图轨迹全部清除 |

### 战局外: 8111 返回的是一张 "?" 占位图

**未进入对局/试车场**时, `/map_info.json` 为 `{"valid": false}`, 而 `/map.img` **不是地图**, 而是
一张固定的灰色问号图。实测(2026-10-06)其特征:

| 项 | 值 |
|---|---|
| 格式 / 大小 | PNG, **1519 字节**(`Content-Type: image/png`) |
| 尺寸 | **128 × 128** |
| SHA1 | `ab516d02191d001d809253c346e8e3f93e13f136` |
| 内容 | 纯灰阶(仅 6 种颜色: 64/68/72/109/115/128), 中心像素 `(128,128,128)` |
| 外观 | 深灰底 + 浅灰 "?" |

存档样本: `docs/assets/8111_map_placeholder.png`。

程序据此把该图片识别为"**当前没有地图**":

- **不当作地图绘制**, 只在画布中央显示提示文字"尚未进入对局/试车场";
- 但仍算作一次"地图变化", 触发上面的**旧轨迹清理**;
- 常量: `route_store.PLACEHOLDER_MAP_SHA1`(测试会校验它与存档样本的 SHA1 一致,
  若 8111 改版导致失效, 测试会直接失败提醒重新抓取)。

### 采样间隔(毫秒)

信息区右上角可设置**采样间隔**(20 / 25 / 30 / 40 / 50 / 75 / 100 ms), **默认 40 ms(≈25 Hz)**:

- 该值同时决定**轮询间隔**与**轨迹采样间隔**(两者必须一致, 否则轨迹点会变稀疏);
- **40 ms 与 8111 的数据更新率匹配** —— 实测陆战 `rpm` 的变化间隔 p50 = 40 ms,
  即数据本身約每 40 ms 才更新一次; 调得更小只是重复采到同一批数据;
- 20 ms(≈50 Hz)已接近 8111 的请求上限, 适合需要极限精度时;
- 右侧实时显示**实际频率**(如 `实际 24 Hz`), 便于确认是否达到目标;
- 选择会被记住(下次启动沿用)。

### 轨迹回放

回放控制在**信息区顶部**(与下方录制功能用分割线隔开):

| 控件 | 说明 |
|---|---|
| **▶ 回放 / ⏸ 暂停** | 开始或暂停回放(播放到末尾后再点会自动从头开始) |
| **⏭ 到下一标记暂停** | 播放到**所有回放轨迹中距当前进度最近的那个标记时刻**自动暂停(精确停在标记时刻, 不会冲过去) |
| **倍速** | 0.5X ~ 16X(0.5 步进, 共 32 档), 选择会被记住 |
| **■ 结束播放** | **退出回放**并恢复显示眼睛点亮(不透明)的轨迹; 回放期间其余功能被锁定, 只有点它才能恢复 |
| 右侧进度 | 实时显示 `回放 00:12.345 / 01:37`, 多条回放时附带 `(3 条)` |

**回放期间其余功能全部锁定**(录制按钮、采样间隔、选项复选框、侧栏/眼睛、右键菜单):
回放绘制优先于轨迹显示, 若不锁定, 点眼睛会看起来“没反应”。
状态栏固定提示“回放模式: 其余功能已暂停使用, 点「■ 结束播放」返回”。
播到末尾时**不会自动解锁**(便于停下来看终点状态), 需手动点「■ 结束播放」。

**回放哪些轨迹**: 侧栏**选中的条目**(Shift/Ctrl 多选) —— 选中一条就播一条, 选中多条就播多条;
**只会是同一版本(地图 + 战区布局)的轨迹**: 双击某条 = 定基准后, 多选锁死在该版本内;
没定基准时如果选到了多个版本, 只保留“本次新选的那个版本”并把其余取消选中。
一条都没选中时依次退回: 眼睛点亮的轨迹 → 刚录制的那条。
未回放时 `lbl_play` 会显示 `基准 … | 待回放: N 条`(没定基准时是 `待回放: N 条`)。

**高亮层 = 侧栏当前选中的那几条**(可多条), 用**速度配色**画在最上面;
没选中任何条目时才退回“刚录制的那条”(它一直是默认高亮)。所以同一张图同一模式
录了好几条时, **点哪条就高亮哪条**(Ctrl 多选就同时高亮多条), 不会永远钉在最后一条;
其余被眼睛点亮的轨迹保持不透明灰色 —— 显示状态仍然只有 `_visible_ids` 一个来源,
选中只是“把它画得更醒目”, 不会改变眼睛亮/灭。

多条同时回放:

- 全部**从 `00:00` 一起开始**(共用一条时间轴), **以最长的那条播完才算结束**;
  较短的那条会自然“跑完停在终点”;
- 每条轨迹各画一个回放光标(位置由时间插值得到);
- **"到下一标记暂停"跨轨迹统一计算**: 把所有回放轨迹的标记放在同一条时间轴上,
  取当前进度**之后最近**的那个标记时刻(可能是任意一条轨迹上的标记);
  已经停在该标记上时再点会跳到**下一个**;
- 回放中改不了轨迹显示(侧栏锁定), 要切换显示先点「■ 结束播放」。

绘制表现:

- **已播放部分**按速度着色(与录制时一致);
- **未播放部分**为**半透明**淡灰蓝(唯一使用半透明的地方), 一眼就能看出进度;
- 已到达的标记正常显示, 未到达的淡化;
- 多条回放时不画时间标签(同一位置的标签会完全重叠、无法阅读);
- **回放光标**(白色圆环)由**时间线性插值**定位(不是取最近的采样点),
  因此在采样点之间也能平滑移动。

注: 回放与录制**互斥** —— 录制中回放按钮不可用(反之亦然)。
另外, 8111 **不提供地图名**(实测结论见 `docs/8111使用经验.md` §3.6), 地图身份用图片哈希,
名字在「地图管理」里自己起一次。

## 6.5 游戏模式:按战区数量判定(2026-10-06 新增)

同一张地图会有**多种模式**(战区控制 / 战区攻陷 / 战区争夺), 跑图线路必须分开看。
8111 不给“模式名”, 但 `/map_obj.json` 里的战区能决定它:

```json
{"type":"capture_zone", "icon":"capture_zone",
 "x":0.432927, "y":0.556106,          // 战区中心(0~1)
 "zone_id":0, "zone_label":"A", "zone_label_code":65}
```

| 战区数 | 模式 |
|---|---|
| 3 | 战区控制(A/B/C 互相争夺) |
| 2 | 战区攻陷(开局双方各一个) |
| 1 | 战区争夺(单点争夺) |
| 其它/取不到 | 未知模式 / `N 战区` |

- 解析与判定都在 `wt81111g/zones.py`(`zones_from_objects` / `mode_name` / `signature`);
- **战区坐标串**是稳定的“模式指纹”: 同一张图的同一模式, 战区位置固定,
  所以 `(地图指纹, 战区坐标串)` 能把同图不同模式彻底分开;
- 录制开始时把 `zone_count` / `zone_signature` / `mode_name` **写进记录**;
  进图瞬间还没拿到战区时会在一拿到就补写进当前录制;
- 见过的战区布局按地图存进 `routes.json` 的 `map_zones`(按指纹去重, 每图最多 8 种),
  这样**战局结束后**(8111 战区数据消失)依旧能在地图上画出战区。

### 侧栏:地图 → 模式 → 轨迹(三层)

轨迹条目(带眼睛图标)在最里层, 模式层由记录的 `mode_label` 聚合而来:

```
地图 1                      3 条
    战区控制                2 条
        12:31  Leopard 2PL  01:37
        12:05  T-80BVM      01:22
    战区争夺                1 条
        11:40  Leopard 2PL  00:58
```

- 一张图的不同模式分开成组, 组内按时间倒序, 最近跑的模式排在最前;
- 旧记录(没有模式字段)归为“未知模式”;
- 只缓存了图片、还没录过轨迹的地图仍以灰色「仅缓存」列出, 悬停能看到见过的模式;
- 眼睛列宽度按“缩进 × 3 + 图标”算(`EYE_COLUMN_WIDTH`), 否则最里层图标会被列边界裁掉。

### 侧栏:地图 → 模式 → 版本 → 轨迹(四层)

**同一个模式还会有多个“版本”** —— 版本就是当时的**战区位置**(坐标指纹):

| 模式 | 版本差异(实测/用户实践) |
|---|---|
| 战区控制(3 战区) | 大地图 / 小地图: 交战区大小不同 → 三个战区位置不同 |
| 战区攻陷(2 战区) | 大地图 / 小地图: 同上, 两个战区位置不同 |
| 战区争夺(1 战区) | 每局从 **3 个位置**里随机一个 |

所以“同一张图的同一条线路”要按 地图 + 模式 + 版本 三层才能对比。
侧栏示例:

```
美国·沙漠之城                                  3 条
    战区控制                                  2 条
        区域 1(大地图)                        1 条
            12:31  Leopard 2PL  01:37
        区域 2(小地图)                        1 条
            12:05  T-80BVM      01:22
    战区争夺                                  1 条
        点位 2                                1 条
            11:40  Leopard 2PL  00:58
```

- 版本默认自动编号: 多战区模式按**跨度**(战区间最大距离)降序 → `区域 1` 通常是大地图;
  单战区模式按坐标排序 → `点位 1/2/3`;
- **共同显示与多选都只限同一版本**: 不同版本(大地图/小地图、不同随机点位)的线路
  不可比, 所以地图上一次只画一个版本的轨迹; 双击某条线路 = 把它的版本定为**基准**
  (标题行前面会出现**图钉**), 之后 Ctrl/Shift 多选只在该版本内生效(状态栏与信息区都有提示);
  没定过基准时, 第一个点到的线路即成为基准;
- **右键版本行 → 「重命名此版本…」** 可以改成自己认得的名字(如“大地图/小地图/西点”),
  名字存进 `routes.json` 的 `layout_names`, 留空即恢复自动编号; 版本行的悬停提示里有
  各战区字母与坐标、跨度值;
- 右键版本行还可以「显示/隐藏本版本全部轨迹」;
- 只缓存了图片、还没录过轨迹的地图(灰色「仅缓存」)也会把**已见过的版本**挂出来(0 条),
  这样还没录就能先把名字起好;
- 旧记录(没有战区字段)归在「未知模式 → 未知位置」下, 不影响使用。

### 地图上的战区(菜单「设置」→ ☑ 显示战区位置(A/B/C))

- 用小**菱形**画(圆已经表示起点/标记/终点, 菱形不会混淆), 中间标字母 A/B/C
  (`zone_label`, 实测可直接拿到), 深色描边保证在任何底图上都看得清;
- **颜色 = 归属**(8111 站在玩家视角的约定): 蓝 `#174DFF` = 我方, 红 `#fa0C00` = 敌方,
  白 = 中立/未被占领。实测两战区局就是“红 A(敌方) + 蓝 B(我方)”;
  状态栏也同步显示 `战区攻陷 · 我方 B, 敌方 A`;
- **归属是实时刷新的**: 占领/丢掉后坐标不变、只有颜色变, 所以“该重画了”的判断
  除了坐标还要看 `color`(详见 `zones.zone_state()`); 落盘的“战区布局”仍只按
  **坐标指纹**去重 —— 归属反复变不会被当成新模式;
- **正在被占领时闪烁**(8111 `blink` 字段, 0/1/2): 脉冲曲线与周期照官方 8111 页面
  (`blink=1` 2.0s / `blink=2` 1.2s, 脉冲 `exp(-(5t-2)^4)`), 但**颜色不掺黄** ——
  官方是拿归属色与纯黄插值, 一闪就分不清是谁的; 这里在**本阵营色里做明暗脉冲**
  (变暗到 40% ↔ 纯色), 也就是“蓝闪蓝、红闪红”;
  状态栏的归属文字会标上 `(占领中)`; 闪烁只在真的有被占战区时跑定时器
  (静态画面不耗 CPU), 关掉「显示战区」也会停;
- 战局内画的是**实时**战区(带实时归属色); 战局外/看缓存底图时, 画的是该地图存过的
  布局(优先匹配“正在看的轨迹的模式指纹”, 匹配不到就用最近一次见过的),
  此时**归属色一律按中立画** —— 当时谁占着哪个战区早已过期, 拿旧颜色会误导;
- 开关记在 `QSettings`(`show_zones`), 下次启动保持。

**已验证 / 待确认**:

- ✅ 三战区局 → 3 个 `capture_zone`(战区控制); 两战区局 → 2 个(战区攻陷, 红/蓝各一个);
  **一战区局 → 1 个**(战区争夺, 占领后立即变蓝) —— 三种模式全部实测到;
- ✅ 归属色 ↔ 我方/敌方的对应关系由“两战区局的蓝/红分布 + 蓝红重生点/机场成对出现”旁证,
  且与用户游戏内观察一致;
- ⏳ `blink`(被占领中)的闪烁目前按官方页面逻辑实现; 若实机中发现“占点时没闪”,
  说明游戏给战区的 `blink` 另有含义, 需要再采一次数据确认。

### 地图上的重生位置(菜单「设置」→ ☑ 显示重生位置(红/蓝方块))

- **数据来源**: 同一份 `/map_obj.json` 里 `type/icon` 以 `respawn_base_` 开头的对象。
  实测(2026-10-07)`respawn_base_tank` 一局 **128 个、蓝红各 64** —— 游戏里“重生区域”
  就是这一堆候选位置(重生时从中随机分配一个), 所以它们**成小片聚集**而不是一个点;
- **画法**: 一个位置一个**空心方块**(不填充, 免得盖住底图与轨迹),
  **红 = 敌方, 蓝 = 我方**(与战区同一套归属色); 深色垫底描边保证在任何底图上都看得清;
  连成一片的方块就是那个“重生区域”(能看出区域的大小与朝向);
- **只画地面载具**(`respawn_base_tank`): 实测 `respawn_base_fighter` 的坐标
  **不是 0~1 归一化**(x/y 是 ±3 量级、还带 `dx/dy≈±200`), 是另一套单位, 照着画会飞出画面 ——
  空军/无人机重生点仍会被**记录下来**(存了 `kind` 字段), 只是不画;
- **跟版本一起存**: 重生位置同样随模式/版本变(同一张图“区域1/区域2”双方重生位置不同),
  所以存进 `map_zones[].spawns`, 按“地图 + 战区指纹”去重; 战局外/看缓存底图时,
  画的就是该版本存下来的那份(匹配“正在看的轨迹的模式指纹”, 没有就用最近一次见过的);
- 归属色同样**按通道判**(见 `zones.side_of()`), 所以老版本/空战里的 `#185AFF`/`#fa3200`
  也认得, 而玩家自己的黄色 `#faC81E` 不会被误判成敌方;
- 开关记在 `QSettings`(`show_spawns`), 下次启动保持。

**已验证 / 待确认**:

- ✅ 解析: 128 个地面重生点、双方各 64, 坐标为 0~1 归一化(与战区同一坐标系);
- ✅ 落盘: 跟战区布局一起存, 同一布局重复进图不会重复写盘;
- ⏳ 位置是否与游戏内小地图上的重生区域完全重合, 需要你在实机里对一眼
  (若发现整体偏了/镜像了, 说明两者的坐标约定可能不同, 需要再采数据核对)。

## 6. 数据来源(战争雷霆 8111 本地接口)

| 端点 | 用途 | 请求频率 |
|---|---|---|
| `/indicators` | 载具内部名(`type`, 形如 `tankModels/germ_leopard_2a4_pzbtl_123`)、速度(`speed`) | 10 Hz |
| `/map_obj.json` | 玩家坐标: 取 **`icon == "Player"`** 的对象(其 `type` 是载具类别, 如 `ground_model`) | 10 Hz |
| `/map.img` | 地图图片(实测 **JPEG 2048×2048**; 坐标 0~1 乘图片尺寸即得像素)。**战局外为 128×128 的 PNG "?" 占位图**, 见上文 | 0.5 Hz(内容变化才刷新界面) |

兜底: 若 `map_obj.json` 中找不到玩家对象, 会尝试读 `indicators` 的 `map_x`/`map_y`。

### 玩家对象识别(2026-10-06 实测, 自定义房间)

```json
{"type":"ground_model","icon":"Player","x":0.536519,"y":0.181914,"dx":-0.673497,"dy":0.73919}
```

- 玩家**不是** `type == "player"`, 而是 `type` 为载具类别、靠 **`icon == "Player"`** 标识;
- `x`/`y` 为 0~1 归一化坐标, `dx`/`dy` 为单位方向向量;
- 同一次实测 `map_obj.json` 共 54 个对象: 玩家 1 个, 其余为 `respawn_base_tank`(40)、`airfield`(6)、
  `capture_zone`(3)、`respawn_base_fighter`(2)、`respawn_base_ucav`(2) —— 所以**必须按 `icon` 精确筛选**,
  不能“取唯一一个带 x/y 的对象”;
- 地物(如 `airfield`)的 `sx/sy/ex/ey` 可能超出 0~1(位于地图外), 不影响玩家坐标。

## 6.9 全局录制(整局所有玩家的线路, 2026-10-21)

单条线路只录“我自己”; 全局录制录**整局所有玩家**。
回放的 `/map_obj.json` **只给观战那一方**的单位, 所以一局要录两次:
一次观战 A 方点「A 队录制」、一次观战 B 方点「B 队录制」。

**侧栏结构**(全局条目放在“存放路线的那一级”的**末尾**, 与单条路线同级):

```
地图 → 模式(战区控制) → 版本(区域 1)
                          ├ 21:03  Leopard 2PL      ← 单条线路
                          └ 全局 10-21 21:41        ← 全局录制条目(名字=录制时间)
                              ├ A 队  (12 条)
                              │   ├ 00:03  MediumTank   ← 组内按时间正序
                              │   └ 02:11  IFV
                              └ B 队  (11 条)
```

**录制时机**: 点按钮时通常还在**等待部署**(8111 没有玩家数据) → 先挂着,
**抓到第一个可录单位的那一刻才定 0 秒**; demo 播完回到车库自动停
(8111 换回 `?` 占位图, 或全场无单位满 3 秒), 也可手动点「停止 A/B 队录制」。
一条线都没录到就撤销条目。

**录制期间锁定地面底图**: 有人上飞机时 8111 会改发空战地图(坐标系与地面图完全不同),
不能跟着换 —— `RouteRecorder._map_loop` 在 `_map_lock` 为真时只监听“是否回到车库”,
不更新 `_map_key` 也不发 `map_changed`。

**速度与配色**: `/indicators` 只给**摄像机所在载具**的速度, 所以全局录制的速度是
用“归一化位移 × 地图边长(米) / Δt”自己算的:

```
v = hypot(Δx·W, Δy·H) / Δt × 3.6
W,H = /map_info.json 的 map_max - map_min(米; 实测陆战图 4096×4096)
```

5Hz 采样 → 速度是 0.2s 的平均值; 截断 200 km/h。绘制走**与单条轨迹完全相同**的
速度配色(`build_speed_segments`), 所以:

- 眼睛点亮 → 灰色普通层; 选中 → 速度配色; **录制中边录边画**(`set_live_multi`);
- 日志会写 `速度标定: 8111=.. | 位移推算=.. | 地图=..×..`, 用来验证尺度。

**回放**: 全局线路暴露了与 `RouteRecord` 同名的 `route_id` / `marks` / `map_key` / `duration`,
所以直接走现成的 `RoutePlayer` + 多轨迹回放: 选中整个条目就播全部线路,
只选中几条就只播那几条。全局线路没有标记点 ⇒ “到下一标记暂停”直接播到底。

**被击毁**(2026-10-21, 回放控制行的两个默认勾选项):

| 选项 | 画法 |
|---|---|
| 被击毁后路线变暗 | 阵亡后整条线改成半透明纯灰 `COLOR_DEAD_ROUTE`(不再按速度着色) |
| 被击毁标记 | 线路末端一个红叉(半臂长 2.6px / 线宽 1.2px / **平头端点**, 与回放光标白点相当) |

判定口径(用户原话: “在 8111 中玩家对应的 icon 消失就是死了”, 不用管是哪个玩家、也不用管是哪条线):

- 这条线的 icon **消失** → 这辆车没了 → `dead=1`;
- 为什么可以放心这么判(用户 2026-10-21 补充): 玩家**一次只能操作一台载具**,
  想换固定翼(如 Su-25)必须先让地面坦克阵亡; **退局**后载具停在原地、
  8111 过一会儿不再上报 → 也算击毁; 只有**微型侦察无人机**与**核弹机**(2500 SP)
  会出现“坦克本体还活着而玩家不在车里”, 且无人机那条线不会断(本体仍作为
  `ground_model` 上报) —— 何况本项目只录地面单位, 两类例外都不影响判定;
- 实现上多一道闸: 线断的那一刻**场上还有别的可录单位**才算 ——
  **全场一起消失**(回到车库 / 录制自动结束)→ 不算  —— 用户特意提过
  “pro 能做到整局一次不死”;
- 手动结束录制时还活着的线 → 不算;
- 实现就在 `GlobalTracker.feed()`: `_expire(t, alive=bool(units))` —— 传的就是
  “这一帧还有没有可录单位”; `finish()` 一律 `dead=False`;
- 旧数据没这个字段 → `route_store._infer_legacy_deaths()` 按“结束得比整局末尾早
  `LEGACY_DEAD_MARGIN`(10s) 以上”推断(新数据总会写 `dead: 0/1`, 所以不会误判旧/新)。

回放时红叉只在**越过阵亡时刻**后出现; 阵亡后不再画白点光标(已经没有“当前位置”)。

**出生保护不记录**(用户 2026-10-21 决定): 重生时玩家会消失好几秒, “消失即结束”
本来就会把重生前后拆成两条线。

**录到哪一条**: 右键全局条目可打「标记为 A/B 队录制目标」;
有标记就录到那条(已录过先问是否清空重录), **没有任何标记就新建一条**。
同一队只允许一条记录带标记, A/B 可同时标在同一条上。

**单位过滤**(`global_record.py`, 白名单):

| 对象 | 处理 |
|---|---|
| `ground_model`(坦克/步战/防空…) | ✅ 录 |
| `aircraft` / `helicopter` | ❌ 跳过(我们只关心地面) |
| 微型侦察无人机 | ❌ 跳过(它的 `icon` 就是 `Fighter`, 与固定翼无法区分) |
| `capture_zone` / `respawn_base_*` / `airfield` / `Airdefence` | ❌ 跳过 |
| 坐标不在 0~1 | ❌ 跳过(空中视角会带出坐标 2.9~3.4 的 AI 防空) |

**跟踪**(8111 没有 id、没有玩家名): 帧间最近邻 + 贪心配对(同 `type`,
半径 0.004 归一化), 5 Hz 存点(5Hz 已足够看路线, 点数少 5 倍);
连续 1 秒配不上 = 该线结束; **蓝 → 深蓝 `#1839A7` = 重生**, 上一段收尾、开新线并标 `protected`。
同一个人中途上飞机/换车会断成两条线(已与用户确认)。

**地图配色**: A 队青 `#22d3ee`、B 队品红 `#e879f9`, 线宽 1.8px ——
刻意避开速度配色(蓝→红)、标记圈与玩家标记的颜色。

**测试**: `tests/global_record_test.py`(9 项: 过滤/跟踪/重生拆线/空场自动停/
落盘与标记/地图绘制/侧栏结构/按钮互斥)。

## 7. 持久化

- 文件: `<可写根目录>/data/routes.json`(与黑名单数据同目录, 互不影响);
- 地图图片缓存: `<可写根目录>/data/maps/<地图键>.<jpg|png>`;

    "routes": [

      {

        "zone_count": 3, "zone_signature": "A@…;B@…;C@…", "mode_name": "战区控制",

## 9. 已知限制与说明

1. **地图名**: 8111 **不提供地图名称**, 因此用**地图图片内容指纹**(sha1 前 12 位)作为地图唯一键分组,
   显示名默认"地图 1 / 地图 2 …", 可在侧栏右键**重命名**为真实地图名(重命名后持久保存)。
2. **自定义房间/试车场同样可用**: 2026-10-06 在自定义房间实测, 玩家对象以 `icon == "Player"` 出现在
   `map_obj.json` 中(`type` 为 `ground_model`), 坐标可正常获取, **自定义房间能够正常录制**。
   此前“自定义对局无玩家对象”的说法不准确: 并非没有, 而是它的 `type` 不叫 `player`。
3. **载具名**: 8111 提供的是内部名(如 `tankModels/germ_leopard_2a4_pzbtl_123`), 界面做了美化显示
   (如 `Leopard 2A4 Pzbtl 123`), 并非游戏内中文全称。
4. **运行环境**: 全局快捷键仅 Windows 可用(非 Windows 下请使用界面按钮, 功能不受影响)。
5. **地图身份靠图片指纹**: 若同一张地图在 8111 输出上有细微差异(图片更新), 会被当成“换图”并清除轨迹。
   实测同一张地图同一局内图片内容稳定, 未出现误判;
   若将来发现误判, 可改用图片尺寸 + 归一化后的像素采样做容错比对。
6. **战局外**只能看到提示文字(8111 只给占位图), 需进入对局/试车场才会显示地图与玩家位置。
7. **全局录制拿不到玩家名**: 8111 的 `/map_obj.json` 没有 `id`、没有名字, 所以线路只能按
   “出现时间 + 载具类别”标识, “同一个人”是按帧间位置最近匹配猜出来的 ——
   两人贴得极近时可能互换, 中途上飞机/换车会断成两条线。
   空中单位**全部跳过** —— 实测(2026-10-21)侦察无人机的 `icon` 就是 `Fighter`,
   与真正的固定翼一字不差, 没有任何字段能分开它俩(详见 `8111使用经验.md` §7.9.1)。
8. **全局录制条目不能回放**(它是几十条线的集合, 时间轴是整局的 A/B 两次录制),
   只能在地图上显示/隐藏; 单条线路录制的回放功能不受影响。

## 10. 打包为 exe

```powershell
.\build_route_tester.ps1              # 仅目录版(onedir, 启动最快, 推荐日常使用)
.\build_route_tester.ps1 -OneFile     # 额外产出单文件版(便于分享)
```

| 产物 | 说明 | 体积 |
|---|---|---|
| `dist\WTRouteTester\WTRouteTester.exe` | **目录版**(onedir), 启动快; 需将整个文件夹一起拷贝 | 目录约 84 MB |
| `dist\WTRouteTester_Portable.exe` | **单文件版**(onefile), 便于单独分享; 启动需先解压到临时目录(稍慢) | 约 40 MB |

打包要点:

- 仅依赖 **PyQt6 + requests**, 不含黑名单主程序的 pywebview/pythonnet 等重型依赖, 因此体积远小于主程序;
- ⚠️ **不要引入新的 Qt 模块**: `tools\trim_qt.py` 会把没被引用的 Qt 模块 DLL 精简掉,
  于是 `import PyQt6.QtNetwork` 在打包版里会抛 `ImportError: DLL load failed while importing
  QtNetwork`(DLL 被删了), exe 一启动就崩 —— 单实例那套因此改成纯 Win32
  (枚举窗口找已有实例), 不碰 QtNetwork;
- 精简 Qt 时使用 `python tools\trim_qt.py WTRouteTester --keep-imageformats`,
  **必须保留 jpeg/webp 图片插件** —— 8111 的 `/map.img` 地图图片可能是 JPEG, 删掉 `qjpeg.dll` 会导致地图无法显示;
- 版本信息取自 `version_info_route.txt`(产品名"战争雷霆跑图线路测试器");
- **图标**(2026-10-07 起): 源图 `icon\icon_512X512_WTRouteTester.png`(AI 绘制) →
  `tools\make_app_icon.py` 转成多尺寸 `icon\WTRouteTester.ico`(16/24/32/48/64/128/256,
  128 及以下用 BMP 帧、256 用 PNG 帧), 打包时 `--icon icon\WTRouteTester.ico`,
  同时把那张 PNG 随包打进去供窗口/任务栏图标用(运行时 `QIcon` 加载);
  **注意别再用根目录的 `app.ico` —— 那是黑名单主程序的图标**;
  换了图标只需重跑 `tools\make_app_icon.py` 再打包(PyInstaller 转 PNG 需要 Pillow, 本环境没装);
- **数据目录随 exe 位置而定**: 目录版存于 `dist\WTRouteTester\data\routes.json`,
  单文件版存于 **exe 同级目录**的 `data\routes.json`; 源码运行的记录存在项目根 `data\routes.json`,
  三者互不影响(如需迁移, 直接拷贝 `routes.json` 即可)。
