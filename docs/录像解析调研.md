# 战争雷霆录像(`.wrpl`)解析 · 调研结论与实施现状

> 目标功能: **导入一段录像 → 自动生成线路**。
> 规则: 玩家在录像里可能换乘多辆载具 —— **出生开始记录, 被击毁停止; 重生则开始第二条**。
> 本文分两半: **§0 现状速览** + §1–§2 公开资料调研 + §2.4–§8 我们自己实测出来的东西。
> 全过程**未读取任何游戏文件**(只用用户提供的回放副本); 按仓库约定, 读游戏文件必须先征求用户同意。

## 1. 录像文件是什么样的

- 游戏录像(`.wrpl`)本质是**网络包记录**: 固定头 + 设置块 + 压缩的包流(+ 结束后的结果块),
  不是文本/JSON, 但**格式已经被人完整逆向并写成文档**(见 §2.1);
- 服务端录像(World War、锦标赛、自定义对局的服务器录像)是**分段**的:
  一个目录下 `0000.wrpl`、`0001.wrpl` … 分别对应时间片, 目录名是录像 id 的十六进制;
- 客户端录像就是单个 `.wrpl` 文件(游戏内「Replays」目录里那个);
- 包流在旧版本是 **zlib**, **2.59 起改成 zstd** —— 只用 zlib 的解析器会直接报 `incorrect header check`,
  所以要按版本(magic)分支处理。
- 因此"能不能解析"的答案是: **能**, 头部几乎免费, 位置需要写一个不大的包流解析器。

### 2.1 ⭐ 格式文档: `FURRO404/WT_KNOWLEDGE_DOCS`(最重要)

<https://furro404.github.io/WT_KNOWLEDGE_DOCS/03-replays/>(+ 第 09 章坐标/热力图)

这是社区整理的战雷逆向知识库, 第 03 章逐字段(含字节偏移)写清了 `.wrpl`:

| 项 | 内容 |
|---|---|
| 文件标识 | 偏移 0 = `header` `0x1000ACE5`(磁盘上 `E5 AC 00 10`) |
| 格式版本 | 偏移 4 = `magic`, 旧为 `0x00018C0B`(即大家说的 "18c0b"), **2.59 起为 `0x00018C1C`** |
| 固定头 | **1234 字节**, 含 `level_path`(地图)、`mission_name`、`gameType`、`start_time`、`player_count`、`session_id`(同一局所有分段共享)、`replay_part_number`、`settings_blk_size`、`footer_blk_offset` 等 |
| 区段布局 | `[0,1234)` 头 → `[1234, 1234+settings_blk_size)` 设置 BLK → 包流 → 结果 BLK(登录后才有) |
| 包流 | 整体的 **zlib** deflate 流(**2.59 = zstd**, 以 `28 B5 2F FD` 开头) |
| 包结构 | 变长长度前缀 → `uint16` 类型 → 时间戳(低位 `0x10` 置位则**继承上一条**的时间) → 载荷 |
| 包类型 | 0 EndMarker / 1 StartMarker / **2 AircraftSmall(飞机状态)** / 3 Chat / **4 MPI(含单位移动与战斗消息)** / 5 NextSegment / 6 ECS / 7 Snapshot / 8 ReplayHeaderInfo |
| **地面载具位置** | 在 **MPI(类型 4)** 包里: 包首固定字节模式 → 压缩实体 id → 紧接 3 个 little-endian **float64**(字节偏移 11/19/27) = 世界坐标 XYZ |
| 飞机位置 | 类型 2 包(飞行模型记录), 位置/姿态为量化 `int16`(`netutils::UNPACKS`, 如角度 scale = π) |
| 击杀/命中 | MPI 载荷以 `02 58 58 F0`(击杀)、`02 58 56 F0`(受击)、`02 58 18 F1`(自己命中)开头, 后跟 32 字段表 |
| 服务器分段录像 | 同 `session_id`; **偶数为状态段、奇数为包流段**(1,3,5… 连续); 每段各自解压、各自独立时间轴, 只能拼包列表不能拼字节流; 只有最后一段带结果 BLK |
| 客户端录像 | 单文件; 老版本 `0x00018C0B`; 新的 `0x00018C1C` 里 ECS 的 uid 关联解不出来(但类型 2 飞行流仍可用) |

### 2.3 对我们的价值

- 头部那几项价值不小, 而且**不用碰包流就能拿到**:
  - `level_path`(如 `levels/avg_guadalcanal.bin`)→ **自动得到地图名**(我们的地图缓存目前只能人工命名, 见 `8111使用经验.md` §3.6);
  - `mission_name` / `gameType` / `environment` / `weather` → 可写进线路备注, 甚至用来**校验模式**(和我们的战区数判定互相印证);
  - `session_id` / `replay_part_number` → 识别同一局的分段;
  - 结果 BLK 里的 `player` 列表(`name`/`clanTag`/`userId`/`team`/`kills`/`deaths`/`score`)→ 直接给线路配上"谁、哪队、战绩"。
- 位置解析**可以只做最小集**: 我们只要地面载具的 XYZ 轨迹 → 只解 **MPI(类型 4)里的地面移动记录**(固定模式 + 3×float64),
  不必碰 ECS 全套、飞机、传感器、导弹引导头这些(wrpl-inspector 那套解析器里我们只需要 `ground movement` 一个模块)。
- **世界坐标 → 地图像素**: 知识库第 09 章专门讲坐标与热力图换算, 与我们要做的"轨迹画到 `/map.img` 上"完全同题。

> 本节三条**均已落地**(2026-10-27): `level_path` → 回放关卡代号(见 CHANGELOG 的
> 「地图身份 = 图片哈希 + 可改的回放关卡代号」); 位置只解 MPI 地面流与飞机流;
> 归一化改走 8111 校准(比 datamine 边界更准)。
> 一处修正: 结算表的 `userId` 实测是**空串**(见 §2.4), 所以玩家身份改用 `name` 对齐。

### 2.4 ⭐ 结算表(results BLK) —— 已完整解出(2026-10-27)

位置: **最后一个分片**的 `results_offset` 之后, 一直到文件尾。
实测 `Abandoned factory`: 偏移 2,639,396, 17,056 字节; `Maginot Line` 等三份回放同样成立。

**FAT BLK 布局**(逐字段验证: 块数、字段数、嵌套表长度都恰好用尽, 零剩余):

```text
+0    type        = 0x01 (FAT)
      n_names     ULEB
      names_size  ULEB
      names       names_size 字节 (NUL 分隔的串表)
      n_blocks    ULEB
      n_fields    ULEB
      params_size ULEB          ← 这里**只有 3 个 ULEB**, 没有"参数个数"
      params      params_size 字节 (字符串池)
      fields_def  n_fields × 8   `name_id u24 LE | type_id u8 | data u32 LE`
      nested      剩余全部       每块 = `ULEB name_id | ULEB 字段数 | ULEB 子块数
                                        | (子块数>0 ? ULEB 首子块 : 无)`
```

类型编码: `0x01` Str(值 = 字符串池偏移) / `0x02` Int(内联 i32) / `0x03` Float(内联 f32) /
`0x04..0x06` Float2..4 / `0x07..0x08` Int2..3 / `0x09` Bool(内联) / `0x0A` Color /
`0x0B` Float12 / `0x0C` Long(内联 i64)。Float2+ / Int2+ / Float12 的值也在字符串池里。

**三个必踩的坑**:

1. **只有 3 个 ULEB**。按"块数/字段数/参数个数/参数字节数"读 4 个, 字段定义表就整体错 1 字节,
   字段名全变成 `0x10000` 的倍数(`<bad fname #65536>`)。铁证: 偏移 684 处
   `ba 02  e2 0c  d3 11  73 75 63 63 65 73 73` = `314 / 1634 / 2259`, 紧跟的 `73` 是
   `"success"` 的首字母 —— 那是字符串池的开头, 不是 ULEB。
2. **块名 1 基, 字段名 0 基**。`name_id == 0` 是根块; 但字段定义的 `name_id` 从 0 开始。
   混用会整体偏 2 项(块名全变成下下个)。
3. **`params_size` 是字节数, 不是条数**。115 那种小数值一定读错了。

**结构**(314 块 / 1634 字段 / 73 个名字, 服务器回放 32 人局):

```text
root                 status='success', timePlayed=429.82
├─ player ×32        每人 22 字段
└─ matchingInfo ×32  子块名 = 数字 **userId**(如 103416866; 子块按 userId 升序)
   └─ crafts_info ×32
      └─ arrayN ×4~10  { name, rank, mrank, rankUnused }
```

`player` 的 22 个字段(顺序即字段定义表顺序):

```text
name clanTag kills groundKills humanKills navalKills teamKills aiKills aiGroundKills
aiNavalKills assists deaths captureZone damageZone score awardDamage missileEvades
shellIntgerceptions userId squadId autoSquad team
```

实测输出(节选):

```text
 #  name              clanTag    kills groundKills deaths score  team autoSquad squadId
 0  核子将军 程世涛    .Flos.     0     1           2      697    2    False     4103
 1  Hupprecht3648     =PerIi=    1     3           3      1088   1    False     4100
 2  -Alyosha-         -TMAG-     0     5           0      1462   1    True      1001
```

**`crafts_info` 到底是什么(已排除一个常见误解)**:

* 每人一个队列, 每项 `{name, rank, mrank, rankUnused}`, `name` 是载具内部 id(`su_30sm2`、
  `ussr_t_90m_2020`、`fa_18e_block_2`…), `rank`/`mrank` 是权重;
* **`mrank = BR × 4`**: 36 → 9.0, 35 → 8.75, 33 → 8.25, 29 → 7.25, 23 → 5.75(实测吻合全部 32 人);
  `rank = floor(mrank / 4)`;
* **`rankUnused` 不是"这辆车出过场"**。实测 32/32 位玩家都**恰好 1 条** `rankUnused=False`,
  而且**总是队列里 `mrank` 最高的那台**(32/32 命中)。有人死了 4 次也只有 1 条 False。
  它更像是"这台车代表本队列的出战权重"。
* 结论: 结算表**给不出**"谁重生了几次、什么时候重生"。`deaths + 1` 只能当**校验上界**用。

**还差一个字段**: `player.userId` 解出来是**空串**(类型被标成 Str, 字符串池里指向空串)。
`matchingInfo` 的子块名就是 userId, Slot 包的 `player_id` 也是同一个数字 —— 用**玩家名**做桥
能对上(`probe_blk_join.py`: 6/6 全部命中), 但 32 人里只有 6 人的 Slot 包带 `player_id`。
**不影响使用**: 名字已经能把玩家对齐。字段位置与原始定义见 `probe_results_blk.py`。

### 2.5 两块还没解开的硬骨头

**① `0xF11A` 导弹/炮弹同步 —— 占 20.5% 字节(5524 包)**

已验证: 载荷 `02 58 1A F1`, `+4` 是 ULEB 总位长(如 993), 之后字节对齐;
记录本体 99 bit **完全正确**: `hasGuidance(1) noExtraTail(1) entity(u32 LE) isRaw(1)`
+ `isRaw ? 3×f32 : 2×u32 反量化(±15000 m)`; 首条记录解出
`entity=1280003, (1769.9, 3933.7, 5797.0)`。

卡住的地方: `noExtraTail == 0` 之后那段**尾部是变长的** —— 同样 `count=1` 的包, 尾部长度有
330/870/945/953 位。把尾部起点在 123..523 位上扫、再乘 4 种模型, **没有一种能恰好用完
`nbits`**。上游也没有参考(公开分支里没有对应实现)。

**② ECS 组件增量 `0x20`/`0x21`/`0x22` —— 占 23.9% 字节**

`tools/ref/ecshashes.json` 已经把 217 个 cid 对到组件名, 但**块内组件顺序 ≠ 模板 `comps` 顺序**:
`unit__className`(模板 idx 9)与 `unit__missionName`(idx 21)在块里是相邻的。
按模板顺序逐值解析必定错位。想解出真实顺序只能靠 delta 索引表, 而实测 **1306/1307 个创建块
`compCount == 0`**, 唯一的 `compCount=119` 那块 `tcc=30` 直接越界 —— 数据本身就没给顺序。

于是现在的做法是"**用块内明文串认型号/出生组名 + 用位置流的 uid 集合现场标定 uid 偏移**",
实测三份回放里每个有采样的 uid 都有 ECS 档案(0 个孤儿), 83 台玩家载具全部对上。
它够用, 但不是严格解析 —— 见 §8.2 的三条残余风险。

| 战区/模式归类 | ✅ 模式已落地, 坐标仍缺 | 模式按**战区个数**判(3/2/1); 战区坐标在关卡对象包里是占位值, 用 8111 的 `capture_zone` |

建议新增:

- `RouteRecord.source`: `"live"`(8111 实时录制) / `"replay"`(录像解析), 侧栏用不同前缀或颜色区分;
- `RouteRecord.replay_id` / `replay_time`: 便于追溯来源。

> 落地时这两项**没有加字段** —— 回放导入的条目天然单独成层(侧栏按地图/模式分组),
> 不需要靠字段区分来源。

## 4. 实现路线建议(分三步, 先易后难)

> ✅ 三步都走完了(2026-10-27): 第一步(头+BLK)、第二步(位置包流)**已在用**;
> 第三步(分段成线)已成主路径, 剩下的边缘情况见 §8.2。本节只作当初的路线留档。

1. **第一步(低风险, 立刻可做): 只读固定头 + 设置/结果块**
   纯 Python(标准库 `struct` + `zlib`/`zstandard`)即可:
   - 头部: `level_path`(地图名)、`mission_name`、`gameType`、`environment`、`weather`、`start_time`、
     `player_count`、`session_id`、`replay_part_number`, 以及那条"是不是服务器录像"的判定
     (偏移 742 = `0x5A`, 或 `playerNo == 0x80000000`);
   - 设置/结果 BLK 是 Dagor `BLK` 格式, 可用 `kotiq/blk` 之类的现成库读;
   - 界面: 「导入录像…」→ 显示"这张图、什么模式、几个人、谁开过哪些车"的信息面板。
     这一步能直接解决**地图名靠人工命名**的老问题。
2. **第二步: 位置包流解析(核心工作量, 但只需最小集)**
   我们只要**地面载具的 XYZ 轨迹**, 所以只需:
   - 按 magic 选解压器(zlib / zstd)→ 按长度前缀拆包 → 读类型与(可继承的)时间戳;
   - 只处理 **MPI(类型 4)** 里的地面移动记录: 固定字节模式 + 压缩实体 id + 3×little-endian float64;
   - 可选: 解析击杀(`02 58 58 F0`)拿"谁在哪被击毁"。
   不需要碰 ECS 实体系统、飞机飞行模型、传感器、导弹引导头这些大工程。
3. **第三步: 分段成线**
   - 判定"这条命"的开始/结束: 优先用**击毁消息 / 载具切换**; 退路是"位置瞬移回出生点/实体消失";
   - 每条命 → 一条 `RouteRecord`(起点 = 首次出现位置, 终点 = 最后位置), 用**载具名**命名,
     时间以该命第一次出现为 00:00;
   - 同一录像的多段(`0000.wrpl`…)按 `replay_part_number` 排序后拼包列表(每段独立解压、独立时间轴);
   - **世界坐标 → 地图像素**(知识库第 09 章有现成公式):
     - 世界系: 右手系、单位米, `x` = 西→东, `z` = 南→北, `y` = 海拔(坦克地图只用 `x`/`z`);
     - 每张图的边界来自 datamine 里该 level 的 `.blkx`(字段 `mapCoord0/1`、`tankMapCoord0/1`,
       即空地两套外框), **可直接从公共镜像按 level 名拉**, 不必碰游戏目录:
       `https://raw.githubusercontent.com/gszabi99/War-Thunder-Datamine/refs/heads/master/aces.vromfs.bin_u/<level>.blkx`;
     - 归一化(地图视图向下增长, 所以 `z` 要翻):
       `originX = tankMapCoord0.x - 0.5`、`originZ = tankMapCoord0.z + 0.5`、
       `areaW = |x1-x0|`、`areaH = |z1-z0|`;
       反算: `fracX = (worldX - originX) / areaW`、`fracZ = 1 - (worldZ - originZ) / areaH`;
     - 这样算出的 0~1 分数正是我们 `/map.img` 上画点要的坐标。

## 5. 风险与注意

- **版本会变**: 2.59 换了 magic 与压缩算法; 上游 `WrplReplayParser` 也只声明支持单一版本(18c0b)
  —— 所以我们的解析器要**对版本显式报错**, 不要静默出错;
- **客户端录像 vs 服务器分段录像**要分开处理(多段规则: 偶数为状态段、奇数为包流段, 只有末段带结果);
- 客户端录像里 **ECS 的"玩家↔单位"关联在新版解不出来**(知识库实测): 若拿不到名字,
  可先用"单位 id + 载具名"给线路命名。**结算表能补上名字**(32/32), 但它的 `userId` 是空串,
  所以别指望用 userId 去 WT Live 查昵称(旧计划已废);
- **反作弊风险**: 阅读录像副本是纯离线行为、不注入游戏、不写游戏目录; 但仍按仓库约定 **先征得你同意**。

## 8. 这些数据对现有软件到底有什么用

> 先说清楚边界: **回放解析只服务跑图线路测试器**。黑名单助手读的是 8111 实时接口,
> 与回放无关。下面说的"应用"都指跑图测试器。

### 8.1 结算表能直接改善的四件事

| # | 现状(靠什么) | 有了结算表之后 |
|---|---|---|
| 1 **阵营** | `uid_pid → Slot.team`; `uid_pid` 来自击杀(覆盖 54/94) + ECS 出生组名公式 | **权威 team, 32/32**。可交叉验证并纠正 —— "线从敌方重生点出发"这类错误直接消失 |
| 2 **玩家名** | Slot 包(32 人有名字, 昵称可能为空/截断) | 结算表 32/32 全量, 中文/空格/特殊字符都正常 |
| 3 **每条线的终点** | 击杀时刻 + ECS 销毁 + 45 s / 200 m 两个启发式 | `deaths` 是**独立的第三方核对**: 这位玩家最多几条命。多切/少切立刻能发现并报账 |
| 4 **对局权重** | 无 | 每人队列 + `mrank = BR×4` → 条目上能标"这局 8.7", 也能筛同权重对局对比 |

实现量很小: 结算表解析约 200 行纯标准库(`probe_results_blk.py` 已是可用实现),
接到 `replay_import` 只是多读一个尾段 + 一张 `name → (team, deaths, lineup)` 表。

### 8.2 "玩家重生路径"的 bug 能不能彻底解决 —— 分三类看

| bug 类型 | 现在的成因 | 结算表能治吗 | 真正可靠的解法 |
|---|---|---|---|
| **线挂错人 / 挂错队**(一个人下面 4 条线、有一条从敌方重生点开始) | `uid → 玩家` 靠击杀反推 + 槽位公式 | ✅ **能**: team/名字是权威值, 再用"型号是否在该玩家队列里"做二次校验 | 结算表 + 队列型号交叉校验 |
| **一条线里串了两台车**(地图上一条瞬移直线) | 回放 `uid` 是"场上槽位", 会复用; 现在靠 45 s 间隔 / 200 m 瞬移两个启发式切开 | ❌ **不能**(结算表没有时间) | ECS 创建包的 `born_t` 已给出**精确**窗口 —— 启发式只该当兜底 |
| **幽灵线拖到对局结束**(残骸一直上报位置) | ECS 不保证对载具发 `0x26`; 现在用击杀时刻截断 | ⚠️ 只能核对总条数 | 击杀时刻(已有)。**玩家不是被打死**(弃车/坠毁/出界)时仍没有终点 —— 这是真正剩下的缺口 |
| **同一玩家两台同型号车被并成一条** | 曾经按 uid 编号 | ⚠️ 无时间信息 | ECS 两次创建 = 两台车(已修) |
| **中途加入/退出导致槽位错位** | 出生组名公式 `K` 要现场拟合 | ✅ **能**: team 独立可得, 不必靠公式反推 | 结算表 |

**一句话结论**: 结算表能治"**是谁的车**"(归属/阵营/型号), **治不了"什么时候重生"**。

而"什么时候"在回放里的唯一权威来源是 **ECS 创建包的时间戳 + 出生组名** —— 它已经能用,
但稳健性卡在 §2.5 ② 那个"块内组件顺序未知"上。具体是三条残余风险:

1. **uid 靠偏移标定**: 少数创建块的组件值布局差 1 字节 → 现在用"二次标定"从源头修,
   实测 83/83 台玩家载具都正确, 但地图/版本一变就要重新核对;
2. **没有出生组名的实体**(UCAV / 玩家放的无人机)只能靠"它自己击杀过谁"定主人,
   从不出手的无人机就没有主人;
3. **终点缺失**: 没被击杀的车, `died_by` 会兜底成"活到对局结束"。

所以务实的做法不是"重写 ECS 解析", 而是 **让结算表当裁判**: 用 `deaths` 与 `队列型号`
自动校验每一条线, 对不上的那几条明确标出来(或在导入报告里报账), 剩下的绝大多数不用动。
这比继续凿 `0x20` 增量包划算 —— 上游三个项目都在这一块退回了锚点法
(Go 版作者在源码里直接留了 `FUCKEDFUCKEDFUCKEDFUCKED`, WTACRP 也退回锚点)。

### 8.3 顺带能拿到的两个小能力

* **玩家名直接用结算表的** → 侧栏不再出现 `uid120` 这种条目;
* **队列 BR** → 同一张图不同权重的对局可按 `mrank` 分组对比(机场位置会随权重变)。
