# 战争雷霆录像(`.wrpl`)解析调研 · 用于"从录像自动生成线路"

> 目标功能: **导入一段录像 → 自动生成线路**。
> 规则: 玩家在录像里可能换乘多辆载具 —— **出生开始记录, 被击毁停止; 重生则开始第二条**。
> 本文只记录**公开资料的调研结论**(未读取任何游戏文件;按仓库约定, 读游戏文件必须先征求用户同意)。

---

## 1. 录像文件是什么样的

- 游戏录像(`.wrpl`)本质是**网络包记录**: 客户端与服务端之间收发的数据包按顺序存下来,
  前段是**明文/半明文头部**, 后面是**压缩(zlib/deflate)的包流**;
- 服务端录像(World War、自定义对局的服务器录像)是**分段**的:
  一个目录下 `0000.wrpl`、`0001.wrpl` … 分别对应时间片, 目录名是录像 id 的十六进制;
- 客户端录像就是单个 `.wrpl` 文件;
- 因此"能不能解析"的答案是: **能, 但要自己实现包流解析**, 不是简单的文本/JSON。

## 2. 公开项目调研(2026-10-06)

| 项目 | 语言 / 授权 | 状态 | 能给什么 | 结论 |
|---|---|---|---|---|
| [`LivingTheDagor/WrplReplayParser`](https://github.com/LivingTheDagor/WrplReplayParser) | C++(+Python 绑定) / MIT | 活跃(近几月仍在改), 支持录像版本 **18c0b** | 战斗消息、聊天、全局对象、**玩家/载具实体信息**, 以及**飞机(FMSync)与坦克(GMSync)的位置** | **唯一确认能取"位置"的**, 但要编译(Windows 需 MSYS2/MinGW) |
| [`nilshellerhoff/warthunder-replay-parser`](https://github.com/nilshellerhoff/warthunder-replay-parser) | Python / MIT | ~5 年前, 基本停更 | 只解析**头部**: `level`、`mission_file`、`mission_name`、`time_of_day`、`weather`、`time_of_battle`、`num_players`、`players[{player_id, vehicles[]}]` | 纯 Python 可参考(**头部解析 + 多段录像合并**的处理方式), **拿不到位置** |
| [`Yay5379/wt_client_replay_parser`](https://github.com/Yay5379/wt_client_replay_parser) | Python | 2025 年, 作者声明"不再更新", 借鉴上面两个 | 同上(头部为主) | 可当参考实现读一读 |
| [`klensy/wt-tools`](https://github.com/klensy/wt-tools) | Python | 老 | 老格式录像 | 作者自己说明**不支持分段的服务端录像** |

要点:

- 头部那几项对我们的价值也不小:
  - `level`(如 `levels/avg_normandy.bin`)→ **可以自动给出"地图名"**(我们的地图缓存只能靠人工命名, 见 `8111使用经验.md` §3.6);
  - `mission_name` / `time_of_day` / `weather` → 可写进线路备注;
  - `players[].vehicles[]` → **载具序列**(换乘顺序), 可直接给每条线路命名(与"一命一条"天然对应)。
- 位置必须走包流: 坦克/飞机的位置在 **GMSync / FMSync** 包里, 且是**增量编码**(基准 + 变长差值),
  这就是 WrplReplayParser 之所以是 C++ 且工作量大的原因;我们自己实现需要:
  1. 录像头的段表/压缩块拆分(必要时 zlib 解压);
  2. 包读取器(长度前缀 + 包号 → 分发表);
  3. `Player`/实体建立(把 `player_id` 与载具实体对上)+ 坐标解码;
  4. 时间轴(包的时间增量 → 秒)。

## 3. 我们这边还需要什么(前置条件)

| 需求 | 现状 | 说明 |
|---|---|---|
| **世界坐标 → 地图像素归一化** | ❌ 缺 | 需要地图边界。8111 的 `/map_info.json` 有 `map_min`/`map_max`(还有 `map_generation`), 与 `/map.img` 配对 → **顺手把它也缓存进 `maps/`**(每个地图存一份, 录像解析时用) |
| 地图身份 | ✅ 有 | 我们按 `/map.img` 的 sha1 认地图; 录像里的 `level` 字符串可与"战斗中缓存过该图"的名字对上 |
| 线路模型 | ✅ 有 | 生成的结果直接写成现有 `RouteRecord`(points/marks/vehicle/duration), 落进 `routes.json` 复用四层分组、回放、对比 |
| 战区/模式归类 | ✅ 有 | 录像里战区是实体, 但我们未必能稳定解出 —— 保守做法: 生成的线路挂在**"未知模式 → 未知位置"**, 或按 `level` 只挂到地图层 |

建议新增:

- `RouteRecord.source`: `"live"`(8111 实时录制) / `"replay"`(录像解析), 侧栏用不同前缀或颜色区分;
- `RouteRecord.replay_id` / `replay_time`: 便于追溯来源。

## 4. 实现路线建议(分三步, 先易后难)

1. **第一步(低风险, 立刻可做): 头部解析**
   纯 Python 读头部 → 自动得到 `level`(地图名)、`mission_name`、天气/时段、玩家与**载具序列**;
   界面里先做一个「导入录像…」-> 显示"这段录像里有谁、开过哪些车、什么图"的信息面板。
   这一步就能让"手动按载具分段补录"省不少事, 且完全不碰包流。
2. **第二步: 位置包流解析(核心工作量)**
   参考 `WrplReplayParser` 的包定义实现 Python 版(GMSync/FMSync + 实体建立),
   或直接**用它的 Python 绑定**(需先编译, 分发会变复杂, 不适合塞进 PyInstaller)。
   产物: `(t, player_id, vehicle, x, y)` 序列 —— 已足够画轨迹。
3. **第三步: 分段成线**
   - 判定"这条命"的开始/结束: 优先用**击毁/出生消息**(battle messages);
     退路是"实体消失/位置瞬移回出生点/载具类型变化";
   - 每条命 → 一条 `RouteRecord`(起点 = 首次出现位置, 终点 = 最后位置), 用**载具名**命名,
     时间以该命第一次出现为 00:00;
   - 同一录像的多段(`0000.wrpl`…)按时间轴拼接;
   - 可选: 与"我们自己用 8111 录的"同图同版本线路放在一起对比。

## 5. 需要用户拍板 / 提供的东西

1. **授权读样本**: 按仓库最高优先级约定(见 `.github/copilot-instructions.md` §0),
   开发前需要你**明确同意**我读取一份录像文件(建议给我**一处副本**, 我只读副本,
   绝不去碰 `Documents/My Games/WarThunder/Saves/**`、`cache/`、游戏安装目录);
   - 需要知道: 这段录像是**本地客户端录像**还是**服务器分段录像**(两者格式不同);
   - 顺便: 录像对应的**游戏版本号**(录像版本号如 `18c0b` 决定了包结构, 版本不符会解析失败)。
2. **选择实现方式**:
   - A. 纯 Python 从零实现(可控、能打包, 但要写包解析 + 跟着游戏版本维护);
   - B. 用/移植 `WrplReplayParser`(省事但引入 C++ 构建与分发问题);
   - C. 先做第一步(头部信息), 位置解析以后再说。
3. **分段判据**: 用"击毁消息"还是"载具切换/重生"来切分(见 §4.3), 以及被击毁后
   "换车重生"是否算同一条(默认算**新的第二条**)。
