# 8111 本地接口 · 使用经验

> 本项目(黑名单助手 + 跑图线路测试器)在开发中通过**实测**得到的 8111 使用经验汇总。
> 接口的原始字段参考(第三方社区文档)见 `docs/wt8111/`;进出场与昵称相关结论见
> `docs/8111自定义对局实测分析.md`;跑图测试器的数据来源见 `docs/跑图线路测试器.md` 第 6 节。

---

## 1. 基本信息

- 地址: `http://localhost:8111`,**游戏启动即监听**,无需任何设置(战争雷霆内置本地服务);
- 除 `/map.img` 返回图片外,其余端点均返回 JSON;
- 中文/UTF-8,响应头带 `Access-Control-Allow-Origin: *`;
- 端口仅在**游戏运行期间**可用;退出游戏即失效。

---

## 2. 端点清单(实测)

| 端点 | 内容 | 本项目用途 |
|---|---|---|
| `/indicators` | 载具与仪表(`type` `speed` `gear` `rpm` `army` …) | 载具名、速度 |
| `/map_obj.json` | 地图对象数组(玩家/地物/战区) | **玩家坐标**、朝向、**战区(模式判定)** |
| `/map.img` | 地图卫星图(**JPEG**) | 地图底图 |
| `/map_info.json` | 地图几何与网格(含 `valid`) | **进出场判定**、坐标换算 |
| `/mission.json` | 任务状态与目标 | 辅助(见 §3.4) |
| `/hudmsg` | 击杀/伤害消息 | 昵称收集 |
| `/gamechat` | 对局聊天 | 昵称收集 |
| `/state` | 空战仪表 | 陆战返回 `{"valid": false}`,不适用 |

## 3. 关键实测结论

### 3.1 玩家坐标(最容易踩坑的一点)

玩家出现在 `/map_obj.json` 里,但**靠 `icon == "Player"` 标识,不是靠 `type`**:

```json
{"type":"ground_model","icon":"Player","x":0.536519,"y":0.181914,"dx":-0.673497,"dy":0.73919}
```

- `type` 是**载具类别**(陆战 `ground_model`,空战 `aircraft`),不是 `"player"`;
- `x`/`y` 为 **0~1 归一化坐标**,`dx`/`dy` 为单位方向向量(可画朝向);
- 同一次实测中 `map_obj.json` 共 54 个对象:玩家 1 个,其余是 `respawn_base_tank`(40)、
  `airfield`(6)、`capture_zone`(3)、`respawn_base_fighter`(2)、`respawn_base_ucav`(2)
  → **必须按 `icon` 精确筛选**,绝不能"取唯一一个带 x/y 的对象";
- 地物(如 `airfield`)用 `sx/sy/ex/ey` 表示线段,数值**可以超出 0~1**(位于地图外);
- **自定义房间同样能取到玩家坐标**(2026-10-06 实测),此前"自定义对局无玩家对象"的说法
  只对*其他玩家*成立。

### 3.2 地图图片与坐标换算

- `/map.img` 实测为 **JPEG**, **2048 × 2048**(但也见过 1024² / 4096², 见下);
- 与 `/map_info.json` 的 `map_max`/`map_min`(实测 `[2048,2048]` / `[0,0]`)一致;
- 换算:**像素 = 归一化坐标 × 图片尺寸**,方向与图片一致(y 向下),无需翻转;
- `map_info.json` 实测字段:`grid_size` `grid_steps` `grid_zero` `hud_type`
  `map_generation` `map_max` `map_min` `valid`;
- ⚠️ 打包分发时**必须保留 Qt 的 JPEG 解码插件**(`qjpeg.dll`),否则地图无法显示
  (见 `tools/trim_qt.py --keep-imageformats`)。

#### ⚠️ 同一张地图会以**不同分辨率**发过来(2026-10-09 实测)

**客户端改不了分辨率**: 逐项试过 `/map.img?size=2048`、`?width=&height=`、`?w=512`、
`?zoom=1`、`?type=tank` —— **全都返回同一张图**(同样的字节数与尺寸, 参数被忽略)。
官方页面的用法也印证了这一点: 它 `map_image.src = '/map.img?gen=' + newMapGen`,
`gen` 只是**防缓存**; 它自己的“地图变大变小”是 canvas 端的 `map_scale/map_pan`
(`ctx.drawImage(map_image, 0, 0, canvas.width, canvas.height)`), 跟服务端无关。
⇒ 分辨率由**游戏侧的缩略图纹理代数**决定(`/map_info.json` 的 `map_generation` 会跟着变)。

**不要**拿字节哈希当地图身份 —— 同一张图换个分辨率, 字节就全变了:

| 缓存文件 | 字节数 | 尺寸 | 说明 |
|---|---|---|---|
| `372ce29b0767.jpg` | 253489 | 2048×2048 | 同一张图(货运港口), 先缓存到的 |
| `0fc34e933121.jpg` | 78090 | 1024×1024 | 同一张图, 后来 8111 发的是这个 |

- 已知出现过的分辨率: **1024² / 2048² / 4096²**(4096² 样本: 爱尔兰·灰烬之川, 601 KB);
- 内容对比(实测, 见 `tools/map_similarity.py`):
  - **同图**换分辨率 + JPEG 重压(0.25~1.0 倍率 × q60~95, 135 份): 64×64 灰度平均差 ≤ **0.60**,
    结构哈希汉明 ≤ **372**(共 4032 位);
  - **不同图**(9 张真实地图 36 对): 灰度 ≥ **11.97**, 汉明 ≥ **1813**;
  - **最坏情况**: 同一张 4096² 大地图的 12 个不同区域裁切(66 对): 灰度可以低到 **2.91**(很像!),
    但汉明 ≥ **1776** → 靠**结构哈希**区分, 单看灰度会被骗。
- ⇒ 地图身份要用**与分辨率无关的内容指纹 + 结构哈希**(阈值 1.2 / 800, 两边各约 2 倍余量)。

#### 战局外返回的是 "?" 占位图(2026-10-06 实测)

**不在对局/试车场**时 `/map.img` **依然 200 且内容合法**,但不是地图:

| 项 | 值 |
|---|---|
| 格式 / 大小 | `Content-Type: image/png`,**1519 字节** |
| 尺寸 | **128 × 128** |
| SHA1 | `ab516d02191d001d809253c346e8e3f93e13f136` |
| 内容 | 纯灰阶,仅 6 种颜色(64/68/72/109/115/128),中心 `(128,128,128)` |
| 外观 | 深灰底 + 浅灰 "?" |
| 同时 | `/map_info.json` = `{"valid": false}` |

存档样本:`docs/assets/8111_map_placeholder.png`。

补充实测(2026-10-09, 机库里查了两种情形, **都是“不在对局”**):

| 情形 | `/map.img` |
|---|---|
| 这一局还没进过对局 | **拿不到图片** —— 请求失败/不是图片, 连浏览器里也渲染不出来 |
| 进过对局又退出机库 | “?” 占位图(上表那张, sha1 `ab516d02…f136`) |

⇒ 黑名单助手 2026-10-09 起直接用**“能不能拿到真地图”**判定:
拿不到图片 **或** 拿到占位图 = 在车库(叠加层隐藏), 见 `wt81111g/garage.py`。

判据建议:

- 用 `/map.img` 判进出场最直接(机库两种情形都盖住);
  `map_info.valid` 也能用, 但它是**状态**字段, 退出对局后会残留一会儿;
- 地图身份: 用字节哈希做**文件名与变化检测**, 但**认身份要算内容指纹**
  (缩到 64×64 灰度, 平均灰度差 ≤ 4 视为同一张图) —— 否则同一张图的
  1024²/2048² 会被当成两张地图(2026-10-09 踩过);
- 同样别忘了过滤上面的占位图。

### 3.3 载具名(`/indicators` 的 `type`)

实测形如:

```
tankModels/germ_leopard_2a4_pzbtl_123
```

即 `xxxModels/` + 国家前缀 + 型号 + 部队/改型后缀。显示前建议:
先剔除 `xxxModels/` 前缀,再按需求美化(本项目: `Leopard 2A4 Pzbtl 123`)。

### 3.4 进出场判定

- `/mission.json` 的 `status` 在**机库 / 对局 / 退出后**都恒为 `"running"` → **完全不可用**;
- `/mission.json` 的 `objectives` 退出对局后**会残留一会儿**(上一局的目标),
  所以“running + 有目标”也会在机库里误判为对局;
- `/map_info.json` 含完整地图数据(`valid` 非 `false` 且有 grid/map 字段) ⇒ 在地图内;
  但同上是**状态**字段, 退出后也会残留一小会儿;
- ✅ **现行做法(2026-10-09)**: 直接看 `/map.img` —— **拿不到图片 或 拿到 “?” 占位图 = 在车库**,
  拿到真地图(≥1024²) = 在地图里; 只读图片前 16KB 即可判(占位图只有 1.5KB);
- ⚠️ 只判 `/map.img` 是否 200 **不够** —— 战局外它也可能返回 200(内容为 "?" 占位图, 见 §3.2), 
  必须比对指纹或看图片尺寸。

### 3.5 陆战 / 空战差异

| | 空战 | 陆战 |
|---|---|---|
| `/state` | 可用(姿态/发动机等) | `{"valid": false}`,不可用 |
| `/indicators` | 姿态、发动机、燃油… | `army`/`type`/`stabilizer`/`gear`/`rpm`/`crew_*` 等约 20 个键 |
| `/map_obj.json` | 玩家 `icon=="Player"` | 玩家 `icon=="Player"`(`type=ground_model`) |
| **`speed` 精度** | **有小数**(实测最多 6 位, 如 `89.072037`) | **整数**(实测 4000+ 样本无一小数) |

`speed` 单位为 km/h。陆战返回的就是**整数**(游戏内仪表同样取整, JSON 里写成 `0.000000` 只是格式化);
空战则是高精度浮点。因此显示速度建议**自适应**:有小数才显示小数位。

### 3.6 地图名:**8111 拿不到**(2026-10-06 实测)

想给地图起名/自动识别地图时会先想“接口里应该有地图名”, 结论是**没有**:

- 逐端点看过:`/map_info.json`(只有 grid/hud_type/map_generation/valid)、`/mission.json`
  (只有 `objectives` 文本, 如“占领并守住战区”)、`/state`、`/indicators`、`/map_obj.json`、
  `/hudmsg`、`/gamechat` 都**没有**地图名或任务名;
- 8111 **官方页面自己**只请求 `/map.img`、`/map_info.json`、`/map_obj.json`、`/mission.json`
  (把 `/` 拉下来数一遍即可确认), 也没有地图名接口;`/map.json`、`/mission_name.json`、
  `/battle.json` 等常见猜名端点都是 404;
- 客户端本地文件也没有:游戏目录 `.game_logs/*.clog` 是二进制/压缩(搜常见词 0 命中),
  `Documents/My Games/WarThunder/Saves/**/*.blk` 里搜 `levels/` 里的 164 个地图名(如
  `avg_*`/`air_*`)**一个都没出现**。

⇒ 只能**自己做地图身份**:按 `/map.img` 的**内容指纹**(缩到 64×64 灰度比相似度,
见 §3.2)归并同一张图的不同分辨率, 再用字节哈希当文件名/变化检测; 图片存本地缓存,
名字交给用户起一次(本项目: 菜单「地图」→「地图管理」)。
想自动识别就得维护“内容指纹 → 地图名”的对照表(社区共享或人工标一次)。

### 3.7 游戏模式:8111 不给模式名,但**战区点位能判定**(2026-10-06 实测)

同一张图会有多种模式(战区控制/战区攻陷/战区争夺),跑图线路不能混在一起。
8111 没有“模式名”字段,但 `/map_obj.json` 里每个战区都是一个对象:

```json
{"type":"capture_zone", "icon":"capture_zone", "color":"#174DFF",
 "x":0.432927, "y":0.556106,          // 战区中心(0~1 归一化, 同玩家坐标)
 "zone_id":0, "zone_label":"A", "zone_label_code":65}   // 65 = ASCII 'A'
```

- 实测(陆战**三战区局**): `capture_zone` **3 个**,`zone_label` 为 `A`/`B`/`C`,
  `zone_id` 0/1/2,坐标互不相同,三个都是白色(中立) —— **字母拿得到,可以直接标在图上**;
- 实测(陆战**两战区局**): `capture_zone` **2 个**(A/B),一个 `#fa0C00`(红, 敌方),
  一个 `#174DFF`(蓝, 我方) —— 正好对应“战区攻陷: 双方开局各拿一个”;
- 实测(陆战**一战区局**): `capture_zone` **1 个**(目标文本只有 1 个占位字形),
  玩家占领后它的 `color` 立即变成 `#174DFF`(我方) —— 归属是**实时**的;
- ⚠️ **归属变化时坐标不变**(战局内战区位置固定), 所以“只在坐标变化时刷新”的代码
  会永远显示第一次见到的颜色(本项目就踩过);判断“该重画了”要连 `color` 一起比:
- **`color` 是归属色**(站在**玩家视角**, 与全图对象同一个约定):

| `color` | 含义 |
|---|---|
| `#174DFF` 蓝 | 我方(ours) |
| `#fa0C00` 红 | 敌方(enemy) |
| `#ffFFFA` 白 | 中立/未被占领(neutral) |

  旁证: 同一局里 `respawn_base_tank` 为 `#174DFF` 与 `#fa0C00` **各 64 个**、
  `airfield` 各 3 个,蓝红成对出现;玩家自己(`ground_model`)是 `#faC81E` 黄色。
  颜色**会随时间变**(攻陷模式会被抢回去),所以不能拿它当模式指纹;
- **重生位置**(实测 2026-10-07 又一次确认): 一局 `respawn_base_tank` **128 个**,
  蓝红**各 64 个** —— 游戏里“重生区域”就是这一堆候选位置(重生时从中随机分配一个),
  所以它们成小片聚集而不是一个点;坐标是 **0~1 归一化**(与战区同一套,可直接画在
  `/map.img` 上)、颜色同样是归属色(蓝=我方、红=敌方);
- ⚠️ **空军重生点的坐标不是 0~1**: 同一次实测里 `respawn_base_fighter` 为
  `x=3.7141, y=3.6744`(红)/ `x=-2.8433, y=-2.8828`(蓝),还带 `dx/dy ≈ ±200` ——
  那是另一套单位。所以画到地图上时**只取地面载具**(`respawn_base_tank`),
  空军/无人机(`respawn_base_fighter` / `_ucav`)只记录不画;
- 重生位置也**随模式/版本变**: 同一张图的不同交战区域,双方重生位置不同 ——
  所以它跟战区布局一起按“地图 + 战区坐标指纹”存(见 `routes.json` 的 `map_zones[].spawns`);
- **归属色建议按通道判**, 别只匹配精确值: 老版本/空战里 8111 给的是 `#185AFF`(蓝)
  与 `#fa3200`(红), 而玩家自己的黄色是 `#faC81E` —— 本项目 `zones.side_of()` 先查已知值,
  查不到就按“蓝通道占优 = 我方 / 红通道占优 = 敌方 / 其余 = 中立”判(黄色因此不会被误判);
- `/mission.json` 的 `objectives[].text` **同样随模式变**, 且带彩色标记:
  - 三战区局: `"占\u200b领\u200b并\u200b守\u200b住\u200b战\u200b区 ╸,╹,╺"`;
  - 两战区局: 两条 objective —— `"攻占敌方战区 <color=@teamRedColor>╶</color>"` 与
    `"防守己方战区 <color=@teamBlueColor>╶</color>"`(蓝/红两条正好对应上面两个战区的归属);
  - 字符里的 `╶╸╹╺` 是**战区字母的占位字形**(游戏字体里渲染成 A/B/C), 字符之间还插了
    零宽空格(`\u200b`) → 解析麻烦、且随语言变, 所以只用它做辅助信号(比如对照归属);
- **同一张图的同一个模式还会有多个“版本”**(用户实践, 2026-10-06):
  战区控制/战区攻陷分**大地图 / 小地图**(交战区大小不同 → 战区位置不同);
  战区争夺的单个战区会从 **3 个位置**里随机 —— 所以“模式 + 战区位置”才是真正的
  比赛版本, 只按模式归类还不够;
  版本可以用战区**坐标串**当指纹 + 用**跨度**(战区间最大距离: 大地图跨度更大)
  给它们自动编号;
- **模式判定就是用战区数量**:3 → 战区控制、2 → 战区攻陷、1 → 战区争夺
  (**三种均已实测**:1 个时目标文本只有 1 个占位字形);
- **`blink` = 正在被占领**(实测字段存在, 值 `0`/`1`/`2`):8111 官方页面就是靠它让图标闪 ——
  `bv = blink==2 ? 快闪 : 慢闪`, 然后在 **`color[]` ↔ 纯黄 `[255,255,0]`** 之间插值;
  脉冲曲线 `exp(-(5t-2)^4)`, 周期 **2.0s**(blink=1)/ **1.2s**(blink=2);
  也就是说官方是“**在归属色基础上闪黄**”;
  注: 官方那样一闪就分不清归属, 本项目改成在**本阵营色**里做明暗脉冲(不掺黄);
- 战区**中心坐标串**是稳定的“模式指纹”(同一张图的同一模式,战区位置固定),
  所以 `(map_key, 战区坐标串)` 能把同图不同模式彻底分开; **指纹不含颜色/闪烁**;
- ⚠️ 战区**只在战局内**有(`/map_obj.json` 战局外是空数组),所以要让用户/程序
  在进入战局时把布局(含当时的归属色)存下来(本项目存进 `routes.json` 的 `map_zones`)。

## 4. 性能与可靠性注意事项

- **前台运行 ~40-50Hz、rtt ~10ms**(空战/陆战一致,高频采样脚本实测 10ms 间隔可得约 46Hz)。
- **数据真实更新率约 25Hz**(2026-10-06 统计 `speed_log_g1_run4.csv` 2072 样本):
  `rpm` 变化间隔 p50 = **40 ms** → 数据本身約每 40 ms 才更新一次;
  实测 46Hz 采样时**每个数据点被重复采約 1.85 次**。
  ⇒ **采样间隔取 40 ms 即与数据源匹配**, 再快只是重复采样。
  (注意: 不能用 `speed`/`gear` 衡量刷新率 —— 陆战 `speed` 是整数、`gear` 极少变,
  实测变化间隔分别只有 93 ms / 500 ms; `rpm` 是连续量, 才可靠。)
- ⚠️ **游戏失焦 / 切到后台时 8111 会显著变慢甚至请求超时**
  → **性能测试必须在游戏前台进行**,否则会得出"只有 0.5Hz"这种错误结论(2026-10-06 踩过)。
- 每轮完整刷新需要 **2 次请求**(`/indicators` + `/map_obj.json`),实测约 20ms ⇒ 理论上限 ~50Hz;
  想再快只能减少请求数(例如把 `/indicators` 降频,坐标每帧取)。
- `timeout` 建议 **0.3 ~ 1.0 秒**:8111 正常 rtt 仅 ~10ms,超时值设太大会让一次卡顿拖垮整轮轮询。
- `/map.img` 约 **230KB+**,**不可每帧请求** —— 应按需/节流(本项目每 2 秒且内容变化才刷新)。
- 任何请求失败都应视作"未连接"优雅降级,**不要把异常抛给 UI 线程**。

### 4.2 黑名单软件(WTBlackList)踩过的坑与待定方案(2026-10-10)

- **一律 `127.0.0.1`,不要 `localhost`**:Windows 上 `localhost` 可能先解析到 IPv6(::1),
  8111 只监听 IPv4 → 每次请求多一轮解析/重试,偶发直接吃满超时。1.0 曾经整仓库都在用
  `localhost`(config + `MonitorWorker` 默认参数),已改。
- **换局/换地图那几十秒 8111 本身会变慢**(实测 `mission` 2005ms 超时、`hudmsg` 1722ms,
  2 秒后恢复 34ms)。所以"请求失败"**不等于**"没有新消息/不在地图里":
  失败时保留游标、不改判定,连通性连续 3 次失败才按断线处理。
- **`/hudmsg` 的 id 跨局只增不重置**,`time` 字段语义不明(同一局内也不递增,不可靠)
  → 判"新增"只能靠 `id`,而且**不能用它回捞"进局前的击杀"**(试过,会把上一局的人误报)。
- **轮询频率会反过来影响游戏**:软件每秒轮询 `/hudmsg`+`/gamechat` 时,用户实测
  "刚进试车场打掉的第一辆靶车偶尔没有记录"(窗口里 id 连续、无缺口 = 游戏压根没生成那条),
  关掉软件反复打则一次不漏。把消息轮询降到 **3 秒一次**(`MonitorWorker.msg_interval`)后
  问题消失。**结论:宁可少打扰,不要抢着高频读。**
- **待定方案(用户提出,若再出现漏消息就上)**:**用 WebView2 在后台打开
  `http://127.0.0.1:8111/` 页面,8111 的查询全部交给页面自己的 JS,我们只解析页面**
  (定时 `evaluate_js` 读列表 DOM,按"文本+顺序"去重)。
  用户的理由:浏览器 JS 轮询从没观察到丢消息;8111 页面多年未变,HTML 脆弱性可接受。
  实现提示:2.0 已内置 pywebview/WebView2(昵称手动兜底在用),基础设施现成。
  注意:页面 JS 请求的还是同一批端点,游戏侧开销不会减少,只是"换成浏览器 JS 来发"。

### 4.1 提高轮询频率的实战做法(2026-10-06)

要让轮询真正跑到 40Hz,以下几点缺一不可(均已在 `route_recorder.py` 落实):

1. **用 `127.0.0.1` 而不是 `localhost`** — Windows 上 `localhost` 可能先解析到 IPv6(`::1`)
   再回退 IPv4,高频轮询下这笔开销很明显;实测脚本 `tools/probe_air_speed.py` 一直用 `127.0.0.1`。
2. **减少每轮请求数** — 单请求实测约 20ms,每轮 2 个请求上限就只有 ~25Hz。
   做法: `/map_obj.json`(坐标, 轨迹平滑的关键)每帧取; `/indicators`(载具/速度, 变化慢)
   **降频到每 4 帧一次** → 每轮平均约 1.25 个请求。
3. **大响应放独立线程** — `/map.img` 约 230KB,若在轮询线程里下载会周期性卡住整帧,
   应交给单独线程按需刷新(内容变化才更新界面)。
4. **超时取小值(0.5s)** — 8111 正常 rtt ~10-20ms;超时值过大会让一次偶发卡顿拖垮整轮。
5. **目标周期调度** — 不要"请求完再 sleep(固定间隔)", 那会把请求耗时叠加进去;
   应按"下一帧的目标时刻"算剩余等待(落后了就重置, 不累积滞后)。

## 7. 回放(Replay)模式实测(2026-10-21)

> 起因: 想在回放里"录下全场所有玩家的路线 + 每次击杀的发生/死亡位置"。
> **结论先说**: 8111 只给**当前观战方**的载具(任何视角都没有对方); 击杀消息**没有坐标**。

### 7.1 `/map_obj.json`: 可见集合随视角变

| 观战视角 | 对象总数 | 载具/飞机 | 构成 |
|---|---:|---:|---|
| 地面单位(普通) | 287 | 14 | 7 中坦 / 4 轻坦 / 1 歼击车 / 1 SAM + 自机; **0 飞机、0 防空** |
| 空中单位(Su-25) | 293~297 | 20~24 | 10 个**机场 AI 防空** + IFV/中坦/轻坦/SAM + 3~5 架飞机(地图切成空战图) |
| 地面单位 + 传感器视角 | 283~287 | 10~11 | 3 SAM / 2 轻坦 / 1 中坦 + 2 飞机 + 自机; **防空消失** |
| 切到敌方观战 | 287~293 | 11~15 | 敌方那一方的载具; 我方载具**消失** |

- **敌方载具在任何视角下都不出现**; 静态地物才是两方都列。
- 静态地物两遍完全一致: `respawn_base_tank` 256(128 蓝 + 128 红)、`airfield` 12
  (6 白 `#ffFFFA` + 3 蓝 + 3 红, 用 `sx/sy/ex/ey` 表示**跑道矩形**)、
  `respawn_base_fighter` 2、`capture_zone` 3。
- 只在空中视角出现的 10 个 `Airdefence` 位于机场旁一小片区域, **位置全程不变**(0 变化)
  ⇒ 是 AI 单位, 不是玩家, 录制时要过滤。
- `Player`(自机)的 `type` 会变: 观战地面车 → `ground_model`, 观战飞机 → `aircraft`
  ⇒ **识别自己只能按 `icon == "Player"`**, 不能按 `type`。
- `dx/dy`(朝向): 实测 **`Player` 与飞机条目有**, 其他地面载具**没有**
  ⇒ 它们的朝向只能由相邻采样点的位置差反推。

### 7.2 颜色语义(相对观战方)

| 色值 | 三通道和 | 含义 |
|---|---:|---|
| `#faC81E` 黄 | 480 | **自己**(Player) |
| `#174DFF` 蓝 | 355 | 友军(正常) |
| `#1839A7` **深蓝** | 248 | **重生保护中**(见 7.3) |
| `#39D921` / `#67D756` 绿 | — | 小队队友 |
| `#fa0C00` 红 | — | 敌方(回放里只出现在机场/重生点/战区等静态地物上) |
| `#abBEFB` 浅蓝 | — | 战区(未占领 / 中立; 战区颜色本身也有深浅档) |

- **深浅与距离无关**: 实测出现过"深蓝那辆是离自己最近的(归一化距离 0.008)",
  而飞得最远的两架飞机(坐标超出 0~1 范围)反而是亮蓝。
- 颜色是**相对观战方**染的(观战方 = 蓝系)⇒ 两遍录制合并时**不能按色值判敌我**。

### 7.3 深蓝 = 重生保护(重启回放实测)

连续采样(每 2 s 一次)统计"深色友军"数量:

| 时间 | 载具数 | 深蓝 | 亮蓝 |
|---|---:|---:|---:|
| 0.0 ~ 18.3 s | 9 | **8** | 0 |
| 20.3 s | 9 | 7 | 1 |
| 22.3 s | 11 | 3 | 7 |
| 28.4 s | 12 | 1 | 10 |
| 30.4 ~ 36.5 s | 14~15 | **3~4** | 10 |

- 开局全体刚重生 → **全深蓝**; 约 **20 s** 后成批转亮蓝(保护结束);
- 之后**新刷出来的车又是深蓝** ⇒ 深蓝 = 刚重生、处于保护中。
- 机制(用户说明): 重生后**不移动**时保护时间最长, **移动会缩短**保护时间;
  游戏未公开具体规则 ⇒ **使用时只需知道"深蓝 = 重生保护状态"**,
  不要试图用颜色精确推算剩余保护秒数。
- 保护到期是**分散**的(不是同一秒)⇒ 录制要**逐车记颜色**, 不能只看整批数量。

### 7.4 刷新率 = 游戏帧率(重要)

| 状态 | 游戏 FPS | 实测轮询 | 目标"变化率" | 间隔中位数 |
|---|---:|---:|---:|---:|
| 游戏挂后台(锁 30) | 30 | 30.0 Hz(32.5 ms/请求) | ~24 Hz | 33 ms |
| 前台(锁 100) | 100 | 73 / 93 / 97 Hz | 58~97 Hz | **10 ms** |

- 数据几乎**每次请求都在变** ⇒ 8111 按**游戏帧率**吐数据;
  之前测到的"30 Hz 上限"是**游戏被切到后台锁 30 帧**导致的, 不是接口限制。
- 单次请求 10~33 ms 浮动 ⇒ 实际可轮询上限在 **30~100 Hz** 之间。
- **静止不动的单位位置永远不变** ⇒ "变化率低" ≠ "刷新慢"(如机场 AI 防空)。
- ⇒ 录制时**别把游戏切到后台**, 否则采样分辨率自动掉到 30 Hz。

### 7.5 `/hudmsg`: 回放里只有 `damage` 文本, 且没有坐标

```
GET /hudmsg?lastEvt=0&lastDmg=0  →  { "events": [], "damage": [139 条] }
```

- 回放模式下**结构化击杀流 `events` 是空的**(实战里黑名单助手读的是它), 内容全在 `damage`;
- 每条字段: `id` / `msg` / `sender` / `enemy` / `mode` / **`time`(比赛秒数, 本次 112~214)**;
- 文本示例(已去零宽):
  `[0ANT0] ⋇stripy_opinion5 (T-80UD) 击毁了 ^HAKU^ _13024682 (90 式战车 B 型 (富士教导团))`
  另有 `A 的攻击引燃了 B`、`获得嘉奖"…"` 等, 需要按后缀分类;
- ⚠️ **中文字符之间夹着 U+200B 零宽空格**(一条实测 8 个)
  ⇒ 不做 `msg.replace("\u200b", "")` 就匹配不到 "击毁";
- ⚠️ 车型名**自带括号**(`90 式战车 B 型 (富士教导团)`)⇒ 正则要从右往左匹配;
- **消息里没有坐标**; `/map_obj.json` 又**没有名字** ⇒ 名字 ↔ 载具无法直接映射。

⇒ 可行做法: 用"某条轨迹消失的时刻 ≈ 击杀消息的 `time`"给每条命**事后贴名字**;
`id` + `time` 还能当两遍录制的**共享时间基准**(两遍都会出现同样的值)。

### 7.6 对"录制全场路线"的设计结论

1. **一次请求就包含全部可见载具**(42~43 KB)⇒ 录 1 辆与录 14 辆的请求成本完全一样;
2. 8111 只给观战方 ⇒ 要拿两方必须**切视角录两遍**; 静态地物两遍一致, 第二遍只录载具;
3. 分段规则: 出现 = 新生; **连续 ≥3 帧缺席 = 结束(阵亡)**; **亮蓝 → 深蓝 = 重生**;
   **一次性大批消失 = 视角切换/切图**(标 `view_changed`, 不能当阵亡);
4. 过滤 AI 防空(`Airdefence` 位置全程不变);
5. 输出建议逐车记 `(x, y, color, protected)`, 另存事件表(出现 / 消失 / 重生 / 保护结束)。

### 7.8 顶级权重的重生点类型(2026-10-21 加测, 直升机视角)

该图实测对象数 172(`respawn_base_tank` 128 = 64 蓝 + 64 红)。

| 类型 | 数量 | 说明 |
|---|---:|---|
| `respawn_base_fighter` | 2(1 红 1 蓝) | **固定翼**重生点(地图上两个飞机标志) |
| `respawn_base_ucav` | 2(1 红 1 蓝) | **大型攻击无人机(UCAV)** 重生点 |
| `airfield` 长矩形(≈0.049) | 4 | **固定翼跑道**:每方 1 条 |
| `airfield` 中矩形(≈0.0076) | 4 | **直升机坪**(离战场较远的那块) |
| `airfield` 短矩形(≈0.0038) | 4 | **直升机坪**(离战场较近、**白矩形更短**的那块) |

- **直升机重生点不是独立类型**,而是 `airfield` 的**短矩形** —— 只能按 `sx/sy/ex/ey`
  算出的**长度**区分:跑道 ≈0.049 > 远直升机坪 ≈0.0076 > 近直升机坪 ≈0.0038
  (归一化对角线;每方 2 个直升机坪, 共 4 个)。
- 同一块机场/坪会发**两条记录**:一条 **白 `#ffFFFA`(跑道/坪本体)**,
  一条**队伍色**(我方 `#174DFF` / 敌方 `#fa0C00`, 即重生点归属), 两者坐标完全重合。
- ⚠️ **`dx/dy` 语义随 `type` 变**:`aircraft` / `Player` 是单位方向向量;
  而 `respawn_base_fighter`(`dx=-286, dy=-90`)、`respawn_base_ucav`(`dx=-20, dy=-0.8`)
  是别的量(疑似跑道方向/长度), **不能当朝向**用。
- **AI 航母:本次未出现** —— 全量 172 个对象里没有任何 `carrier` 类型, JSON 里也搜不到 carrier/航母。
  航母在顶级图上是“彩蛋”单位、离战场很远(陆战也不联动海军), **可能与未点亮有关**;
  暂按“拿不到”处理, 将来若真拿到再补。

### 7.9 侦察无人机(Scout Drone)视角(2026-10-21 加测)

轻坦/步战车的侦察无人机在回放里观战时, 8111 会出现**两个黄色 `#faC81E` 对象**:

| `type` | `icon` | 说明 |
|---|---|---|
| `aircraft` | `Player` | **摄像机所在的无人机**(带 `dx/dy` 朝向) |
| `ground_model` | `IFV` / `LightTank` 等 | **同一玩家的本体地面载具** |

⇒ **全局录制时的注意点**:

- **"黄色"不再唯一表示摄像机**:按颜色认自机会认到两个对象;
  认"摄像机"要看 `icon == "Player"`, 认"本体地面车"要看"另一条黄色 + `type == ground_model`";
- `Player` 的 `type` 再次变成 `aircraft`(与观战飞机时相同)⇒
  它表示"**摄像机所在的实体**", 不一定是地面载具;
- 无人机**没有独立 icon**, 也没有高度字段 ⇒ "侦察无人机"与"观战飞机"在数据上**无法区分**;
- 无人机视角同样会带出**远处机场的 10 个 AI 防空**(`Airdefence`, 坐标 2.9~3.4,
  **远超 0~1 的地图范围**)⇒ 录制/画图必须过滤, 否则会被当成 10 个远处目标, 且坐标溢出会画到图外。

**全量实测(暂停在无人机视角时抓的, 297 个对象)**:

| `type` | `icon` | 数量 | 说明 |
|---|---|---|---|
| `respawn_base_tank` | 同名 | 256 | 双方各 128 个候选重生点(静态) |
| `airfield` | `none` | 12 | 只有 `sx/sy/ex/ey`, **没有 `x/y`** |
| `ground_model` | `Airdefence` | 10 | 机场 AI 防空, **坐标 2.9~3.4(越界)** |
| `ground_model` | `IFV` / `MediumTank` / `LightTank` / `SAM` | 6/4/2/1 | 真正的车辆(含自己的车) |
| `capture_zone` | `capture_zone` | 3 | 战区 |
| `respawn_base_fighter` | 同名 | 2 | 空中重生点(静态) |
| `aircraft` | `Player` | **1** | 就是摄像机所在的无人机 |

配色: `#174DFF`×154(蓝=友方)、`#fa0C00`×132(红=敌方, 全在静态地物上)、
`#ffFFFA`×7(中立)、`#faC81E`×2(黄=自己: 无人机 + 本体车)、`#67D756`×1(绿=小队)。

**其他要点(同一次实测)**:

- `icon` 才是"车种", `type` 只有 `ground_model` / `aircraft` 两大类 ——
  所以"空中单位"的判据就是 **`type` 属于 `aircraft` / `helicopter`**, 非常干净;
- 敌方地面车在这个视角下**一个都没有**(回放只给观战方), 印证了"一局要分 A/B 两次录制";
- **`/indicators` 在这个视角下返回 `{"valid": false}`**(只有这一个键)⇒
  拿不到载具名与速度; 单条线路录制仍能录坐标, 但速度会一直是 0;
- `/map_info.json` 仍是 `valid: true`, 只有 `grid_*` / `map_min` / `map_max` 之类, **没有高度**。

⇒ **尚缺一个数据点**: 这里只有"自己在飞", 看不到**别人**的侦察无人机长什么样
(它的 `type`/`icon` 是否也叫 `aircraft`, icon 会是 `UAV` 还是别的)。
需要在多方混战、有人放无人机的时刻再抓一次, 才能确定无人机是否真能按名字认出来。

#### 7.9.1 侦察无人机 vs 固定翼: **数据上分不出来**(2026-10-21 实测)

多人回放里, 屏幕上同时出现"一个绿色的车 + 一个绿色的飞机"时抓到的两条对象:

```json
{"type":"aircraft",    "icon":"Fighter", "color":"#39D921", "x":0.330122, "y":0.534358,
 "dx":0.133541, "dy":-0.991043, "icon_bg":"none", "blink":0}
{"type":"ground_model","icon":"IFV",     "color":"#67D756", "x":0.330062, "y":0.535045,
 "icon_bg":"none", "blink":0}
```

* 前者 = **侦察无人机**, 后者 = **放出它的那辆步战车**(用户肉眼确认);
* 两者坐标只差 `(0.00006, 0.00069)` —— 无人机几乎就在车顶上;
* **无人机的 `icon` 就是 `"Fighter"`**, 与真正的固定翼**一字不差**;
  也没有高度、没有 `id`、没有名字 ⇒ **无法用任何字段把侦察无人机和战斗机分开**。

同时段的另一架固定翼(蓝 `#174DFF`)在 10 秒内飞了 0.065(约 0.0066/s),
而无人机在 3 秒内只挪了 0.0135(约 0.0045/s) —— 速度量级差别不大,
且地图尺度未知(0.0045/s 在 8km 图上是 36 m/s, 在 20km 图上是 90 m/s), **不足以当判据**。

⇒ **全局录制的实际口径**: 因为有 `type == "aircraft"` 这一条干净的分类,
"要不要录空中"就变成一个简单的取舍:

| 方案 | 结果 |
|---|---|
| 录 `aircraft` | 无人机、固定翼、直升机**全都会**被录进来(方向与我们只关心地面相悖) |
| 不录 `aircraft` | 地面一辆不落, 无人机也一起跳过(无人机本身就是贴着释放者的一个小抖动, 信息量很低) |

**当前代码选的是后者**(`global_record.recordable()` 里空中一律返回 False,
只保留 `uav/drone/scout/recon` 字样的"备选口"—— 实测从未出现过)。

#### 7.9.2 观战视角切到空中单位时, 坐标会被整体换算(2026-10-21 实测)

回放里观战的那位玩家上了固定翼之后, 8111 会把地图切成**空战图**, `/map_obj.json` 里
**同一批地面单位的坐标整体被缩放 + 平移** —— 全局录制原来就在这儿断线(帧间最近邻
全部脱靶, 线突然断掉、换个地方重新开始)。用暂停回放 + 在两个视角之间来回切,
把 259 个静态锚点(256 个 `respawn_base_tank` + 3 个 `capture_zone`)抓下来对比:

| | 陆战视角(地面单位) | 空战视角(Su-25 等) |
|---|---|---|
| 锚点数量 | 259 | **259**(完全一样的一批点) |
| 锚点包围盒 x | `[0.3196, 0.6655]` | `[0.5200, 0.5416]` |
| 锚点包围盒 y | `[0.2550, 0.6746]` | `[0.4534, 0.4797]` |
| `/map_info.json` | `map_min=[0,0]` `map_max=[4096,4096]` | `map_min=[-32768,-32768]` `map_max=[32768,32768]` |
| `Player` 的 `type` | `ground_model` | `aircraft` |

反解出来的关系**精确**到 1e-5(拟合残差 0.00001, 无旋转):

```
空战坐标 = (陆战坐标 + (8, 7)) / 16        # 即 陆战坐标 = 16 × 空战坐标 − (8, 7)
```

- 也就是说空战图的归一化坐标系覆盖**大 16 倍**的范围, 地面战场落在它中间的一小块;
  来回切换时每次都能原样还原(切回地面视角 → 判为"同坐标系")。
- `map_max − map_min` 也从 **4096 → 65536(×16)**, 与坐标缩放比一致。
  ⚠ 因此**速度尺度不能跟着变**: 坐标换算回陆战图之后, 边长必须继续用 4096
  (`route_recorder._update_map_size` 在“非同一坐标系”时直接跳过更新)。
- 机场/空中单位的坐标在空战图里可以到 2.9~3.4(`Airdefence`), 换算回陆战图后
  是 38 左右 → 仍然会被 `0~1` 的范围过滤掉; 空中单位本来也不录。

**程序里的做法**(`global_record.py`): 录制开始时把这一帧的静态锚点记成"参考坐标系",
之后每帧用 `fit_frame()` 反解相似变换(质心/bbox/最近邻中位数多给几个初始尺度候选 +
4 个 90° 旋转 + 最近邻配对最小二乘), 把单位坐标**换算回陆战图**再喂给跟踪器;
残差过大或锚点太少就**不认**(宁可这一帧不换算, 也不能把点画到错的位置)。
换过视角之后的 5 秒内不判"被击毁"(`VIEW_CHANGE_GRACE`), 因为那几秒单位消失更可能是
"从这个视角看不见了"。

现场核对工具: `tools/probe_frame_align.py`(只读 8111, 切换视角时实时打印锚点 bbox
与反解出的变换)。
